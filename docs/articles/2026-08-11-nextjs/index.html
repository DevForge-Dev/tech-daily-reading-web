await しない — Server→Client へ Promise を渡して use() で解くストリーミング

遅い取得を await するとページごとブロックする。Promise のまま Client に渡し React 19 の use() で解けば、サーバー起点で早く始まり、フォールバックから即ストリームできる。

📅 2026年8月11日 ⏱ 約3分 🔗 出典 3 件

RSC 時代のデータ取得は「Server Component で await して確定データを props で渡す」が基本だ。ところが遅い取得を await すると、その Server Component（ひいてはページ）全体がその場でブロックされる。これを避ける定石が、Server Component で取得関数を呼ぶが await せず、返ってきた Promise をそのまま Client Component に渡し、Client 側で React 19 の use() で解くパターン。Next.js 16.3 公式（2026-07-24 更新の Fetching Data ガイド）が「Client でデータを取る手段」の第一に挙げる、App Router の中核だ。

効果は、取得がサーバー起点で早く始まり（クライアント側のリクエストウォーターフォールを回避）、レスポンスが即ストリームされること。use() を呼ぶコンポーネントは Promise 解決まで最寄りの <Suspense> にサスペンドされ、JS ロード完了前にプレレンダー済み HTML（フォールバック→本体）が見える。

最重要の落とし穴は「Promise は安定していなければならない」こと。use() を呼ぶコンポーネントのレンダー本体内で Promise を新規生成すると、毎レンダーで新 Promise が生まれ、サスペンド→再レンダー→また新 Promise…の無限サスペンドループになる。Promise は Server Component／ルートローダー／useMemo など作り直されない場所で生成する。

'use client'
// ❌ NG: レンダー本体で Promise を新規生成 → 無限サスペンド
export default function Bad({ id }) {
  const user = use(fetchUser(id))   // ここで作ってはいけない
  return <p>{user.name}</p>
}
// ✅ OK: 親(Server Component / useMemo / cache)で作って渡す

ほかに、use() は重複排除しないため共有データは取得関数を React cache() で包む。エラーは try/catch で捕まらず最寄りの Error Boundary（error.tsx）へ伝播する。ローディングは Suspense、失敗は Error Boundary と役割を分ける。

使い分け：サーバーで解いて確定値を渡せるなら await。クライアントで解く必要がある／先にフォールバックを見せてストリームしたいときだけ Promise を渡して use()。「まず Server Component で読めないか？」を先に検討するのが定石だ。SWR 2.3+／TanStack Query はこの原始的な仕組みの抽象で、再検証やミューテーションが要るならライブラリ、一度読むだけなら素の use() で十分。
