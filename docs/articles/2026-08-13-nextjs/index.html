Next.js 16をセルフホストする — standalone × Docker × cacheHandlerで本番の落とし穴を塞ぐ

「next build して next start」で済むのは単一インスタンス＋永続ディスクの時だけ。コンテナ化・水平スケールで噴出するISR分裂・Server Action復号失敗・ストリーミング詰まりを、公式ガイドの具体設定で塞ぐ。

📅 2026年8月13日 ⏱ 約4分 🔗 出典 4 件

Vercel以外（自前VPS・Docker・K8s・Cloud Run）にNext.js 16 App Routerを載せる需要は根強い。だがnext startで素直に動くのは単一インスタンス＋永続ディスクの時だけ。コンテナ化・水平スケール・ローリングデプロイに入ると、ISRキャッシュがpodごとに分裂する／Server Actionが復号できず落ちる／ストリーミングがproxyでバッファされPPRの旨味が消える、といったチュートリアルに載らない落とし穴が一気に出る。公式セルフホストガイド（16.3.0, 2026-04-30更新）は、これらを具体設定で塞ぐ手順を明文化した。

土台は output: 'standalone'。.next/standalone/ に本番実行に必要なファイルとnode_modulesだけを抽出した自己完結フォルダが出る（イメージが激減）。ここで最大の落とし穴が3つ。(1) 起動は next start ではなく node server.js。(2) standaloneに静的アセットは含まれないので .next/static と public/ を手動コピー（忘れるとCSS/JS/画像が全部404）。(3) next/image を使うなら sharp を本番依存に入れ、デプロイ先と同じOS/archでインストール（MacでビルドしてxLinuxへ、はネイティブバイナリ不一致の地雷）。

キャッシュとマルチインスタンス整合。ISR・revalidate・生成済み静的ページは既定で各インスタンスのローカルディスク＋メモリ（既定50MB）に保存されるため、LB配下の複数コンテナでは内容がズレる。対策はカスタム cacheHandler ＋ cacheMaxMemorySize: 0 で値をRedis/S3等の共有ストアへ。さらにServer Functionのクロージャ暗号鍵 NEXT_SERVER_ACTIONS_ENCRYPTION_KEY を全機共通・ビルド時固定（違うと「Failed to find Server Action」）、deploymentId でローリング中の版スキューを検出、refreshTags() でタグ失効を全機同期する。

// next.config.js（マルチインスタンス）
module.exports = {
  output: 'standalone',
  cacheHandler: require.resolve('./cache-handler.js'),
  cacheMaxMemorySize: 0,
  deploymentId: process.env.DEPLOYMENT_VERSION,
}

ランタイム環境変数とストリーミング。NEXT_PUBLIC_* はビルド時にJSへインラインされ後から変えられない。サーバー専用変数は await connection() で動的化してから process.env を読むと確実にリクエスト時評価になり、1イメージを dev→staging→prod へ昇格できる。ストリーミング／PPRはnginxが応答をバッファすると死ぬので proxy_buffering off; か X-Accel-Buffering: no を必ず入れる。

注意点：standaloneの3点コピー忘れ・sharpのOS不一致・非rootでのISR書き込みEACCESが定番の詰まり。runtimeConfig はstandalone非対応なので process.env 直読みへ移す。ひとことまとめ：セルフホストの本質は「キャッシュと暗号鍵の共有」。standaloneで軽くし、共有ストアと共通鍵でスケールに耐えさせるのが勘所だ。
