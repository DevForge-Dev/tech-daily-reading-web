厳格CSPをnonceで — proxy.ts × strict-dynamic × 動的レンダリングのトレードオフ

'unsafe-inline'を捨て、リクエスト毎の使い捨てnonceでXSSを封じる。Next.js 16では起点が proxy.ts に改名。代償は動的レンダリング必須という重い判断。

📅 2026年8月22日 ⏱ 約3分 🔗 出典 4 件

CSP（Content Security Policy）は「どのオリジンのscript/style/画像等を実行・読込してよいか」をブラウザに宣言し、XSS・クリックジャッキング・インジェクションを緩和する多層防御の最前線。認可が「誰が何をできるか」を守るのに対し、CSPは「注入された悪意あるスクリプトをそもそも走らせない」層を担う。今日の主役は、その厳格化の定石＝nonce＋'strict-dynamic'だ。

何が新しい / 重要か

素朴に script-src 'self' 'unsafe-inline' にすると全インラインscriptを許可＝XSS対策としてほぼ無力になる。厳格CSPはリクエスト毎に生成する予測不能なランダム値=nonceを使う。攻撃者は各リクエストで変わるnonceを当てられないため注入scriptは実行されない。Next.js 16では従来の middleware.ts が proxy.ts に改名され、CSP実装の起点も変わった。静的生成を維持したい場合の逃げ道として、実験的SRI（ハッシュCSP、v14で追加・App Router専用）も用意されている。

実装のキモ

ポイントはCSPヘッダをリクエスト側にも載せること。Next.jsはSSR中にリクエストのCSPヘッダをパースして 'nonce-{value}' を取り出すため、レスポンスだけに付けても自動適用されない。

// proxy.ts (旧 middleware.ts)
const nonce = Buffer.from(crypto.randomUUID()).toString('base64')
const csp = `script-src 'self' 'nonce-${nonce}' 'strict-dynamic';`
const h = new Headers(request.headers)
h.set('x-nonce', nonce); h.set('Content-Security-Policy', csp)
const res = NextResponse.next({ request:{ headers:h } })
res.headers.set('Content-Security-Policy', csp)  // レスポンス側にも
return res

'strict-dynamic' は「nonce/hashで信頼したscriptが動的に読む子scriptにも信頼を伝播」させ、効くブラウザでは 'self' やドメインのホワイトリストが無視される＝抜け道を塞ぐGoogle推奨の書き方。ページ側は await connection() か dynamic='force-dynamic' で動的化しておく。

トレードオフ（nonce vs SRI vs unsafe-inline）

最大の落とし穴はnonceは動的レンダリング必須＝静的最適化・ISRが無効、追加設定なしではCDNキャッシュ不可、PPRと非互換。厳格さ＞キャッシュなら nonce、静的生成＋CDNを保ちたいなら実験的SRI（experimental.sri）、XSS対策として弱い最終手段が 'unsafe-inline'。開発時のみ 'unsafe-eval' が要り（本番は不要）、WebAssemblyは 'wasm-unsafe-eval'、_next/static や prefetch は matcher で除外する。

ひとこと

16のCache Components時代は「厳格CSPを取るか、静的最適化を取るか」の設計判断がそのまま性能に直結する。まず自分のページが本当に動的化してよいかを見極めてから nonce か SRI を選ぶ。
