App Router のエラー処理を制する — error.tsx / catchError / retry() と「制御フローを握りつぶさない」

Error Boundary とフレームワークの制御フロー（notFound/redirect）が同じ throw に乗る二重性が落とし穴。Next.js 16 は reset() を retry()（サーバー再取得）へ進化させ、catchError（16.3安定）がコンポーネント単位の正しい境界を提供する。

📅 2026年7月30日 ⏱ 約3分 🔗 出典 4 件

App Router のエラー処理は、React の Error Boundary と、Next.js が制御フローとして投げる特殊エラー（notFound()／redirect()／unauthorized()／forbidden()）が同じ throw の仕組みに乗っているのが要だ。この二重性を理解しないと、try/catch や react-error-boundary が404やリダイレクトを握りつぶす、あるいは「Try again」を押してもServer Componentのデータが再取得されず何も直らない、という定番の罠にはまる。

2026年に状況を変えたのが3点。(1) Next.js 16 で回復コールバックが従来の reset()（クライアント再レンダーのみ）から retry()（サーバー側で再取得＆再レンダー）へ進化。(2) catchError（next/error）が16.2で unstable_catchError として入り 16.3で安定化——制御フローを正しく素通しし retry() でサーバーデータを取り直す、コンポーネント単位の境界。(3) global-not-found.tsx（16新規）でルーティング層から全体404を返せる。

設計の芯は「予期したエラー」と「予期しないエラー」を分けること。バリデーション失敗や在庫切れは throw せず戻り値にして useActionState で返す。DBダウン等の予期しないエラーだけを throw し error.tsx／catchError に拾わせる。notFound() や redirect() は throw で表現されるがエラーではない——握りつぶさないのが最重要だ。try/catch するServer Componentは、catch先頭で unstable_rethrow(err) を呼び、フレームワーク内部エラーだけを素通しする。

'use client'
import { notFound, unstable_rethrow } from 'next/navigation'
export default async function Profile({ id }) {
  try {
    const u = await getUser(id)
    if (!u) notFound()          // NEXT_NOT_FOUND を投げる
    return <p>{u.name}</p>
  } catch (err) {
    unstable_rethrow(err)       // 制御フローは素通し
    throw new Error('取得に失敗しました')
  }
}

実装のポイント：error.tsx／global-error.tsx は 'use client' 必須。global-error.tsx はルートレイアウト自体の例外専用で発火するとレイアウトを丸ごと置換するため <html>／<body> 込みの自己完結UIにする。回復は一過性エラー向けの retry() を使う。注意点：forbidden()／unauthorized() は experimental.authInterrupts が必要で2026年時点でもまだ experimental（本番非推奨）、ルートレイアウトからは呼べない。本番ではErrorのメッセージは伏せられ digest だけが渡るので、サーバーログと突き合わせて原因を追う。まとめ：境界を島に切り、制御フローを素通しし、回復は retry() で——これがApp Routerのエラー処理の定石だ。
