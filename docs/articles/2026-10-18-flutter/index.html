Dart 3.14 Augmentations と 3.50前の環境整備、Lottie実務投入、DIスペクトラム、jank切り分け

現行stableは3.47.7/Dart3.13.5、3.50 betaのブランチは10/6カット済み。macrosの穴を埋めるAugmentationsを軸に、Lottieの自前制御、DIの6風味、DevToolsでのjank切り分けまで、11月の3.50に向けた実務4題を通して読む。

📅 2026年10月18日 ⏱ 約6分 🔗 出典 4 件

Flutter は次の節目が近い。現行の安定版は Flutter 3.47.7 / Dart 3.13.5（10/8 patch）、beta は 3.49系 / Dart 3.14で、次の stable 3.50 は11月、その 3.50 beta のブランチは10/6にカット済み（master に10/6以前にマージされたPRが確定）。つまり今は「3.50に何が入るか」がほぼ見えていて、flutter channel beta && flutter upgrade で先取り検証できる好機だ。この日は、言語・アニメ・アーキ・性能の4領域を横断して整理する。

Dart 3.14 の目玉は Augmentations — macros の実務的な代替

無期限ポーズに入った macros の穴を埋めるのが Augmentations だ。既存クラスに後付けでメンバー・メソッド・コンストラクタを足せる言語機能で、augment 宣言により元クラスを汚さずに拡張を分離できる。狙いは codegen（build_runner + source_gen）が生成コードを本体へ注入する土台を提供すること。マクロのように「コンパイル時に型を生やす」世界をもう一度、しかし言語機能として現実的な形で取り戻す動きだと捉えるとわかりやすい。beta で早めに素振りし、codegen 依存の生成物がどう変わるかを確認しておきたい。

3.50の確定事項も実務に効く。WebAssembly の遅延ロードが stable GA に昇格、Android は Impeller 一本化が完了（legacy Skia バックエンドを Android 10 以降で引退）、Android 17 の day-zero 対応も同梱される。SDK 内蔵の Material/Cupertino は11月で正式 deprecation となり、移行は dart fix --apply --code=migrate_design_widgets、import は package:material_ui/material_ui.dart 系へ切り替える。準備としては、安定を 3.47.7 に pin しつつ beta で CI を回し、flutter build web --wasm と appbundle を今のうちに緑にしておくのが堅い。

Lottie を AnimationController で駆動する（lottie 3.6.1）

Lottie は「貼って終わり」でなく自前制御するほど化ける。controller: に AnimationController（vsync は TickerProviderStateMixin）を渡し、onLoaded(composition) で _controller.duration = composition.duration を設定してから forward() すると、前後再生・区間ループ・停止が自在になる（dispose() は必須）。純粋ループだけなら repeat:/animate: でも足りる。フレームレートは既定が FrameRate.composition（AE書き出しレート）で、FrameRate.max にするとデバイス上限（最大120FPS）に追従する。さらに LottieDelegates を使えば、ValueDelegate.color/.opacity/.position でレイヤーをパス指定し、1本の .json をテーマ色やデータに応じて動的に着色・文言差し替えできる。コスト面では renderCache（v3.0〜） が各フレームをオフスクリーンに遅延ラスタ化して再利用し CPU/電力を下げる（代償はメモリ増）。使い分けの基準は明快で、受動再生のデザイナ資産は Lottie、対話・state machine は Rive、常時ループは画面外で停止させる。

DI は『スペクトラム』で選ぶ

状態管理・DIは一つの正解を探すより、6つの風味の連続体として捉えると整理しやすい。

肝は feature-scoped DI＝依存を機能の寿命に縛ること。コントローラ/ViewModel はその機能ツリーの頂点に注入し、アプリ全体には晒さない。get_it なら機能突入時に pushNewScope→lazy singleton 登録、離脱時に popScope で破棄する（手動ライフサイクルが弱点で、予期せぬ遷移やクラッシュで pop 漏れ→リーク）。ツリー型の Provider ならルート widget 除去で自動 dispose、Riverpod は autoDispose で深いネスト無しに機能スコープ相当を得る。土台は feature-first + go_router、新規は Riverpod 3（autoDispose 既定）、監査・大規模は Bloc 9、細粒度は signals、が指針になる。

スクロール jank は『どのスレッドが赤か』で切り分ける

最後に性能。計測の型は flutter run --profile（debug は release 比2〜10倍遅い）→ Performance で janky スクロールを Record → 赤フレームをクリックして Frame Analysis。ここでUI スレッドが赤なら Dart コード、Raster スレッドが赤ならシェーダ/画像/エフェクトを疑う、という分岐が全ての起点だ。予算は 60Hz=16.67ms / 120Hz=8.33ms で、vsync 余白を見て各スレッド実質8ms未満を狙う。UI スレッドの典型犯は build 内での巨大 JSON パース（→compute()/isolate へ）、巨大サブツリーを巻き込む setState（→変化部分を小 widget に隔離）、build 内での TextStyle/Paint の new（→ファイルスコープの const へ巻き上げ）。Raster 側は Opacity/BackdropFilter/antiAlias な ClipRRect が誘発する saveLayer、4K 画像のベタ表示（→cacheWidth/cacheHeight でデコード時ダウンサンプル）、初回シェーダコンパイル（Impeller の AOT で解消）が定番だ。

まとめ — 試すなら

この日の4題は「11月の3.50を迎える準備」で一本につながる。Augmentations を beta で素振りして codegen 生成物を確認し、--wasm/appbundle のビルドを緑に保つ。アニメは Lottie を AnimationController + renderCache で実務投入、DI はチームで一方式に統一して feature-scoped で寿命を縛る、性能は「赤いスレッドを特定してから手を打つ」。どれも派手さはないが、3.50 の Impeller 一本化と Wasm GA が来たときに効いてくる地力だ。
