Next.jsのRUM実装 — useReportWebVitalsで「ラボ値」から「フィールド値」へ

Lighthouseのスコアは理想環境の一発計測。検索順位を左右するのは実機・実回線のフィールドデータだ。Next.js標準のuseReportWebVitalsで、有料サービス無しの自前RUMを組む要点と5つの落とし穴。

📅 2026年10月26日 ⏱ 約4分 🔗 出典 5 件

LighthouseやPageSpeedの数値は「1台・1回・理想的な回線」のラボスコアにすぎない。Google検索がCore Web Vitalsを評価するのは フィールドデータ＝実ユーザーの28日間・75パーセンタイル だ。バンドル削減や画像最適化で“直した”つもりでも、実機の分布を計測しないと効果は分からない。ここで効くのが RUM（Real User Monitoring） で、Next.jsは next/web-vitals の useReportWebVitals を標準提供している。

何が新しい／重要か

内部はGoogleの web-vitals（v5系）。報告するのは TTFB / FCP / LCP / CLS / INP に加え、Next.js固有の Next.js-hydration や route-change-to-render も metric.name で受け取れる。重要なのは時代の変化で、2024/3にINPがFIDに代わりCore Web Vital入り、FIDは2024/9に完全廃止。計測コードが今もFIDを見ているなら時代遅れだ。しきい値（good / needs-improvement境界 / それ超はpoor）は次の3指標が中心。

仕組みと実装のポイント

フックなのでRSCでは使えない。'use client' を付けた専用コンポーネントに隔離し、レイアウト（Server Componentのまま）へ差し込む。送信は離脱に強い navigator.sendBeacon() を第一選択に、無ければ fetch(url,{keepalive:true})。累積系は二重加算を避けるため delta を送るのが基本だ。

'use client'
import { useReportWebVitals } from 'next/web-vitals'
// ← コンポーネント外に定義。毎レンダーで参照が変わると重複報告される
function report(m) {
  const body = JSON.stringify({ name:m.name, value:m.value, delta:m.delta,
    rating:m.rating, id:m.id, path:location.pathname })
  navigator.sendBeacon?.('/api/vitals', body) ||
    fetch('/api/vitals', { body, method:'POST', keepalive:true })
}
export function WebVitals(){ useReportWebVitals(report); return null }

受け口の Route Handler は req.text() で受けると堅い（sendBeaconは text/plain で飛ぶことがある）。遅い“原因”まで欲しいときは web-vitals/attribution ビルドに切り替えると、INPなら interactionTarget（遅かった要素）・inputDelay・processingDuration まで取れる。

5つの落とし穴

① コールバック参照を固定（インライン関数は毎レンダー参照が変わり重複報告）。② Client Component必須（'use client' はファイル先頭）。③ 送信はsendBeacon/keepalive（普通のfetchは離脱で中断されうる）。④ reportAllChanges は デバッグ用で本番非推奨。⑤ 集計は1行の生データでなく 「ページ種別×デバイス×接続種別」で75パーセンタイルの分布 として見る。

ひとことまとめ

「直したか」はラボでは分からない。useReportWebVitalsで自前RUMを組み、INP時代のフィールド分布で検証する——これが順位に効く計測の最短路だ。
