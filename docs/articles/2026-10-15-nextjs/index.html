バンドルサイズ最適化 — barrel file問題と optimizePackageImports / next analyze

barrel経由のimportでdevチャンクが552kB→64kB（約88%減）。標準のoptimizePackageImportsとnext analyzeで“use client”ツリーを削る。

📅 2026年10月15日 ⏱ 約3分 🔗 出典 4 件

App Routerでは Server Components のおかげでサーバ側コードは原則クライアントに出ない。だがClient Components('use client')が import したものはすべてクライアントバンドルに入る。LCP/INPはクライアントJSの量にそのまま効くので、ここを削るのがパフォーマンスの本丸になる。今日のテーマは最大級の落とし穴であるbarrel fileと、Next.js標準機能での潰し方。

何が問題か — barrel fileは“全部辿る入口”

barrel fileとはexport * from './x'を集めたindex.tsのこと。1つの名前をimportしただけでも、バンドラ・tsc・devサーバは背後のモジュールグラフを全部解決・評価する。参考記事の実測では、1つのフックをbarrel経由でimportしただけでdevのクライアントチャンクが552kB。barrelを外して直接importしたら64kB——約88%削減だ。

tree-shakingが効く条件は厳しく、(1)ESM出力、(2)副作用なし("sideEffects": false)、(3)トランスパイル後も純粋に見える、が揃って初めて効く。CommonJS出力だと無効、devモードは原則shakingしないため、cold startごとに全モジュール読み込みが起き得る。barrelは循環参照(Cannot access 'X' before initialization)の温床でもある。

標準機能での対処

experimental.optimizePackageImportsは、barrel importをビルド時に「使っているper-moduleの直接import」へ自動で書き換える。named importの書き味は保ったまま、実際に使うモジュールだけ読む。前提は対象パッケージがper-module出力(distがsrcをミラー)を持つこと。lucide-react・date-fns・@mui/material・recharts・react-icons/*などは既定で最適化されるので自分で足さなくてよい。計測はNext.js 16.1+のnext analyze(Turbopack Bundle Analyzer)が公式で、importチェーンまで辿れる。Webpack系は従来の@next/bundle-analyzer。

自分が試すなら

手順は「測る→大物を潰す→importを直す→クライアント処理をサーバへ寄せる」。まずnpx next analyzeでtreemapを開き、'use client'ツリーに紛れ込んだ重いライブラリ(syntax highlight/chart/markdownパーサ)を探す。自前の@/hooksバレル経由は@/hooks/useAuthのように兄弟直importへ。コードハイライトのような重処理は、Client Componentでprismを使う代わりにServer ComponentでshikiのcodeToHtmlを使い、クライアントには静的HTMLだけ返す。

注意点

optimizePackageImportsに足したのに縮まないときは、パッケージがper-module出力でない/CJSのことが多い。devチャンクが実際に縮んだか必ず確認する。next.config変更は再起動・再ビルドが要り、計測は本番ビルド(next build)基準で。自作パッケージ側なら"sideEffects": falseとサブパスexports("./*": "./dist/*.js")を吐き、CIにimport/no-cycleを入れておく。

ひとことまとめ

「本当にクライアントに要るか」をまず問い、barrelを外して標準のoptimizePackageImports+next analyzeで潰す。88%級の削減が普通にあり得る領域。
