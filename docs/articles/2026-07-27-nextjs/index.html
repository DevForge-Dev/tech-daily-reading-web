after() でレスポンス後に副作用を走らせる — ログ/分析をブロックせず、静的最適化も壊さない

after(callback)（next/server）は、レスポンス送信が終わった後にコールバックを実行するAPI。ロギング・分析・通知・キャッシュのウォームアップなど「応答をブロックしなくていい副作用」を本処理から切り離せる。15.1 で unstable_after から after へ安定化、16 でも推奨。肝は「リクエストタイムAPIではない＝ルートを動的化しない」点で、PPR/Cache Components を壊さず副作用フックを差し込める。

なぜ今これが話題か

RSC と Server Actions が定着し、「ユーザーへの応答」と「その裏で走らせたい副作用」を分けたい場面が増えた。after() はレスポンス（またはプリレンダー）がユーザーへ送信し終わった後にコールバックを走らせるAPIで、TTFB や応答完了を遅らせずにロギング・分析・監査・通知を後ろに逃がせる。v15.0.0-rc の unstable_after から v15.1.0 で after として安定化し、Next.js 16 系でも安定APIとして推奨されている。

何が新しい/重要か

最大のポイントは 「after はリクエストタイムAPIではない」こと。呼んでもルートは動的化しないので、静的ページ内で使えばコールバックはビルド時、またはリバリデート時に走る。つまり PPR / Cache Components の静的最適化を壊さずに副作用フックを差し込める。使える場所は Server Components（generateMetadata 含む）／ Server Functions／ Route Handlers／ Proxy（旧 middleware）。エラー時・notFound()・redirect() でも実行されるので、確実に走らせたいクリーンアップや監査に向く。

仕組み・実装のポイント

サーバー側APIなので 'use client' は不要。サーバーレスでは内部的に waitUntil(promise) でインボケーション寿命を延ばして実現する。Route Handler / Server Function の after 内では cookies() / headers() を直接呼べる。

import { after } from 'next/server'
import { headers } from 'next/headers'

export async function POST() {
  // 本処理（応答はここまでで確定）
  after(async () => {
    const ua = (await headers()).get('user-agent')
    logUserAction({ ua }) // 応答送信後に非同期実行
  })
  return Response.json({ ok: true })
}

注意点・落とし穴

Server Component 内の after コールバックでは cookies()/headers() を呼べない（レンダリング後に走り追跡外になるため）。対策はリクエストデータをレンダリング中に読み、値をクロージャで渡す。after 内で Set-Cookie は不可なのでクッキー書き込みは本体側で。処理時間は maxDuration に従うので、重い処理はキューやジョブ基盤へ逃がす。Cache Components では動的部分を <Suspense> で包み、その中で読んだ値を after へ渡す。

ひとことまとめ

after() は「応答をブロックしない後処理」の標準口。静的最適化を壊さず、失敗経路でも走るのが強み。cookies/headers の読み場所と maxDuration だけ押さえれば、ログ・分析・監査を素直に後ろへ逃がせる。
