Better Auth を App Router で正しく噛ませる — toNextJsHandler / nextCookies / RSCはcookieを書けない問題

Auth.jsがメンテナンスモードへ入り、公式が新規はBetter Auth推奨とした「本命側」の実装ナレッジ。焦点はNext.js 16のRSC/Server Actions/proxyという実行モデルに認証のcookie副作用をどう噛ませるか。RSCはcookieを書けない、nextCookiesは必ず最後、getSessionCookieは"NOT SECURE"——ハマりどころが集中する。

📅 2026年8月27日 ⏱ 約4分 🔗 出典 4 件

Auth.js(旧NextAuth)が2025-09-22にメンテナンスモード入りし、公式も新規は Better Auth 推奨とした地殻変動の「本命側」の実装ナレッジ。Better Auth（GitHub 29.5k★・現行1.x）はフレームワーク非依存・完全セルフホストのOSSで、NextAuthに無い2FA/パスキー/RBAC/組織(マルチテナント)/impersonationをプラグインとして公式提供する。2026年初頭にはBetter AuthチームがAuth.js本体の保守も引き継ぎ、新機能はすべてBetter Auth側という体制になった。

何が新しい/重要か

実務の核心は「Next.js 16のRSC/Server Actions/proxyという実行モデルに、認証のcookie副作用をどう噛ませるか」。骨格はサーバー側の betterAuth({...}) が返す auth インスタンス（auth.handler と、各エンドポイントを関数として直接呼べる auth.api）と、クライアントの createAuthClient()（内部はnanostores＋better-fetch、useSession等）。APIルートは app/api/auth/[...all]/route.ts に export const { GET, POST } = toNextJsHandler(auth) の1行。RSC/Server Actionでのセッション取得は auth.api.getSession({ headers: await headers() }) で、Next.js 16では headers() がPromiseなのでawait必須だ。

仕組みの勘所（落とし穴）

最重要の落とし穴はRSCはcookieをセットできないこと。cookie cacheの更新はRSCでは走らず、クライアントからServer Action / Route Handler経由で操作したときに初めて更新される。そして nextCookies() プラグインが無いと、Server Action内で signInEmail のようなcookieを書く関数を呼んでもSet-Cookieが付かず「ログインできたのにセッションが継続しない」典型バグになる。nextCookies() は必ずplugins配列の最後に置く。認可の階層も要注意で、getSessionCookie(request) はcookieの存在確認のみ・検証しないため、コメントで明示的に「THIS IS NOT SECURE!」——誰でも偽造して素通りできる。フル検証をしたいなら Next.js 16の proxy.ts でNodeランタイムの auth.api.getSession を使うか、各ページ/Server Actionで必ず再検証する（CVE-2025-29927のヘッダ偽装バイパスと同じ教訓＝middleware/proxyは境界ではない）。

実務での使いどころ・注意点

SaaSで2FA/組織/RBAC/パスキーが要る、または将来Next.js以外にも展開しうるならBetter Authが本命。逆に「DB無しの完全ステートレスJWTセッションで十分」なら従来のAuth.jsも依然選択肢、手離れ優先ならClerk。実装は lib/auth.ts（Server専用）にDrizzle等のアダプタと plugins:[nextCookies()]、BETTER_AUTH_SECRET（32文字以上）を置き、保護は各RSCで getSession→無ければ redirect('/sign-in')。useSessionやサインインフォームなどクライアントアクションを使う島だけ 'use client' に隔離し、初期セッションはRSCから props で渡してhydration mismatchを避ける。middleware→proxy移行は npx @next/codemod middleware-to-proxy . で自動化できる。

ひとこと

Better Authは「速い認証」ではなく「正しく境界を引ける認証」。RSCの制約を理解し、cookieはServer Action経由・認可はデータに近い所で再検証、という多層防御を最初から設計に織り込むのが要だ。
