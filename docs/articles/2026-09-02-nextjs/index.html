成功時のコンフェッティ／セレブレーション・バースト——canvas・依存ゼロ・reduced-motion対応でServer Actionの成功を祝う

購入完了やオンボーディング達成など「一度きりの達成」を祝う紙吹雪バーストを、外部依存ゼロのvanilla canvasで実装する。全画面固定オーバーレイ＋pointer-events:none、粒子物理（velocity→gravity→drag）、prefers-reduced-motionでの全面ゲート、useActionStateの成功結果をuseEffectで監視して発火——App Routerでの組み込みまで。多用は禁物、本当に嬉しい節目に限定する。

📅 2026年9月2日 ⏱ 約4分 🔗 出典 4 件

コンフェッティ（紙吹雪）バーストは、GitHub・Linear・Stripeなどが要所で使う定番の“喜びのマイクロインタラクション”だ。トーストや送信ボタンの成功モーフが状態を伝えるフィードバックなのに対し、コンフェッティは情報量ゼロの純粋な情緒的報酬——「やった！」の一瞬を演出する。だからこそ決済成功・実績解除・オンボーディング完走のような稀で本当に嬉しい節目に限定し、フォーム保存のたびに撒かない。実装はデファクトのcanvas-confetti（約6KB）を入れるか、40〜60行のvanilla canvas自前か。ここでは依存ゼロの自前を軸にする。

なぜ DOM でなく canvas か

数十〜数百個の紙片を同時に動かすと、各粒子を<div>にした場合は毎フレーム数百要素のtransform書き換え・レイヤ合成でカクつく。canvasなら1要素に全粒子をfillRectで描くだけで、リフローもDOMミューテーションも起きず60fpsを保ちやすい。最重要の実務ポイントは置き方で、祝いは画面全体に降らせたいので全画面固定オーバーレイにし、必ずpointer-events:noneを付ける（忘れるとページ全体がクリック不能になる最頻出事故）。canvas内部解像度はdevicePixelRatioを掛けないとRetinaでぼやける。祝い終わったら要素をDOMから外してGPUメモリを解放する。

App Routerでの組み込み（本題の肝）

canvas/window/matchMedia/requestAnimationFrameはブラウザAPIなので、撃つコンポーネントは'use client'。ただし島を最小化し、ページ本体・データ取得はRSCのまま。決済/登録はServer Actionで行い、サーバーの成功をクライアントのcanvasへ橋渡しする。定番はuseActionStateの戻り値をuseEffectで監視して発火する構図だ。

useEffect(() => {
  if (state.ok && state.ts !== fired.current) {
    fired.current = state.ts;
    if (!matchMedia('(prefers-reduced-motion: reduce)').matches) fireConfetti();
  }
}, [state]);

Server Action側は{ ok:true, ts:Date.now() }のようにtsを必ず返す。同じok:trueの連続でもuseEffectを再発火させるためだ。redirect()を挟むと同一stateで発火しないので、祝ってから遷移するなら遷移前に撃つか、遷移先でcookieフラッシュして1回だけ撃つ。SSRでcanvasを触らなければhydration mismatchも起きず、JS未ロードでも<form action>の素のPOSTで購入自体は成立する（プログレッシブエンハンスメント）。

アクセシビリティ（必須）

コンフェッティは動きが激しく、前庭障害等で動きに敏感なユーザーに有害になりうる。canvas-confettiでも「reduced-motionで止まらない」ことが長く課題だったので、自前なら発火直前に必ずmatchMedia('(prefers-reduced-motion: reduce)').matchesで全面ゲートし、trueなら一切出さない。成功の事実は必ず静的テキスト＋role="status" aria-live="polite"で伝え、canvasはaria-hidden="true"の純装飾に留める。明滅・ストロボは避ける。

ひとこと

紙吹雪は“撒きすぎると陳腐化する”のが最大の落とし穴。頻度の高いフィードバックはトーストやボタンモーフに任せ、コンフェッティは本当の節目にだけ。自前実装なら挙動を完全制御でき、バンドルも増やさずに済む。
