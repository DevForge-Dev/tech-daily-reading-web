MDX × App Router 実戦 — @next/mdx・リモートMDX・Shikiハイライト・Turbopackの罠

文章＋React部品を同居させる定番MDXを、ローカル/リモート2系統でApp Routerに載せる。RSC既定で軽く、frontmatterとハイライトの流儀、Turbopackの制約まで一望する。

📅 2026年9月24日 ⏱ 約4分 🔗 出典 4 件

ブログ・ドキュメント・変更履歴・LPコピーのような「文章＋ときどきインタラクティブ部品」を扱うNext.jsサイトの定番が MDX（Markdownのスーパーセットで本文中にJSXを直接書ける）。App Routerでは公式プラグイン @next/mdx が第一級で、.md/.mdxをそのままページにでき、しかも本文は既定でServer Componentとしてレンダーされる＝クライアントJSを増やさずリッチな本文を出せるのが効く。地味だが「コンテンツ主体のNext.jsサイト」を作るなら避けて通れない土台だ。

いま押さえるべき2系統

実装は大きく2つ。①ローカルMDXは@next/mdxでファイルをビルド時コンパイルし、app/blog/hello/page.mdxがそのまま/blog/helloになる。速く型も効き、generateStaticParams＋dynamicParams=falseでSSGと相性が良い。②リモートMDXはCMS/DBから取ったMDX文字列をサーバーでコンパイルする経路で、コンテンツをコードから分離できる。ローカルは速さと型、リモートは分離、と割り切って選ぶ。

2026年に効いた地殻変動

長年の定番 next-mdx-remote は2026-04-09にアーカイブ（保守終了）。リモートMDXの本命は維持フォークの next-mdx-remote-client、またはビルド時に型付きコンテンツ層を作る Velite / Content Collections 系へ移った。移行時の落とし穴として、MDXRemote(RSC)は async Server ComponentでReact Contextを持てないためMDXProviderは使えず、部品はcomponents propで明示的に渡す必要がある。

流儀と落とし穴

プロジェクトrootの mdx-components.tsx は App Router＋@next/mdxでは必須で、h1/a/img/preなどの生成要素や独自部品の共通注入点になる（imgをnext/imageに、aをnext/linkへ差し替えるのが定石）。frontmatterは@next/mdxでは非対応で、代わりにexport const metadataを普通にexportして一覧のメタ抽出に使うか、remark-frontmatter系を足す。シンタックスハイライトはrehype-pretty-code(+Shiki)でビルド時＝サーバー側に寄せると、重いハイライタをクライアントへ送らずに済む。

// next.config.mjs（プラグインはESMで・Turbopackは文字列名指定）
const withMDX = createMDX({
  options: {
    remarkPlugins: ['remark-gfm'],
    rehypePlugins: ['rehype-slug', [rehypePrettyCode, opts]],
  },
})

最大の罠がTurbopack（Next.js 16の既定バンドラ）。remark/rehypeプラグインは関数でなく文字列名で指定する必要があり（'remark-gfm'、オプション付きは['remark-toc', { heading:'...' }]）、関数を渡す＝JSON化できないオプションはまだ使えない（JSをRustに渡せないため）。実務は文字列＋シリアライズ可能オプションに寄せるのが安全だ。

ひとことまとめ

「文章はRSCのまま・動く部分だけ'use client'の島」という原則がMDXでもそのまま効く。ローカル主体なら@next/mdx、CMS連携ならリモート＋use cache/revalidateTagで"静的並みに速い＋編集後すぐ反映"を両立させたい。自分で試すなら、まずpage.mdxを1枚置いてmdx-components.tsxとShikiを通し、Turbopackでプラグインが動くかを最初に確認するのが近道。
