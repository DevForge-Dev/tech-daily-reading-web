<Suspense>ストリーミング設計 — 体感速度は「どこに境界を置くか」で決まる

loading.tsx一枚で満足しない。境界の切り方・動的アクセスの押し下げ・Cache Components相互作用・CLS対策までを総点検する。

📅 2026年10月20日 ⏱ 約3分 🔗 出典 3 件

App Routerの体感速度を決めるのは「遅いデータを待つ間、ユーザーに何を見せるか」だ。Next.jsはReactの <Suspense> を土台にストリーミングSSRを無設定で提供する。静的な殻(シェル=レイアウト・ナビ・フォールバック)を即座に送り、データが解決したセクションから後追いでHTMLを差し込む。差し込みはJSバンドルやハイドレーションを待たないインラインスクリプトで走るため、重いデータが画面全体をブロックしなくなる。

何が重要か — 粒度がすべて

多くの人は loading.tsx を1枚置いて満足するが、それはページ全体を1つの巨大スケルトンに変える最も粗い粒度でしかない。実務の質は「どこに境界を置くか」「動的アクセス(cookies()/headers()/params/searchParams/非キャッシュfetch)をどこまで押し下げるか」で決まる。さらにNext.js 16のCache Components(cacheComponents:true)では、シェルがビルド時プリレンダーされ動的部分だけがストリームされるため、境界設計がそのまま「静的に出せる範囲」を決めてしまう。

定石：動的アクセスは「押し下げる」

layout/page の先頭で動的アクセスを await すると、その配下すべてが動的化しプリレンダーもブロックされる。定石はawaitせずにPromiseを開始し、それを必要とする子に渡すこと。子は use()(Client)や境界内で解く。これで必要な部分だけがサスペンドし、シェルは即出せる。

// awaitしない：Promiseを開始して子へ渡す
const cookieStore = cookies()
return <UserMenu cookiePromise={cookieStore} />
// 子（'use client'）: const cookies = use(cookiePromise)

使いどころ・落とし穴

ダッシュボードはセクション単位で <Suspense> を切り、遅いDB集計だけを後追いにする。LCP要素は境界の外(シェル)へ。遷移時に即フォールバックが欲しいセグメントだけ loading.tsx を置く(こちらはプリフェッチされる)。落とし穴は、親で1つ await を挟むとそこで全体がブロックしストリーミングの利点が消えること。use() に渡すPromiseはレンダー本体で新規生成しない(毎回新Promise=無限サスペンド)。ストリーム開始後はヘッダ送信済みでステータスは常に200——本物の404は最初の await/境界の前に notFound() を呼ぶ。スケルトンは min-height で寸法を予約してCLSを0にし、prefers-reduced-motion ではシマーを止める。

ひとこと：境界は「動的アクセスの近く」に明示的に置く。loading.tsxは万能ではなく、最も粗い既定値だと割り切るのが設計の出発点。
