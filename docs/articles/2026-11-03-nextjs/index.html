Next.js

11/3のNext.js — Multi-Zonesで1ドメインを複数アプリに分割（App Router版）。assetPrefix＋rewrites、ゾーン間は素の<a>、@vercel/microfrontendsでプリフェッチ

巨大化したアプリをビルド時間・チーム独立・段階移行のために「ゾーン」へ割る公式マイクロフロントエンド手法。Next.js 15で不要になった設定と5つの落とし穴を整理する。

📅 2026年11月3日 ⏱ 約3分 🔗 出典 3 件

背景・なぜ今これか。 アプリが巨大化すると全ページ共通でビルド・同梱され、ビルドが遅く、ある画面でしか使わないコードまで全体に乗る。Multi-Zones は1つのドメイン配下を複数の独立したNext.jsアプリ（＝ゾーン）に割る公式のマイクロフロントエンド手法で、/blog/*はブログアプリ、/dashboard/*はダッシュボードアプリ…と「関連の薄いページ群」を別アプリへ切り出す。App Router版ドキュメントが整備され、2026年の実務選択肢として再注目されている。

何が新しい/重要か。 恩恵は3つ——ビルド時間とバンドルの肥大化対策、チーム/デプロイの独立（別リポ・別リリースサイクル）、ゾーンごとに別フレームワークや旧Pages Routerを選べる段階移行の受け皿。重要な更新として、古い記事にある「静的アセット用の追加rewriteが必須」は Next.js 15以降では不要になっている（旧情報のコピペは二重設定の元なので注意）。

仕組み。 各ゾーンは普通のNext.jsアプリで、next.config.js に assetPrefix を設定するだけ。これでJS/CSS等が /<assetPrefix>/_next/... 配下に出て他ゾーンと衝突しない（最もパスをさばく既定アプリ /* は不要）。ドメイン全体を受ける窓口アプリが rewrites で各パスを対応ゾーンの本番ドメインへ転送する。

// main/next.config.js — 窓口アプリ
async rewrites() {
  return [
    { source: '/blog',        destination: process.env.BLOG_DOMAIN + '/blog' },
    { source: '/blog/:path+', destination: process.env.BLOG_DOMAIN + '/blog/:path+' },
  ];
}

ゾーン間リンクはハードナビゲーション。 同一ゾーン内はソフトナビ（<Link>が効く）だが、別ゾーンへの遷移はフルリロードに近いハードナビになる。このため別ゾーンへのリンクは<Link>でなく素の<a>タグを使う（<Link>はプリフェッチ＆ソフト遷移を狙うがゾーンまたぎでは成立しない）。設計指針は「よく一緒に遷移されるページは同じゾーンに置く」。Server Actionsを使うゾーンは各 next.config.js で allowedOrigins にユーザー向けドメインを明示しないとオリジン不一致で弾かれる。

自分が試すなら。 素のMulti-Zonesの弱点は「ゾーン間はプリフェッチできず体感が重い」こと。Vercel公式の @vercel/microfrontends（v0.14系）は microfrontends.json にアプリと担当パスを宣言し、窓口のrewriteを手書きせず解決、さらにゾーン間プリフェッチ対応の強化版 Link を提供する。ただしVercel前提機能を含むため、セルフホスト時は素のMulti-Zonesに戻る判断も要る。

注意点・まとめ。 落とし穴は(1)旧版rewriteの二重設定、(2)ゾーン間での<Link>使用、(3)パス重複によるルーティング競合、(4)Server ActionsのallowedOrigins未設定、(5)共通ヘッダー/フッターの各ゾーン重複実装（共有パッケージ化しないとUIがズレる）。「配信の分割であってRSCやキャッシュ挙動は変えない」と割り切るのが使いこなしの肝だ。
