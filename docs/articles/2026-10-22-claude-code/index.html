v2.1.304/305 — Code Reviewに「深度」、worktreeの事故を塞ぎ、サンドボックスと非対話を締める

3日連続リリースの芯は「レビューの深さを選べる」と「事故る経路を1つずつ潰す」。増やした自動化は規約でなくフックと権限で縛る。

📅 2026年10月22日 ⏱ 約4分 🔗 出典 4 件

Claude Code は10月中旬に小刻みなリリースを重ね、v2.1.303（10/18）→ v2.1.304（10/19）→ v2.1.305（10/20）と3日連続で更新された。中心テーマは「レビュー律速の時代に、レビューの深さを選べるようにする」ことと、worktree・サンドボックス・非対話実行まわりの事故を塞ぐ安全強化だ。並行してAnthropic公式が制御手段の使い分けを整理した「Steering Claude Code」も読み直す価値がある。

何が新しいか

v2.1.304 は76件の変更（新機能8・改善19・修正42・セキュリティ3・破壊的4）を含む大型版。目玉は Code Review の「レビューレベル」で、組織オーナーが Quick / Standard（既定） / Deep を選べ、リポジトリ単位でも設定できる。GitHub組織内の全リポジトリ（将来追加分を含む）を個別選択なしで一括対象にする管理設定も加わった。安全面では rm -r がマウントドライブやトップレベル（/Volumes・/media・WSLの/mnt/c）でも確認プロンプトを出すようになり、claude --worktree 終了時に HEAD detach や別ブランチだと worktree とブランチを無確認削除してコミットを失いうる不具合が修正された。翌日の v2.1.305 は、サンドボックスのLinuxコマンドにユーザー名前空間（user namespace）生成を許可する設定と、非対話（unattended）モードのリトライ設定を追加している。

レビューレベルをどう使い分けるか

Quick は差分の明白な問題だけを素早く拾う軽量モード、Standard は既定のバランス型、Deep は時間をかけて設計・境界・セキュリティまで踏み込む。PRの性質で選ぶのが実務的で——依存更新やリネームのような低リスク差分は Quick、通常の機能追加は Standard、認証・課金・権限など壊れると痛い領域は Deep、という当て方になる。レビューがボトルネックになりやすい今、「全部を厚くレビュー」ではなく深度をリスクに合わせて配分できるのが効く。

「Steering Claude Code」の要点

公式ブログは CLAUDE.md・ルール・スキル・サブエージェント・フック・出力スタイル・システムプロンプト追記の7手段を、読み込みタイミング・コンテキストコスト・強制力で整理した。CLAUDE.md は常駐コストが高いのでビルドコマンドや規約に絞り200行以内に、手続き（デプロイ手順など）は呼び出し時に本体が読まれるスキルへ。サブエージェントは独立コンテキストで要約だけ返すので調査やログ解析の切り離し向き。重要なのは「絶対にするな系のルールはモデルが圧力やプロンプトインジェクションで従わないことがある」という指摘で、本当に止めたい操作はフックや権限に置き、組織全体の強制は managed settings が唯一の手段だとする。

実務での使いどころ

自分なら、まずリポジトリ単位で Deep を「高リスクパスを含むPR」に、Standard を既定に設定して可観測性を上げる。非対話モードのリトライ設定は、CIやスケジュール実行でのツール検索失敗・一時的エラーの取りこぼしを減らせるので、unattended で回しているパイプラインから順に有効化していきたい。事例として、開発者が Claude Code でスマートTVの広告・ブロートを非rootで除去する試み（標準ランチャーを192MB→83MBに削減など）が話題だが、文鎮化例もあり自己責任——「エージェントに端末を触らせる」系はまさに Deep レビューとフック制御の出番だ。

注意点

サンドボックスの user namespace 許可はファイル保護を回避しうるため、必要なコマンドに限定して有効化するのが前提。worktree 修正は過去バージョンでコミット喪失のリスクがあったので、worktree を日常的に使うなら 2.1.304 以降への更新を優先したい。レビューレベルはあくまで「深さの指定」で、Deep でも人間の最終確認を置き換えるものではない。

ひとことまとめ

「レビューの深さを選べる」＋「事故る経路を1つずつ塞ぐ」の合わせ技。増やした自動化の分だけ、強制は規約でなくフックと権限に寄せる——が今週の芯だ。
