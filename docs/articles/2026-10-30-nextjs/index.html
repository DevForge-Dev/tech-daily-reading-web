Next.js App RouterでtRPC v11 — RSCプリフェッチ×TanStack Query v5、そしてServer Actionsとの棲み分け

スキーマもコード生成もなしに型が流れるエンドツーエンド型安全RPC。v11はReact Query v5連携を刷新。『クライアントに渡す』prefetchと『サーバーで使う』createCallerの2つの呼び口を押さえる。

📅 2026年10月30日 ⏱ 約4分 🔗 出典 4 件

なぜ今か。App Router時代は「RSC/Server Actionsがあるのに tRPC は要る？」が繰り返し議論される。tRPC は別途スキーマやOpenAPIを書かず、appRouterの型AppRouterをimportするだけで入力・出力・エラーまで補完が効くエンドツーエンド型安全RPCだ。v11は2025-03-21に正式リリースされ、v10とほぼ後方互換。目玉はTanStack React Query v5連携の刷新、RSCプリフェッチ＋ハイドレーション、FormData/Blob等の非JSONボディ、SSEベースのSubscription(httpSubscriptionLink、WebSocketより推奨)あたりだ。

何が新しい/重要か。連携が2系統になった。旧来のcreateTRPCReactに加え、新しい@trpc/tanstack-react-query(createTRPCOptionsProxy/createTRPCContext)は「tRPCがReact QueryのqueryOptionsを生成し、useQuery/useSuspenseQuery/useMutationは素のTanStack Queryフックを使う」設計で、React Queryの全機能が素直に乗る。新規は新方式が推奨。TanStack Queryはv5必須だ。

仕組みと落とし穴。RSC対応の呼び口は図1の2つ。Aはtrpc.x.queryOptions()をサーバーでprefetchQueryし、HydrationBoundaryでクライアントのReact Queryキャッシュへ渡す。BはappRouter.createCaller(ctx)でサーバーが直接await caller.hello(...)と関数呼び出しする——結果はキャッシュに入らないので「サーバーが値そのものを使う」ケース向けだ。落とし穴は多い:(1)prefetchQueryをawaitしない(void)とストリーミング、ただしshouldDehydrateQueryにpendingを含める設定が必須。(2)staleTime: 0だとハイドレーション直後に即再フェッチするので30秒などへ。(3)QueryClientはサーバーは毎リクエスト新規・ブラウザは単一再利用(cache(makeQueryClient)で固定)。(4)superjson等のtransformerを入れるならサーバー・HTTPリンク・dehydrate/hydrateの3箇所すべてに設定。(5)trpc/server.tsxにはimport 'server-only'を付けて漏洩防止。

// app/page.tsx (Server Component)
const qc = getQueryClient();
void qc.prefetchQuery(trpc.hello.queryOptions({ text: 'world' })); // awaitしない=ストリーミング
return <HydrateClient><ClientGreeting /></HydrateClient>;

Server Actionsとの棲み分け(2026時点)。フォーム送信・単発のサーバー副作用・プログレッシブエンハンスメントはServer Actionsで十分。クライアント主導の取得/キャッシュ/楽観更新/無限スクロール/ポーリング/SSE購読、複数クライアント(Web＋モバイル)から叩く型付きAPIが欲しいときはtRPC＋React Queryが光る。両者は排他でなく、RSCで初回データ・以降は tRPC/React Query という併用が現実的だ。自分が試すなら、まずhelloprocedure一本を新方式で通し、staleTimeとtransformerの3点設定でハイドレーション破綻が起きないかを確認してから本採用する。
