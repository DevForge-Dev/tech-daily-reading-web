middleware.ts は proxy.ts へ — Next.js 16「リクエスト前処理の表玄関」を正しく使う

単なる改名ではない。runtime 既定が Edge→Node.js に変わり runtime 指定は throw、公式は Proxy を「最後の手段」と明文化した。

📅 2026年9月7日 ⏱ 約3分 🔗 出典 3 件

Next.js 16 の目玉のひとつが、長年おなじみの middleware.ts → proxy.ts というファイル規約のリネーム。だが本質は名前ではない。middleware.ts は deprecated（削除ではなく非推奨）となり、公式は Proxy を「最後の手段（last resort）」と設計スタンスを明文化した。Express の middleware と混同され濫用されてきた歴史への軌道修正だ。

何が変わったか（最重要は runtime）

v16.0.0 で Proxy は Node.js runtime が既定（旧 Middleware は Edge 既定）。しかも export const runtime = 'edge' のような runtime 指定を書くと throw する＝実行環境は固定で選べない。「Edge だから Node API が使えない」を前提に組んでいたロジックは Node.js 前提へ置き換え可能になる一方、Edge の地理分散を当て込んだレイテンシ設計は前提が崩れる。

matcher とセキュリティの落とし穴

config.matcher が無いと _next/static や public/ 資産まで全リクエストで発火する。否定ルックアヘッドで除外が定石だ。

export const config = {
  matcher: ['/((?!api|_next/static|_next/image|favicon.ico).*)'],
}

ただし _next/data/* は除外指定しても走り続ける（データルート保護漏れを防ぐ意図的仕様）。さらに Server Function は使用先ルートへの POST 扱いなので、matcher 除外で Proxy を素通りしうる。公式は「認証・認可は各 Server Function 内と DAL（Data Access Layer）で必ず検証し、Proxy だけに頼るな」と明言する。Proxy は粗いゲート、認可の真実の源は DAL。

移行手順

npx @next/codemod@canary middleware-to-proxy . でファイル名・関数名を自動置換。skipMiddlewareUrlNormalize→skipProxyUrlNormalize にリネーム、runtime 指定は削除する。認可を Proxy 依存にしていたら DAL / Server Function 内検証へ移す。

ひとこと：「アプリ前段のネットワーク境界」という名前どおりの役割に絞れば健全。早期リダイレクト・CORS プリフライト・ロケール振り分けだけを Proxy に残そう。
