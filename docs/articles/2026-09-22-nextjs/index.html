Container Queries（@container）で“ビューポート非依存”の真にレスポンシブなコンポーネント — App Router × Tailwind v4

同じカード部品を広いメインにも狭いサイドバーにも置ける。@mediaのビューポート依存を捨て、親コンテナ幅でレイアウトが自律的に組み変わる。’use client’不要でRSCのまま動く。

📅 2026年9月22日 ⏱ 約3分 🔗 出典 4 件

レスポンシブ設計の主役だった @media は、常にビューポート幅を見る。しかしコンポーネント指向（RSC / shadcn / デザインシステム）では、同じカード部品が「広いメイン領域」にも「狭いサイドバー」にも置かれる。ビューポートが同じでも、置かれた親コンテナの幅は違う——ここで @media は破綻し、isSidebar のような prop のバケツリレーやページ別の上書き CSS が増えていく。

何が新しいか — 親コンテナ幅で組み変わる

Container Queries は「自分を囲む親の幅」でスタイルを切り替える。これでコンポーネントは「どこに置かれても自分の幅に応じて正しく組み変わる」＝真の意味で再利用可能になる。2023 年に主要ブラウザへ載り、2026 年現在は Baseline widely available（クエリ長単位 cqw/cqi 等も含む）。ポリフィル不要で本番投入できる。Next.js と相性が良いのは、純粋に CSS だけで完結し 'use client' が一切不要な点だ（＝Server Component のまま動く）。

仕組みと最大の落とし穴（2層構造が必須）

親を container-type: inline-size で「クエリコンテナ」に指定し、子孫側で @container (min-width: 420px){…} と書くと、最も近い祖先コンテナの幅で分岐する。名前付きは container-name、長さ単位は cqi（コンテナ幅の 1%）で font-size: clamp(1rem, 4cqi, 1.75rem) のように親幅比例のタイポも作れる。最大の落とし穴は「コンテナは自分自身をクエリできない」こと。@container が当たるのは子孫なので、部品には必ず「外側ラッパ（＝コンテナ）＋中身」の 2 層が要る。

Next.js（App Router）での組み込み・Tailwind v4

CSS Modules でもグローバル CSS でも 'use client' 不要で RSC のまま使える。Tailwind は v3 では @tailwindcss/container-queries プラグインが要ったが、v4 ではコア内蔵。コンテナに @container/card、子孫に @md:grid-cols-[160px_1fr] のように付けると、「この部品を囲む @container の幅」基準で効く（ビューポート基準の md: とは別物）。SSR/RSC キャッシュとは無関係で、JS 計測も window サイズ依存もないため、FOUC やレイアウトシフトが @media 版より起きにくいのも利点だ。

注意点

container-type: size（縦横両方）は高さ包含が効いて中身から高さが決まらず 0 に潰れやすい。特別な理由がなければ inline-size を使う。containment は新しい包含ブロック/スタッキング文脈を作るため、position: sticky や z-index の基準が変わることがあり、組み込み後の実挙動確認が要る。列数変化の transition は効かないので、切替の演出は透明度/transform 側に寄せ、prefers-reduced-motion で無効化する。

ひとことまとめ

「ページが部品を配置する」から「部品が置き場所に合わせて自分で組み変わる」へ。2 層構造さえ守れば、prop バケツリレーを一掃できる、CSS だけの強力な武器だ。
