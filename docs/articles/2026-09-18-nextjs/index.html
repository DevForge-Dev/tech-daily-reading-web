Draft Modeで安全なヘッドレスCMSプレビュー — キャッシュ全透過とuse cache／SameSiteの罠

draftMode()は特定リクエストだけNext.jsの全キャッシュ層を透過させ、常に最新の下書きを上流から取り直す仕組み。15でasync化、16では必ずawait。isEnabledはuse cache内でも読める。root layoutで読むと全体が動的化、SameSite=Laxでiframeが壁、Edgeでenable()が落ちる等の罠に注意。

📅 2026年9月18日 ⏱ 約3分 🔗 出典 3 件

ヘッドレス CMS 運用で必ず出るのが「編集者が未公開の下書きを本番と同じレンダリングで確認したい」という要件だ。だが App Router は既定でキャッシュ/静的化/ISR が効くため、素直に fetch すると編集者にもキャッシュ済みの公開版が見えてしまう。Draft Mode（next/headers の draftMode()）はこの一点だけを解く——特定リクエストに限り Next.js の全キャッシュ層を透過させ、常に最新の下書きを上流から取り直す。Pages Router の旧 Preview Mode の後継で、App Router では draftMode() に一本化された。

API と挙動（16 の肝）

Next.js 15 で同期→async 化され、16 では必ず await draftMode()。返り値は isEnabled（今 Draft か・Server Component や use cache 内でも読める）／enable()・disable()（Route Handler か Server Action 専用、__prerender_bypass Cookie を出し入れ）。Cookie が載ると fetch() は fetch キャッシュを飛ばしネットワーク直行、'use cache' 配下は毎リクエスト再実行され結果を保存しない。ページ側は「今 Draft か」を知らなくてよいのが要点だ。

実装の型

契約は「Studio の Preview→/api/draft?secret=XXX&slug=/posts/foo を新規タブ(GET)で開く」。Next 側は secret 検証→slug 実在確認→enable()→検証済み slug へ redirect。GET なのは CMS がタブで開く操作が GET だから。離脱は POST（Server Action）が正解で、Link は既定 prefetch でクリック前に Cookie を勝手に触る事故になるため使わない（どうしてもなら prefetch={false}、フォームは prefetch されず安全）。

落とし穴・まとめ

実運用の罠は多層だ。root layout で draftMode() を読むとアプリ全体が動的化するので、バナーは末端の Suspense 島に隔離する。__prerender_bypass は既定 SameSite=Lax で CMS の iframe（クロスサイト）に送られず、Contentful/Sanity/DatoCMS の公式パッケージは Set-Cookie を SameSite=None; Secure へ書き換えて回避している（実装依存で将来壊れうる）。ほかに Edge Runtime で enable() が落ちる（Node.js runtime に置く）、open redirect（検証済み slug へ飛ばす）、secret は定数時間比較、Draft 中は noindex。まとめると Draft Mode は「公開前にキャッシュを一時的に無視する」ピースで、revalidateTag（公開後にキャッシュを捨てる）の対に当たる。
