macOS風ドック・マグニフィケーション — 距離→サイズ写像という一つの発想と、widthかtransformかの判断

カーソルに近いアイコンほど膨らむDock挙動。主要UIライブラリが共有する中核アルゴリズムを分解し、Motion実装・reflow回避・App Router組み込みまで通して読む。

📅 2026年10月19日 ⏱ 約3分 🔗 出典 3 件

macOS Dockの「カーソルに近いアイコンほど大きく、離れると小さく、連続的に膨らむ」あの挙動。ポートフォリオ・ランチャー・ツールバーで繰り返し求められる定番で、Magic UI / cult-ui / Aceternity の dock 系コンポーネントは軒並みたった一つの発想を共有している——ポインタのX座標と各アイコン中心の距離を、サイズへ写像する。見た目のインパクトのわりに原理は素朴で、仕組みを理解するのにうってつけの題材だ。

中核アルゴリズム（ライブラリ非依存）

① ドックで pointermove を購読しカーソルの clientX を保持。ドック外（pointerleave）では「無限遠」= 全アイコンが基準サイズに戻る状態にする。② 各アイコンの中心X cx = rect.left + rect.width/2 とカーソルの差 d を取る。③ |d| を影響半径（例140〜150px）で正規化し、基準サイズ→最大サイズへ補間。半径外なら基準サイズ。④ 目標サイズへバネ/慣性で寄せると、あの"ぷるん"とした質感が出る。

Motion（旧Framer Motion）版の定石

パッケージは motion に、Reactインポートは motion/react に改称された（旧 framer-motion も当面動くが新規は motion 推奨）。ドックで mouseX = useMotionValue(Infinity) を持ち、各アイコンで useTransform により距離を導出、useTransform(distance,[-150,0,150],[48,100,48]) で幅へ写像し、useSpring(..., {mass:0.1,stiffness:150,damping:12}) に通して幅へ渡す。getBoundingClientRect を useTransform 内で毎回読むのが肝で、レイアウト変化に追従する（Magic UIの既定は iconSize=40 / magnification=60 / distance=140）。

落とし穴 — widthかtransformか

最大の判断は幅アニメ＝レイアウト誘発（reflow）という点。本物のDockは幅を変えて隣を押し出すので width を動かすが、これはレイアウト→ペイントを走らせる。対して transform: scale は合成だけで安価だが隣を押さず重なり、テキストもボケる。「隣接を押す演出が要るか」で選ぶのが要点だ。さらに：CSS transition 単体は pointermove ごとに再始動してカクつくので rAF か useSpring が要る／タッチでは matchMedia('(hover:hover) and (pointer:fine)') で無効化／prefers-reduced-motion で拡大停止／SSRは初期 Infinity（＝基準サイズ）にしてハイドレーション不整合を避ける。

App Routerでの組み込み・ひとこと

イベント・useRef・useMotionValue を使うのでドックは必ず 'use client' の島に切り出し、ページ本体はRSCのまま保つ。ナビ用途なら各アイコンを next/link（prefetch）にし、現在ルートは usePathname() で判定。拡大は純粋に装飾——reduced-motionやタッチで切ってもランチャー/ナビとしての機能は一切損なわれない設計が理想だ。自分で試すならまずVanilla+rAFで距離→サイズの写像を体で理解してから、Motionに載せ替えると腹落ちが早い。
