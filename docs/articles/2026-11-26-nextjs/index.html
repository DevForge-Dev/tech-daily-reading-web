マルチステップ・フォーム／ウィザード — 本質は演出でなく「状態をどこに持つか」（App Router）

1画面1トピックに割るウィザード。スライド遷移より先に決めるべきは状態の持ち方。4つの保持戦略と、退場アニメ・ハイドレーションの罠。

📅 2026年11月26日 ⏱ 約3分 🔗 出典 3 件

サインアップ・オンボーディング・決済・アンケート——長いフォームを1画面に詰め込むと離脱が増える。だから「1画面1トピック」に割り、上部のステッパーと戻る/次へで進ませるのが定番（GOV.UK の one thing per page と同じ思想）。だが Next.js（App Router）でこれを作るときの本質は、スライド遷移という演出ではなく「状態をどこに持つか」だ。素朴に作ると「リロードで全消え」「戻るが効かない」「ハイドレーション不一致」「退場アニメが出ない」を順に踏む。

状態の持ち方 4択（最重要）

① クライアント状態のみ（useReducer）＝最短だがリロードで消える。短いフロー向き。② 現在ステップをURLに（?step=2）＝ブラウザの戻る/進む・共有・リロード耐性が効く。ただしフィールド値はURLに置かない（機微・履歴汚染）。③ 値を永続化＝sessionStorage／Cookie／サーバー下書き。決済・個人情報はサーバー下書きが安全。④ プログレッシブ・エンハンスメント＝各ステップを独立 <form action={serverAction}> にして POST→redirect。JS なしでも動く。実務の落としどころは「位置＝URL or client state／値＝sessionStorage or サーバー下書き」の組み合わせだ。

遷移アニメと退場の罠

方向（次へ=+1／戻る=−1）を状態に持ち、key を差し替えて入場アニメを走らせるのが素直だ。問題は退場——React は旧ステップを即アンマウントするので CSS だけでは「出て行く絵」を描けない。対策は (a) 退場中に一時クラスを当て animationend 後にアンマウント、(b) View Transitions API（document.startViewTransition が前後を自動キャプチャ）、(c) Motion の AnimatePresence。バリデーションは Zod の safeParse をクライアント即時＋サーバー再検証の二段で、送信は useActionState の pending でボタンを無効化する。

落とし穴と reduced-motion

ハイドレーション不一致を避けるため、初期ステップは page.tsx の searchParams をサーバーで読んで渡す（sessionStorage は useEffect 内で読む）。ステップごとの高さ差は min-height で CLS を抑える。切替でフォーカスが body に落ちたら次ステップの見出しへ移す。演出は @media (prefers-reduced-motion: no-preference) の中だけに置き、既定は瞬時切替＝非対応環境でも安全にする。進捗は色＋aria-current＋状態テキストで伝わるので、アニメを切っても機能は無損だ。

ひとことまとめ

ウィザードは「位置」と「値」を分けて持つ設計が8割。演出は View Transitions で退場まで含めて最後に乗せる。
