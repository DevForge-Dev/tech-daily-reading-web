アニメは implicit/explicit を用途で分け、フレーム予算（16/11/8.3ms）を超えない — Impeller 既定時代の設計

Impeller が iOS＋Android(API29+) 既定で Skia を撤去し shader jank を排除、120fps がベースライン。上物は implicit（150〜500ms/標準カーブ）を基本に、physics・gesture・割り込みだけ explicit へ。性能は不要な rebuild を const/Selector/RepaintBoundary で削り、profile モードの DevTools で UI/Raster スレッドとフレーム予算を実測するのが王道。

📅 2026年8月10日 ⏱ 約3分 🔗 出典 3 件

今日はアニメーションとパフォーマンスの「予算」に絞って整理する。描画基盤の Impeller が iOS＋Android(API 29+) で既定になり Skia を撤去、ビルド時 AOT シェーダーで shader compilation jank を排除して 120fps をベースラインに置いた。土台が速くなったぶん、上物のアニメ設計とリビルド削減の効き目がそのまま体感差になる局面だ。

アニメは implicit / explicit を用途で分ける

UI アニメの多くは implicit（AnimatedContainer／AnimatedOpacity／AnimatedSwitcher）で1行、割り込みも自動処理。時間は 150〜500ms・標準カーブ（easeInOut／fastOutSlowIn）。複雑な choreography・physics・gesture 駆動だけ explicit（AnimationController＋Tween＋CurvedAnimation＋AnimatedBuilder）に落とし、AnimationController は dispose 必須。時間設計の目安は micro 50〜200ms＝implicit／component 200〜400ms＝explicit／Hero 300〜600ms。宣言的連鎖なら flutter_animate（.animate().fadeIn().slide().scale()＋.then() でスタッガー）、状態機械でロジックを描画から分離したいなら Rive（events で haptics/sound/navigation を発火）。

パフォーマンスはフレーム予算で考える

最も多い性能問題は不要な widget rebuild。Flutter は const widget の再ビルドを完全スキップするので const を積極活用し、大きな build() を分割、Selector／select で局所再描画、アニメ領域は RepaintBoundary で隔離する。計測は必ず profile モードで DevTools の Performance Viewを使い、UI スレッド／Raster スレッドの処理と jank フレーム位置を見る。

実務での使いどころ・注意点

自分が新規で作るなら、まず const 徹底と RepaintBoundary でアニメ領域を隔離し、実測は必ず profile モードで DevTools を回す（debug モードの数値は当てにならない）。画像は width/height を明示し cached_network_image を使う。Material 3 Expressive は spring モーション物理・35 シェイプ・shape morphing を持ち、useMaterial3 既定で dynamic color と adaptive layout が効く。落とし穴は、explicit を使いすぎて controller の dispose 漏れやリビルド過多を招くこと——「動きの複雑さ」ではなく「割り込み・物理・ジェスチャの有無」で implicit/explicit を選ぶと事故りにくい。

ひとことまとめ：Impeller で土台は速い。あとは用途で implicit/explicit を分け、フレーム予算（16/11/8.3ms）を超えないようリビルドを削るのが王道。
