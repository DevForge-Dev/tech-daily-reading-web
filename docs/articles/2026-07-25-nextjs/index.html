CSS sibling-index() / sibling-count() — JSもinline styleも無しで「ずらし出現」スタッガーを純CSS化

リストを0.1sずつ遅らせて順に出す定番のスタッガー演出。これまでは nth-child の手列挙・inline styleで --i を流し込む・JS のどれかが必要だった。sibling-index() は「兄弟の中で何番目か」を整数で返す新しいCSS値関数で、animation-delay: calc((sibling-index()-1)*.06s) と書くだけ。RSCのままインラインstyleゼロ・use client不要でスタッガーが完成する。

📅 2026年7月25日 ⏱ 約3分 🔗 出典 3 件

背景から。「リストの子要素を少しずつ遅らせて順番に出す（stagger）」は定番のUI演出だが、実装はどれも面倒だった。:nth-child(1){delay:0} :nth-child(2){...} の手列挙は項目数が可変だと破綻し、style="--i:3" を各要素にinline styleで埋める方式は index を props/ループから流し込む必要があり、JS（Motion の stagger や element.animate()）はクライアント処理が増える。

何が新しいか

sibling-index() は要素が兄弟の中で何番目か（1始まりの整数）、sibling-count() は兄弟要素の総数を返す新しいCSS値関数。counter() と違い文字列でなく整数を返すので calc() の中でそのまま演算でき、animation-delay: calc((sibling-index() - 1) * .06s) と書くだけで、マークアップに index を一切書かずに位置依存スタッガーが完成する。Server Component でサーバ側に map したリストが、inline styleゼロ・use client不要・hydrationコストゼロでずれて出現する——これが Next.js 文脈での一番のうまみ。さらに (sibling-index()-1)/max(sibling-count()-1,1)*total と正規化すれば、項目が3個でも30個でも総演出時間を一定に保てる。

実装（App Router / Server Componentのまま）

純CSSなので 'use client' 不要。サーバで data.map() した各 <li> が位置情報を props で受け取らずにCSSだけで自動スタッガーする。動き系は必ず @media (prefers-reduced-motion: no-preference) の内側へ、初期の opacity:0 もそのブロックに閉じ込める。

@supports (animation-delay: calc(sibling-index()*1s)) {
  .item { opacity:0; animation:fadeUp .4s ease both;
          animation-delay: calc((sibling-index() - 1) * .06s); }
}

注意点・ひとことまとめ

落とし穴は3つ。①セレクタでは使えない（値関数であって :nth-child(sibling-index()) は不可）。②数えるのは「同じ親の全要素」なので見出しや区切り線が混ざると番号がずれる→アニメ対象は専用の親でラップ。③Firefox など未対応で opacity:0 のまま消えるリスク→ @supports で機能検出し、サポート外は最初から表示。index を流し込める場面では style={{'--i':i}}＋calc(var(--i)*.06s) の全対応版が堅く、真価は「index を渡せない/渡したくない純CSS」の場面。まとめると「indexを書かないスタッガーの決定版、ただし当面フォールバック前提」。
