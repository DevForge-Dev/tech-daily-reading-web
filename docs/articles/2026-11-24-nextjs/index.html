App Router のリアルタイム通信 — 「Next.js 自身は WebSocket サーバーにならない」を出発点に、接続をどこへ逃がすかの4+1パターン

チャット・プレゼンス・ライブダッシュボードの要件は増える一方、App Router の主戦場サーバーレスは永続 WS を保持できない。マネージド／別建て WS／Vercel Fluid WS(beta)／SSE・ポーリングをどう使い分けるか。

📅 2026年11月24日 ⏱ 約5分 🔗 出典 5 件

「サーバー発の更新をブラウザへ押し出す」要件——チャット、通知バッジ、プレゼンス（オンライン／入力中）、ライブダッシュボード、共同編集、進捗バー——は今やほぼ全アプリに現れる。ところが App Router の主戦場であるサーバーレス関数は「リクエストで起動→応答で即終了」で、永続的な WebSocket 接続を保持できない。接続は分単位で切られ、インメモリのルーム状態はスケールを跨いで共有されない。だから app/api/ws/route.ts に ws を生やす実装はローカルでは動くが Vercel では壊れる。2026 の定石は、「Next.js 自身は WS サーバーにならない」を出発点に、接続の“保持”をどこへ逃がすかを設計で決めることだ。

① マネージド実時間サービス（サーバーレスの既定解）。ブラウザはサービスのエッジへ直接 WSS 接続し、Next.js（Server Action / Route Handler）はそのサービスへ HTTP でイベントを publish するだけ。接続の保持・スケール・fan-out・プレゼンスは全部サービス側が持つので、Next.js はサーバーレスのまま Vercel で無改造デプロイできる。代表格は Pusher Channels、Ably（履歴・プレゼンスが手厚く Vercel 公式も例示）、Supabase Realtime（Broadcast／Presence／Postgres Changes の3機能）、Upstash Realtime、Cloudflare が買収した PartyKit（Durable Objects ベースの“部屋ごと常駐”＝共同編集向け）。

② 別建ての自前 WS サーバー。ws や Socket.IO を Next.js とは別プロセス（Fly.io / Railway / Render / 自前VM）で常駐させ、状態は Redis/DB で共有する。Socket.IO は再接続・ルーム・HTTPロングポーリング fallback が内蔵で、水平スケール時は @socket.io/redis-adapter を入れないとノード跨ぎでブロードキャストが届かない。低レイテンシや独自プロトコルを握りたい・接続数が読める場合に向くが、常駐・スケール・監視の運用責任を負う。

③ Vercel Functions の WebSocket（Fluid Compute・public beta）★新着。Route Handler で @vercel/functions の experimental_upgradeWebSocket() を使う。ただし制約が効く——Function の実行時間に縛られる（既定5分、Pro/Enterprise は800秒〜拡張betaで30分）ので長時間接続は定期再接続前提、新規接続が同一インスタンスに来る保証がないのでルーム／プレゼンス状態は外部（Redis/DB/マネージド）に持つ必要があり、提供は HTTP/2（HTTP/3 不可）。「別プロセスを建てずに Vercel 内で完結させたい」軽量用途の新手段で、重い実時間は結局 ①/② に寄る。

④ SSE / ポーリング（双方向が不要なら最小解）。通知・進捗・株価・LLM トークンのようなサーバー→クライアント一方向なら、Route Handler の ReadableStream による SSE で十分——WS インフラ不要・HTTP・EventSource の自動再接続つき。送信はふつうの fetch/Server Action で足りることが多い。さらに単純なら SWR の refreshInterval や TanStack Query の refetchInterval でポーリング。まずここから検討し、双方向・低遅延・高頻度が要るときだけ WS へ上げる。

クライアント側の鉄則も押さえたい。WebSocket はブラウザ API なので必ず 'use client'＋useEffect 内で生成（トップレベルで new WebSocket() すると SSR 時に window 不在でクラッシュ）、クリーンアップで close()。接続はルート遷移で生かすためルートレイアウトの Provider でシングルトン化し、再接続は onclose で指数バックオフ＋ジッタ。認証は Route Handler で exp 数十秒の短命 JWT を発行し wss://...?token=... で渡す（長命トークンを URL に載せない）。+α として、セルフホスト時のみ createServer にカスタムサーバーで WS を同居させる手もあるが、standalone output と併用不可・Vercel 非対応という代償がある。

自分が試すなら：まず要件が本当に双方向かを疑い、通知・進捗なら SSE で済ませる。双方向が要るなら Vercel 運用なので ① を既定にし、Supabase 採用済みなら Realtime、共同編集なら PartyKit を候補に。ひとことまとめ：WS の設計は「どのサービスを使うか」ではなく「接続の保持をサーバーレスの外のどこに置くか」の判断から始める。
