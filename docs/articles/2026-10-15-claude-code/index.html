Claude Code v2.1.299/300 — “アイドル圧縮”と可観測性強化、そしてAnthropic自作のソース管理Scion

長時間セッションのコスト最適化に効くアイドル圧縮と、OTel/gzip/MCP修正。背景はキャッシュ退避問題としての3層コンテキスト管理。

📅 2026年10月15日 ⏱ 約4分 🔗 出典 6 件

10/9のv2.1.296以降途切れていた公式更新が10/14に再開し、同日にv2.1.299とv2.1.300が相次いで公開された。長時間セッションを常用する身としては、今回の目玉「アイドル圧縮」はそのまま日々の体感に効く変更なので整理しておく。

何が新しいか

v2.1.299の中心はアイドル圧縮(idle compaction)。ターミナルで200Kトークン超の会話が約54分アイドルになると、1時間のプロンプトキャッシュが失効する前に先回りでコンパクトし、次のメッセージで会話全体を再処理せずに済ませる。閾値はCLAUDE_CODE_IDLE_COMPACT_MIN_TOKENSで調整、idleCompaction:falseで無効化(いずれもv2.1.290以降)。あわせて--debug時のメモリ肥大や多数サブエージェント実行後の高メモリ、@メンションしたPDFの生バイト保持を修正し、/usageに最大エフォートや巨大ツール結果の警告を追加した。翌番のv2.1.300は可観測性で、OTelのapi_requestにcache_creation_5m_tokens/cache_creation_1h_tokensを足してキャッシュ書込を存続期間別に計測。大型リクエストはテレメトリ無効時もgzip圧縮し、MCPツールの入力スキーマ拒否で毎ターン400失敗していた不具合を「パラメータなし送信」でフォールバックするよう直した。

仕組み — なぜ“アイドル”で圧縮するのか

第三者の解説記事『無限セッションを支えるコンテキスト管理』が背景の理解に効く。Claude Codeは文脈管理を「保存の問題ではなくキャッシュ退避の問題」として3層で扱う。第1層マイクロ圧縮は古いツール結果(ファイル読取・シェル・grep)を短いプレースホルダに置換し、件数超過時と約1時間アイドル時に発火する——この時間ベースの圧縮が、今回正式化された“アイドル圧縮”の原型だ。約1時間でプロンプトキャッシュが失効するなら退避コストはどうせゼロ。ならキャッシュが切れる直前に畳んでおけば、再開時に全履歴を再処理せずに済む、という発想になる。

事例 — Anthropicが社内Gitを自作Scionへ

ニュース面ではAnthropicが社内モノレポのGitを自作のサーバ中心型ソース管理Scionへ置換した件(10/13ブログ)。AI生成コードの激増で日次マージが5月の約2,500件から9月には3万件超、履歴約100GB・CIのソース取得が日2,500万回に達し、フルクローン前提が破綻したのが背景。7人が5か月でScionとレビュー基盤Antiqueを構築し、Claudeをシミュレーションや競合解消に多用した(設計とレビューは人間)。これを受けた論考は「Gitは消えないがGitクライアント・モデルが中心性を失う——価値はサーバ側へ、主クライアントは常時接続のAIエージェントになる」と主張し、CursorのフォージOriginと対比する。

自分が試すなら / 注意点

長いセッションを張りっぱなしにする運用なら、アイドル圧縮は基本オンのまま恩恵を受けられる。逆に「アイドル後に文脈が畳まれて困る」ケース(直前の細部に依存した作業)ではidleCompaction:falseを検討。可観測性を回しているならOTelの新メトリクスで5分/1時間キャッシュの比率を見ておくと、キャッシュ戦略のムダが見える。Scionの話はOSS化されない社内ツールなので直接は使えないが、「マージ/レビュー層が主戦場」という規模別指針(小=ホスト型Git、中=サーバAPI/sparse checkout、超大規模=内製)は自分のCI設計の目安になる。

ひとことまとめ

v2.1.299/300は「長時間・大規模セッションのコスト最適化」に寄った実務アップデート。アイドル圧縮はキャッシュ経済の理解があると腑に落ちる。
