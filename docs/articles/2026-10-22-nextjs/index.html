App Router を Cloudflare Workers に載せる — OpenNext アダプタ @opennextjs/cloudflare の設計と落とし穴

コードは据え置き、勝負は wrangler と open-next.config。R2増分キャッシュ＋DOキュー＋D1タグキャッシュで ISR/ストリーミングまで Workers で回す。

📅 2026年10月22日 ⏱ 約4分 🔗 出典 4 件

Vercel 以外で Next.js の App Router（RSC・Server Actions・ISR・ストリーミング）を「フルに」動かす本命が OpenNext の Cloudflare アダプタ @opennextjs/cloudflare だ。Cloudflare 公式が「Next on Pages ではなく、これが Next を Cloudflare に載せる推奨方法」と明言しており、旧 @cloudflare/next-on-pages（Pages＋Edge限定）からの移行が進む。狙いは Workers のグローバル実行、R2/KV/D1/Durable Objects のバインディング、従量課金——つまり Vercel ロックインを避けたいプロダクトでの採用だ。Next.js 16 世代でも 1.x 系アダプタで実用段階にある。

仕組み

opennextjs-cloudflare build が next build を呼んだ後、OpenNext の中間表現を Workers 用の単一 Worker（.open-next/worker.js）＋静的アセット（.open-next/assets）に変換する。リクエストは Worker 上で Next のサーバを起動して処理し、静的アセットは Workers Static Assets（ASSETS バインディング）が配信する。

何が要るか（キャッシュが肝）

対応ランタイムは Node ランタイムのみ。export const runtime = "edge" は未対応なので全ソースから削除する。nodejs_compat 互換フラグ必須、compatibility_date は 2024-09-23 以降。そして ISR/SSG/データキャッシュは自前で有効化が必要だ——既定では永続化されないため R2 を増分キャッシュに割り当て、時間ベース再検証には Durable Objects のキュー、タグ再検証には D1（または Sharded DO）のタグキャッシュを足す。next/image の動的最適化は Workers に sharp が無いため既定では動かず、Cloudflare Images 連携（images バインディング）で代替する。

組み込み手順

新規は npm create cloudflare@latest -- my-app --framework=next --platform=workers、既存は npx @opennextjs/cloudflare migrate（R2 有効ならキャッシュ用バケットも自動作成）。next.config.ts 末尾で initOpenNextCloudflareForDev() を呼ぶと next dev でもバインディングが使える。検証は npm run preview（Workers ランタイム）、本番は npm run deploy。RSC/Server Actions のコード自体はそのままでよく、対応は主に設定とビルドパイプラインの話だ。

落とし穴

ミドルウェア（Next.js 16 では proxy.ts）は Edge ランタイム相当で動くため、crypto など Workers サブセット外の API を import するとビルド時でなくリクエスト時に失敗する。env は process.env に出ないことがあり、サーバ側では getCloudflareContext() から env（バインディング）を取る（NEXT_PUBLIC_ はビルド時に焼き込み）。初回デプロイ直後のコールドスタートが大きい実測報告（約30ルートで初回45〜60秒、以降は改善）もある。OpenNext のマイナー更新で wrangler 設定の追従が要る点と、.open-next の gitignore も忘れずに。

ひとことまとめ

コードは据え置き、勝負は wrangler.jsonc と open-next.config.ts の設定。R2 増分キャッシュ＋DOキュー＋D1タグキャッシュを正しく組めば、App Router の ISR・タグ再検証・ストリーミングまで Workers で回る。Vercel 依存を外す現実解として押さえておきたい。
