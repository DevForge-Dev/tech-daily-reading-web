useOptimistic で楽観的UI — 送信前に先出し、成功で収束・失敗で自動ロールバック

対話UIの5プリミティブの中核。親stateの更新を忘れなければコードは驚くほど短い。

📅 2026年10月8日 ⏱ 約3分 🔗 出典 4 件

ミューテーション（いいね／優先度切替／コメント投稿／カード移動）は、サーバー往復が終わるまで画面が変わらない。素朴に await serverAction() を待つと、クリックしたのに何も起きない空白時間が生まれ、体感（INP）が悪化する。これを埋めるのが React 19 の useOptimistic だ。Next.js公式が2026年に出した「Building interactive apps（Taskboard）」ガイドは、<Suspense>／useOptimistic／useTransition／useActionState／data-pending の5プリミティブの組み合わせとして対話UIを体系化した。本稿はその中核を深掘りする。

何が新しく、何が効くのか。const [opt, addOpt] = useOptimistic(state, updateFn?)。state は「本物の値」（通常はServer Componentから届くprops）、updateFn は現在状態と楽観値から次の楽観状態を返す純関数。返る opt はActionが進行中の間だけ楽観値になり、終わると state に戻る。核心は「楽観を消すための追加レンダーが無い」こと——本物と楽観が同じレンダーで収束するのでチラつかない。

収束とロールバックの要点。成功時は、Server Action が refresh()（動的読み取りの再実行）か updateTag()（キャッシュのタグ無効化）を呼んでRSCを再レンダーし、新propsが state に届くことで確定する。親が state を更新しないと楽観値はAction終了で消える——これが「一瞬出て元に戻る」最頻出バグの正体だ。失敗時は Action が throw すると現在の state（＝変わっていない元値）で再描画され、自前のロールバックを書かずに元へ戻る。保留中に state が変化すれば、新しい state を土台に updateFn が再実行される（リベース）。

最重要の制約。addOptimistic は必ずAction（startTransitionに渡す関数 or action/formAction prop）の中で呼ぶ。外で呼ぶと「outside a Transition」警告が出て一瞬描画してすぐ戻る。レンダー中にsetterを呼ばない。保留項目のkeyは crypto.randomUUID() の安定IDにし、本物が届いた時のkey衝突を避ける。className等はpropsの古い値ではなく楽観値から読むと連打トグルが正しく進む。

使い分け。Server Actions/RSCネイティブで、クライアントに大きな状態ストアを持ち込まないなら useOptimistic（自動ロールバック）。細かい再試行や無限スクロール等クライアントが真実源なら TanStack Query/SWR（onMutateでロールバックを自分で書く）。ひとこと：「送信前に結果を先出しし、成功で確定・失敗で自動で戻す」——対話UIの気持ちよさの核。親stateの更新を忘れないことだけ守れば、コードは驚くほど短い。
