Next.js 16 — runtime='edge' は非推奨に。原則Node.js、移行は“exportを消すだけ”

「困ったらEdge」の終わり。Edgeで落ちる仕組みと、2026の選び方。

📅 2026年10月6日 ⏱ 約4分 🔗 出典 4 件

Next.jsには2つのサーバー実行ランタイムがある。全Node APIが使えるNode.js（既定）と、Web標準APIの限定サブセットだけを持つ軽量なEdgeだ。Edgeは元々、CDN近接の低レイテンシ実行と小さなコールドスタートを狙ってexport const runtime = 'edge'でページ/レイアウト/Route Handlerに指定できた。ところがNext.js 16でこの構図が大きく変わった。「困ったらEdgeに逃がす」時代の終わりで、全App Router開発の土台になる評価軸なので取り上げる。

何が変わったか。(1) ルートセグメントのruntime = 'edge'が非推奨（deprecated）になり、型も'nodejs' | 'edge' (deprecated)と明記。(2) preferredRegionも非推奨。(3) Proxy（旧middleware）の既定ランタイムもEdge→Node.jsに変更（Proxyではruntime設定自体が書けず、書くとthrow）。runtime='edge'を残しているとビルド警告edge-runtime-deprecatedが出るが、公式の移行案内は拍子抜けするほど単純で、「export を削除せよ。Node.jsが既定なので置き換え不要」。背景はVercelのFluid computeなどNodeサーバーレスのコールドスタート/コスト改善で、「Edgeでしか得られない利点」が薄まったことにある。

なぜEdgeで“なぜか本番で落ちる”のか。Edgeはfs/net/child_processなどネイティブNode APIが全面非対応で、require直呼びも禁止（ESMのみ）。さらにeval/new FunctionやWebAssembly.instantiateのような動的コード評価も無効、そしてISR非対応。だからEdge指定のルートに、内部でNodeネイティブを触るパッケージ（DBドライバのネイティブバインディング、fsを使う画像処理、Nodeのcrypto前提のライブラリ等）をimportすると、ビルド時にnode-module-in-edge-runtime、または到達時に実行時エラーになる。紛らわしいのがcryptoで、グローバルのWeb Crypto（crypto.randomUUID()）は動くのに、import crypto from 'node:crypto'は落ちる——「Web標準のcryptoか、Nodeモジュールのcryptoか」の見分けが肝だ。

実務の指針（2026）。原則はNode.js（既定のまま、runtimeを書かない）。レンダリング、データ取得、DBアクセス、after()、use cache、ISR——ほとんどの実ルートはこれが最適だ。既存コードにexport const runtime = 'edge'があれば原則削除してNodeへ寄せる。削除して動かなくなるのは「Edgeでは本来動かないNode依存を無理にEdgeで動かしていた」稀なケースだけで、むしろNodeに戻すとNode APIが解禁され安定する。落とし穴：ISR（generateStaticParams＋revalidate）のページを絶対にEdge化しないこと。どうしても外せない動的評価はProxyのunstable_allowDynamic（glob配列）で検査除外できるが、実際に実行されればthrowする“到達しない箇所専用”の緩和策にすぎない。

まとめ：ルートではruntimeを書かず既定のNode.jsに集約し、Edgeは本当に必要な境界だけ——それも多くはProxy（Node既定）で足りる。移行は「export const runtime = 'edge'を消すだけ」で怖がらなくてよい。
