スクロール・スクラブのフレームシーケンス — Apple風の“映像をスクロールで巻き戻す”演出を、連番画像×canvas drawImage で破綻なく作る

スクロールで製品が回転・分解するApple定番の演出。CSSの scroll-driven animations が2026-10にBaseline入りした今でも、“写実的な映像フレームを何百枚もスクロールに完全同期”させる用途は連番画像＋canvas の drawImage が依然ベスト。video 直スクラブがなぜ本番で破綻するか、sticky区間→進捗→フレームindex の写像、先読み/decode、rAF合流＋lerp＋差分スキップ、Next.js App Router 組み込みまでを押さえる。

📅 2026年11月28日 ⏱ 約5分 🔗 出典 4 件

Apple の製品ページで定番の「スクロールすると製品が回転・分解・組み立てされ、映像がスクロール量にぴったり同期する」演出。ヒーローでの没入感が大きく、2025〜2026 も現役の王道テクニックだ。CSS の scroll-driven animations（animation-timeline: scroll()）が 2026-10 に Baseline Newly available 入りして普及した今でも、「写実的な映像フレームを何百枚もスクロールに完全同期させる」用途は、連番画像 + <canvas> の drawImage が依然ベスト。CSS の animation-timeline は要素の transform/opacity をスクロールで動かすのは得意だが、“動画の各コマそのもの”を順送りする用途ではない。

なぜ video を直接スクラブしないのか

video.currentTime = progress * duration でも作れそうに見えるが本番で破綻する。seek が非同期で次の描画フレームまでに間に合わず、キーフレーム（I-frame）間隔に引っかかって途中コマへ飛ぶとデコードが走ってカクつき、モバイル Safari が autoplay／inline 再生／省電力と戦ってスクラブが詰まる。連番画像なら「frame N は常に frame N」でコーデック状態に依存せず決定的だ。Codrops の OPTIKKA 事例も「HTML5 video → フレームシーケンスへ移行」という同じ結論に至っている。

仕組み：進捗→index を rAF に合流し、lerp＋差分スキップで滑らかに

基本構造は、動画を N 枚の連番画像に分解し、position: sticky; top:0; height:100vh のステージを背の高いスクロール区間（例 400〜600vh）に置く。その区間の進捗 0→1 を フレーム index（index = round(progress * (N-1))）へ写像し、毎フレーム ctx.drawImage(frames[index], …) で描く。肝は3つ——① 全フレームを new Image() で先読みし await img.decode() まで済ませ、重い列は IntersectionObserver と requestIdleCallback でクリティカルパス外へ逃がす。② スクロールイベントで直接 drawImage を呼ばない——目標進捗だけ更新し、実描画は requestAnimationFrame に合流（1表示フレーム＝最大1描画）。③ playhead を lerp（慣性補間）してから round し、index が前回と同じなら描画スキップして冗長 drawImage を避ける。

Next.js（App Router）での組み込み

canvas 描画・scroll 計測・rAF はすべてブラウザ API なので、シーケンスは 'use client' のクライアント・コンポーネントにする。連番は取得順・decode・fetchPriority を自前制御したいので next/image ではなく生 new Image() で先読みし、public/sequence/frameNNNN.webp を素の URL で読む。装飾は SSR 不要なので next/dynamic で ssr:false 遅延ロードして First Load JS を増やさない。連番は不変なので next.config の headers() で Cache-Control: public, max-age=31536000, immutable を付ける。サーバーは画像を配信するだけで、RSC/PPR/ISR とは無干渉だ。

'use client';
const FRAME_COUNT = 120;
const url = (i) => '/sequence/frame' + String(i + 1).padStart(4, '0') + '.webp';
// 1) new Image() で全フレーム先読み → img.decode() を requestIdleCallback に逃がす
// 2) scroll(passive) は target だけ更新し、描画は requestAnimationFrame に合流
// 3) current を lerp → index=round(current*(N-1)) → 前回と同じならスキップ → drawImage(cover)

注意点・ひとこと

落とし穴は3つ。DPR は 1.5 上限（canvas.width = cssW * dpr）でモバイルのメモリを節約する。ffmpeg→WebP 化は静止画基準で品質を選ぶと重すぎる——動いて一部マスクされるフレームは cwebp -q 68 程度で破綻しない。そして prefers-reduced-motion: reduce ではスクラブを無効化し、代表（組み上がった）フレーム1枚を静止表示にして内容を保つ——スクロールで映像が巻き戻る演出は前庭系に強い刺激になり得るためだ。フレーム数が少なく1枚のスプライトに収まるなら animation-timeline: scroll() ＋ steps(N) で JS ゼロの CSS 版にできるが、写実的な数百枚は canvas + drawImage が正解だ。
