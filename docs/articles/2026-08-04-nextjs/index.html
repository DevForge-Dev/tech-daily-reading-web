App Router のテストは「層で分ける」— async Server Component は単体不可、Playwright で E2E／同期は Vitest + RTL

RSC が主流でも詰まりやすいのがテスト。核心は async Server Component を単体テストできない一点。Next 16.2 公式は Vitest/Jest の async RSC 非対応を明記し、async は E2E（Playwright）推奨。三層で役割を分けるのが2026年の実務解。

📅 2026年8月4日 ⏱ 約3分 🔗 出典 5 件

App Router / RSC が定着した後も、もっとも情報が散らばるのが「どうテストするか」だ。核心はシンプルで、async Server Component（async function Page() でデータ取得するコンポーネント）を単体テストできないという一点にある。ここを踏み外すと「テストできない」と行き詰まる。

なぜ落ちるか。async コンポーネントは Promise を返す。render(<Page/>) に Promise を渡すと、同期前提の React レンダラが Error: Objects are not valid as a React child (found: [object Promise]) を投げる。await して解決してから描画する必要があるが、RTL/React は現状それを公式サポートしていない。

何が重要か。Next.js 公式（16.2）は Cypress・Playwright・Vitest・Jest の4ツールをサポートしつつ、Vitest / Jest は async Server Component を公式サポートしないと明記し、async は E2E（Playwright / Cypress）を推奨する。したがって解は「レイヤーで役割を分ける三層戦略」だ。① データ整形などのロジックは純関数に切り出して単体、② 同期 Server Component と Client Component は Vitest + React Testing Library で単体・結合、③ async Server Component・ハイドレーション・ブラウザ依存挙動は Playwright で E2E。

どうしても単体で見たい場合は、<Suspense> でラップして findBy* を await する非公式ワークアラウンドがある（React 19 前提）。ただし公式非サポートなので、基本は E2E に寄せ、切り出した純関数だけを単体で固めるのが堅い。

落とし穴。import 'server-only' や next/headers を含む RSC を jsdom で読むと落ちるため vi.mock() でモックする。Client Component が useRouter/usePathname/useSearchParams を使う場合は vitest.setup.ts で next/navigation をモック。use や useFormStatus など React 19 の新フックを含むならテスト側の React も 19 に揃える。E2E は dev ではなく next build && next start の本番ビルドに当てる（webServer で自動起動）。

自分が試すなら：Server Actions は入力→出力の純ロジックへ寄せて単体（DB/認証はモック）、実フォーム送信は Playwright で E2E。まとめ：「何でも単体」をやめ、async とブラウザ依存を E2E に渡すだけで、App Router のテストは一気にほどける。
