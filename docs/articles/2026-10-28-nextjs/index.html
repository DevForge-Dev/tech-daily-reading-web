Next.js App Routerのレート制限 — 組み込みが無いServer Actions/Route Handlersを多層で守る

Upstash RatelimitとArcjet、3つのアルゴリズム、proxy.ts→アクション層の多層防御、そしてin-memoryという最大の罠まで。429の作法込みで実装の勘所を整理する。

📅 2026年10月28日 ⏱ 約4分 🔗 出典 5 件

Next.js の App Router にはレート制限の組み込み機能が無い。Server Actions / Route Handlers はそのままだと誰でも無制限に叩けるため、総当たり・クレデンシャルスタッフィング・スクレイピング・DoS・従量課金のコスト爆発の入口になる。認証で「誰が何を」を固めても、「どれだけ叩けるか」を絞る層が無ければ守りは未完成だ。

2026年の定番と、まず選ぶアルゴリズム

定番は Upstash Ratelimit（@upstash/ratelimit + @upstash/redis）か、レート制限＋ボット検知＋Shield(WAF)を1つの aj.protect() に束ねる Arcjet。カウント方式は3種あり、用途で選ぶ。

どこで・誰を数えるか

識別子は匿名ならIP、認証後はユーザーID（共有IP・IPローテーション対策）。ただし Next.js 15+ で req.ip/req.geo は廃止——Vercel は ipAddress(request)、他は x-forwarded-for の先頭エントリ（信頼できるプロキシ配下でのみ信用）。掛ける場所は多層で、proxy.ts（旧 middleware、最前段）で計算コストを節約しつつ、Route Handler / Server Action でも limit() を呼び直すのが鉄則だ。

Server Action は自動IP取得が無いので headers() から自分でIPを取り、アクション名で prefix して枠の食い合いを防ぐ。

"use server";
const ip = (await headers()).get("x-forwarded-for")?.split(",")[0]?.trim() ?? "anonymous";
const { success } = await ratelimit.limit(`contact_${ip}`); // ← アクション別に分離
if (!success) return { ok: false, message: "送信が多すぎます。少し待って再試行を" };

落とし穴

最大の罠はin-memory ストア。サーバーレス/マルチインスタンスでは各インスタンスが別カウンタを持ち、実効上限が「上限×インスタンス数」に膨らんで機能しない。Upstash Redis 等の分散ストア（HTTP/RESTでEdge互換）が必須。超過時は 429 + Retry-After（resetはUNIXミリ秒なので Math.ceil((reset-Date.now())/1000)）と X-RateLimit-* を返す。分析書き込みの pending は waitUntil(pending) / after() で背後完了させ、new Map() を ephemeralCache に渡してブロック済みIPの無駄なRedis往復を省く。クライアントはモジュールスコープで1回だけ生成して使い回す。

ひとことまとめ

「Redisを持ち細かく握りたいなら Upstash、ボット＋WAFまで一括なら Arcjet」。どちらでも①分散ストア必須 ②機微操作はエッジ層だけに頼らない ③429にRetry-After ④認証後はユーザーIDが共通の作法。next-safe-action を使うなら .use() ミドルウェアで全アクションに横断適用でき、型付きエラー契約に乗せられる。
