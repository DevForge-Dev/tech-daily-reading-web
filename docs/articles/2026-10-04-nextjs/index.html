Next.js 16 データ取得の“滝”を断つ — 並列フェッチ / React.cache / preload

awaitの置き方ひとつで直列ウォーターフォールが生まれTTFBが悪化する。fetchが既定キャッシュなしになった16だからこそ、並列・重複排除・先回りの設計が効く。

📅 2026年10月4日 ⏱ 約3分 🔗 出典 4 件

App Routerでは Server Component を async にして直接 await fetch() やORMクエリを書ける。書き味は素朴で気持ちいいが、awaitの置き方ひとつで「リクエストウォーターフォール（直列の滝）」が簡単に生まれる。互いに独立した取得まで一本道で待たされ、TTFB/LCPを悪化させる。Next.js 16では fetch が既定でキャッシュされず毎リクエスト実行になったため、「いつ走り、いつ重複排除され、いつブロックするか」を設計する価値がいっそう高まっている。

既定の挙動を押さえる。layout・page・各セグメントは既定で並列レンダリングされる。直列化が起きるのは「同一コンポーネント内でawaitを並べたとき」と「親→子でデータ依存があるとき」だけだ。また同一レンダーパス内の同じ引数の fetch は自動で重複排除(リクエストメモ化)されるので、props drillingせず必要な場所でその都度呼んでよい。fetch を使わないDB/ORMは効かないので React.cache でラップする。

直列を並列に直す。独立なのに const a = await getA(); const b = await getB(); と書くと、getBはgetA完了まで待つ。関数を先に呼んでPromiseを作り、まとめて待てばよい：

// ✅ 呼んだ瞬間に両方着火 → まとめて待つ
const artistData = getArtist(username)   // await しない
const albumsData = getAlbums(username)
const [artist, albums] = await Promise.all([artistData, albumsData])
// 一部失敗を許容するなら Promise.allSettled

さらに preloadパターン——消費コンポーネントの隣に export const preload = (id) => void getItem(id) を置き、描画より前に着火しておくと、別のブロッキング処理と並行してデータが流れる。成立条件は重複排除（fetchは自動／ORMはReact.cache／Cache Componentsなら use cache）だ。

落とし穴。Promise.all は1つでも失敗すると全体がrejectになる——一部許容は allSettled。React.cache はリクエストスコープのみで、リクエストをまたいだ永続キャッシュではない点に注意。params/searchParams は非同期なので await が要る。loading.js は同一セグメントのlayoutが未キャッシュデータ(cookies()等)を読むとフォールバックせずナビゲーションをブロックするので、その箇所を個別の <Suspense> で包むか取得をpage側へ寄せる。同じコードでも「いつ着火するか」で体感速度は大きく変わる。
