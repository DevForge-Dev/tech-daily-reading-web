11/1のNext.js — styled-componentsがメンテナンスモードへ。RSC時代の“ゼロランタイムCSS”(Panda/vanilla-extract/StyleX)への移行

styled-componentsが公式にメンテナンスモード入り。レンダリング時注入はRSCに乗らず、新規App Routerの既定はビルド時に静的CSSへコンパイルするゼロランタイム型へ。3者の違いと選定の勘所を図解。

📅 2026年11月1日 ⏱ 約4分 🔗 出典 4 件

背景・なぜ今これか。2025年、styled-components が公式にメンテナンスモード(新機能停止・重大修正のみ)へ移行した。作者 Max Stoiber 自身が区切りを宣言。理由は単純で、React Server Components(RSC)とランタイム CSS-in-JS の相性が本質的に悪いこと。「styled-components が悪い」話ではなく、レンダリング時に JS でスタイルを生成・注入する方式そのものが Server Component モデルに乗らない構造問題で、App Router 新規の既定が「ランタイム型」からビルド時に静的 CSS へコンパイルする“ゼロランタイム”型へ移る潮目として注目に値する。

なぜ RSC で苦しいか。styled-components / Emotion はレンダリング中にスタイルを集約し DOM へ注入する——クライアント実行前提の振る舞いで、原則ランタイムを持たない Server Component では直接成立しない。App Router でランタイム型を使うには必ず 'use client' 境界＋スタイルレジストリ＋SSR 統合層が要り、その瞬間ツリーはクライアント化して RSC の利点(サーバ完結・JS 送信量削減)を失いやすい。React 18 のストリーミング SSR とは FOUC やハイドレーション不整合のリスクもある。React 19 のネイティブ <style> は改善だがランタイム CSS-in-JS を“RSC ネイティブ”にはしない。

ゼロランタイム3者の違い(落とし穴込み)。vanilla-extract は *.css.ts に書きビルド時に静的 CSS へ(型安全・ランタイム0、CSS Modules に型を足した感覚)。Panda CSS は css()/cva() の書き味で静的アトミック CSS を出力、strictTokens で生 hex をコンパイルエラーにできデザインシステムからの逸脱を型で止められる(ただし [123px] の角括弧任意値は型チェックを素通り)。StyleX(Meta 製)は stylex.create()＋stylex.props() でマージ順＝呼び出し箇所で勝敗が決まる決定的合成が売りで、大規模のスタイル漏れ対策に向く。3者共通でプロバイダもレンダリング時注入も不要だから RSC で動く。共通の落とし穴は実行時にしか決まらない動的値はアトミッククラスにできないこと(CSS 変数や data-* で逃がす)。

実務の指針・ひとことまとめ。既存の安定コードや実行時データでのテーマ切替が本質なアプリはランタイム型のままで問題ない。移行は「RSC 採用」「計測可能なボトルネック」「大規模リライト中」など具体的な理由がある時だけ段階的に進める。新規の App Router 中心なら、トークン逸脱を型で止めたいなら Panda、大規模のスタイル漏れを封じたいなら StyleX、素の CSS に型だけ欲しいなら vanilla-extract、学習コストを避けたいなら CSS Modules か Tailwind——が 2026 年の現実的な勘所だ。
