Rive を Next.js App Router で — 状態を持つベクターアニメを 'use client' の島に隔離する

Lottie が再生専用なのに対し、Rive は State Machine と Data Binding でユーザー操作に反応する。App Router では完全クライアント専用のこのランタイムを RSC ページの中の小さな島に閉じ込め、SSR を外して CLS を防ぐのが定石になる。

📅 2026年7月28日 ⏱ 約3分 🔗 出典 4 件

なぜ今これが話題か

マイクロインタラクションやオンボーディングのキャラクターなど「操作に反応して滑らかに変形する UI」を、動画でも大量の CSS でもなく1つの .riv バイナリで賄いたい需要が増えている。Rive はデザインツールと各プラットフォーム共通ランタイムがセットで、成果物を実行時に WASM＋Canvas/WebGL2 で描画する。Lottie との決定的な差は状態を持ち対話できること。Lottie が録画済みアニメの宣言的プレイヤーなのに対し、Rive は State Machine をファイル内に内蔵し、実行時に Inputs を送り込むと状態遷移とブレンドで動きが変わる。

何が新しいか

2026 のランタイムの主役は Data Binding（View Model / VMI）。デザイン側で宣言した型付きプロパティ（number/boolean/string/color/enum など）に、コードから autoBind ＋ useViewModelInstanceNumber 等のフックで双方向に触れる。State Machine Input の上位互換的な「アプリ状態とアニメの共有言語」だ。パッケージは公式クイックスタートが @rive-app/react-webgl2 を推奨（旧 react-webgl よりビルドが大幅に小さい）、軽量重視なら @rive-app/react-canvas。

App Router での組み込み

大原則は「Rive は完全にクライアント専用」。WASM・Canvas/WebGL・window/document に依存するため SSR 不可。したがってページ本体とデータ取得は RSC のまま、<RiveComponent> を含む部品だけを 'use client' の島にする。ちらつきや CLS を避けたいなら島を dynamic(() => import('./RiveButton'), { ssr:false }) で読み込み、固定サイズのプレースホルダを出しておく。State Machine を使うなら useRive ＋ useStateMachineInput のフック方式が推奨で、入力は Trigger=fire()、Boolean=value=true/false、Number=value=0.5 の3型で使い分ける。

注意点・落とし穴

最頻の罠はサイズ。Canvas は親コンテナに追従するので、幅・高さの無い箱に入れると何も描画されない。入力名・ステートマシン名は文字列一致で、エディタ表記とズレると useStateMachineInput が null を返す（必ず optional chaining）。多数同時表示は WebGL のコンテキスト上限に当たるので useOffscreenRenderer:true を付ける。アクセシビリティは prefers-reduced-motion を検出して .riv に渡す（専用 Boolean 入力か autoplay:false）のが公式推奨。

ひとことまとめ

Rive は「RSC は据え置き、動く部分だけ小さなクライアント島」というApp Router の分割思想にきれいに乗る。SSR 外し＋固定サイズプレースホルダで CLS をゼロに保ちつつ、Data Binding でアプリ状態とアニメを同じ言葉で繋ぐのが2026の型だ。
