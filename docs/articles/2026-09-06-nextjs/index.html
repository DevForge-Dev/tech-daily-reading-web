SWRをNext.js App Routerで — RSCのfallbackで初期化→Client useSWR→mutate楽観更新×updateTagで2層キャッシュ整合

SWRはVercel製で、Next.js公式ドキュメントに専用の統合ガイドがある唯一のデータ取得ライブラリ(依存ゼロ・約4KB)。SWR 2.3.0＋React 19でServer Componentが未awaitのPromiseをfallbackに渡し、境界を越えてSSR中に解決。Next.js 16のCache Components(use cache/cacheTag/updateTag)と組み、サーバーキャッシュとブラウザキャッシュを共有コントラクト(同一key/tag)で整合させる。

📅 2026年9月6日 ⏱ 約4分 🔗 出典 3 件

状態管理カテゴリはこれまで Zustand(クライアント状態)・nuqs(URL状態)・TanStack Query(サーバー状態)を扱ってきたが、もう一つのサーバー状態ライブラリ SWR(Vercel製・stale-while-revalidate)が抜けていた。SWRは Next.js公式ドキュメントに専用の統合ガイドがある唯一のデータ取得ライブラリで、TanStack Queryより軽量(依存ゼロ・約4KB)。2026の注目点は、RSC(Server Component)からClient Componentへの初期データ受け渡しが公式に整理されたことだ。

何が新しいか

SWR 2.3.0 ＋ React 19 で、Server Componentが SWRConfig の fallback に未awaitのPromiseを渡し、それが use client 境界を越えてクライアントに流れ、SSR中にSWRが自動解決する。実験的な SWR 2.5.0-beta では preload() ＋ cacheData という別のプリフェッチ経路も追加された。そして Next.js 16 の Cache Components(use cache / cacheTag / updateTag)と組み合わせ、サーバーキャッシュ(Next.js)とブラウザキャッシュ(SWR)の2層を共有コントラクト(同一のkeyとtag)で整合させるパターンが確立した。

仕組みのポイント

RSCで import できるのは SWRConfig / preload / unstable_serialize まで。フック(useSWR/useSWRInfinite/useSWRMutation)はクライアント専用で、使うコンポーネントには use client が要る。最重要は fallbackのkeyと useSWR のkeyを完全一致させること——ズレるとfallbackが無視され二重取得になる。だから key と tag は共有コントラクトとして1ファイルに定義して使い回すのが定石だ。書き込みは楽観更新でUIを即反映し(mutate の optimisticData / rollbackOnError)、サーバー側はServer Actionで updateTag を呼び、cacheTag と同じタグを失効させて次の読取を新鮮化する。

使いどころ・注意点

Vercel/Next.js中心で軽さ重視ならSWR、staleTime/gcTimeや高度なキャッシュ制御が要る大規模はTanStack Query、という住み分け。SWRには時間ベースの鮮度窓(staleTime相当)が無い点は要注意で、定期更新は refreshInterval、マウント毎の再取得抑制は revalidateIfStale:false で制御する。取得を Server Actionに直結すると直列化で固着しやすいので、取得はRoute Handler(GET)、書込はServer Action＋mutate/updateTagに分けるのが安全。params と Route Handler の ctx.params はNext.js 16でPromise化されawait必須になった点も忘れずに。

ひとことまとめ：keyを1箇所に定義し、fallbackで初期化・mutateで楽観更新・updateTagでサーバー整合、の三点セットでSPAの体感とSSRの初速を両立できる。
