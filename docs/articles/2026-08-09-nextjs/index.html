next/dynamic とコード分割 — App Router で ssr:false を正しく効かせる土台

初期JSを削ってLCP/INPを稼ぐ、コンポーネント/ライブラリ単位の遅延読み込み。Server Componentsは既定で自動分割され、遅延が効くのはClient Componentsとライブラリだけ。ssr:falseはClient専用で、window/WASM依存の島は'use client'ラッパに隔離するのが王道。Next.js 16.3の作法を1本に。

📅 2026年8月9日 ⏱ 約3分 🔗 出典 3 件

アニメ島（Rive・three.js・WebGL・カスタムカーソル）を扱うメモの大半が前提にしている『window/canvas/WASM に触るから SSR 不可 → dynamicの島に隔離』。その土台を1本に集約する。狙いは初期ロードのJSを減らして LCP/INP を稼ぐこと、つまりルート単位より一段細かいコンポーネント/ライブラリ単位のコード分割だ。

何が新しい/重要か

Next.js 16.3.0（更新 2026-03-10）の公式は、Server Components は既定で自動コード分割されクライアントJSに乗らないため、遅延読み込みの対象はClient Components とインポートしたライブラリに限られると明言する。手段は3つ。①next/dynamic（loading と ssr を持つNextの抽象、React.lazy+Suspenseの合成）、②素の React.lazy()+<Suspense>、③import() 式でライブラリを操作時に遅延。最重要は ssr:false の意味：Client Component は既定でSSR（プリレンダー）されるが、ssr:false を付けるとサーバーでは描画せず最小プレースホルダだけ送り、クライアントでJS到達後に初めて描画する。

落とし穴

ssr:false を Server Component に直書きするとビルドエラー（`ssr: false is not allowed with next/dynamic in Server Components`）。回避は 'use client' のラッパを1枚挟むこと。名前付きexportは import('./B').then(m => m.Named) で継ぐが、ssr:false×名前付きは不安定な既知の罠なので default export に寄せるのが堅い。prefetchオプションは無いので、高確率の操作は onMouseEnter/onFocus で同じ import() を叩いてチャンクを温める。CLS対策にプレースホルダは最終描画と同寸法を先取りする。Turbopack（Next16でbuildも既定）では webpackOptional は非対応で turbopackOptional:true を使う。

まとめ

RSCファーストなら『そもそも分割不要な領域が広い』のが前提。効かせどころは重い・使用確率が低いClient島とライブラリに絞り、@next/bundle-analyzer で効果を確認する。分割し過ぎのウォーターフォールは逆効果。
