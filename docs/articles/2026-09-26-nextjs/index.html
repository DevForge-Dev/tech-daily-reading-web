Vercel AI SDK 7でストリーミングチャットを組む — streamText × useChat × UIMessage/parts

v7でAPI名が総入れ替え。サーバのstreamTextとクライアントのuseChatで型安全なチャットを最短で組む、今動く書き方。

📅 2026年9月26日 ⏱ 約3分 🔗 出典 4 件

入力すると LLM がトークンを逐次生成し、UI に1文字ずつ流れ込むチャット／コパイロット UI は、2026 年の Next.js アプリで最頻出の機能になった。生の Route Handler から SSE を手書きしても実現はできるが、プロトコル・再接続・ツール呼び出し・メッセージ整形・型付けを全部自前で抱えることになる。Vercel AI SDK はこの層を丸ごと引き受ける事実上の標準で、サーバの streamText() とクライアントの useChat() の2つで型安全なストリーミングチャットがほぼ完成する。

何が新しいか（v7 でAPI名が総入れ替え）

厄介なのはバージョンが速いこと。現時点の npm 最新はコア ai が 7.0.x、React アダプタ @ai-sdk/react が 4.0.x とメジャー番号が別採番で、プロバイダ（@ai-sdk/openai 等）も v7 世代へ揃える必要がある。ネット上のチュートリアルの大半は v4/v5 で止まっており、名前がいくつも変わっている。前提として v7 は Node.js 22+ / ESM 専用。

仕組みの勘所

設計の核心は UIMessage / parts モデルだ。UI の真実である UIMessage（ID・メタ・parts を持つ）と、LLM 入力用に最適化した ModelMessage を分離し、convertToModelMessages() で変換してから渡す。レンダリングでは message.content を読まず必ず message.parts を回す——1応答は text / reasoning / tool-<name> / data-<name> などの順序付き配列で、content を読むとツール呼び出しや推論・ファイルが空になる。履歴は RSC で DB から読み、props でクライアント島へ渡して useChat({ messages }) に流す。保存はサーバ側の終了コールバック（v7 の onEnd）で確定した UIMessage[] 全体を書く——クライアント保存は改ざん・欠落リスクがある。

落とし穴と自分の試し方

ハマりどころは、番号ズレによる型不整合、parts を無視した表示欠落、サーバレスの関数タイムアウト（export const maxDuration = 30 を Route Handler に置く）、stopWhen 付け忘れによるツールループ暴走、そして入力状態の二重管理（v7 の useChat は入力を持たない）。自分が試すなら、まず既存の生 SSE 実装（LLM 以外の任意イベント向き）はそのまま残し、チャット部分だけ AI SDK 7 へ載せ替えて住み分けるのが安全だ。
