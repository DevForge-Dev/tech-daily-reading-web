Clerk を Next.js 16 App Router で使う — 鍵は「proxy.ts へ改名」と「Cache Components 下は auth() を Suspense で囲む」の2点

マネージド認証の最有力 Clerk の導入完全手順。Next.js 16 との噛み合わせが2つ更新された——(1) ミドルウェアが middleware.ts→proxy.ts に改名、(2) cacheComponents 既定下では auth()/currentUser() を Suspense で囲まないと next build が失敗。この2点を外すと最新テンプレートでビルドが通らない。

📅 2026年11月18日 ⏱ 約5分 🔗 出典 3 件

認証 SaaS の Clerk は、サインイン/サインアップ UI・セッション・ユーザー/組織管理・ソーシャルログイン・MFA をホスト型で提供し、プリビルト UI コンポーネントを置くだけで本番品質の認証が立ち上がる。自前でセッション・OAuth を実装する Better Auth/Auth.js とは『どこまで預けるか』の思想が異なり、実装速度を最優先するスタートアップ/SaaS で定番だ。注目すべきは、Next.js 16 との噛み合わせが 2026 後半に2つ更新され、これを外すと最新テンプレートで next build が通らないことだ。

仕組み：ブラウザ・ミドルウェア・サーバヘルパの3層

Clerk は ClerkProvider（Client）＋ clerkMiddleware()（proxy.ts）＋ サーバヘルパ auth()/currentUser() の3層で動く。セッションは Cookie で運ばれ、ミドルウェアが各リクエストで検証して『認証状態』をアプリ全体に通す。パッケージは単一の @clerk/nextjs で、導入は CLI npx -y clerk@latest init が推奨（.env.local・Provider・proxy.ts・認証ルートを自動生成）。環境変数は公開鍵 NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY と秘密鍵 CLERK_SECRET_KEY の2つだ。

Next.js 16 の落とし穴①：middleware.ts → proxy.ts

ファイル名は Next.js 16+ = proxy.ts、15 以前 = middleware.ts（中身は同一）。src/ 採用時は src/proxy.ts、無ければプロジェクト直下。場所違いは『ミドルウェアが動かない』定番バグだ。なお clerkMiddleware() は既定で何も保護しない（全ルート公開＝認証状態を通すだけ）。保護はオプトインで、createRouteMatcher ＋ auth.protect() で宣言する。

// src/proxy.ts（NJS15以前は src/middleware.ts・中身同一）
import { clerkMiddleware, createRouteMatcher } from '@clerk/nextjs/server'
const isProtected = createRouteMatcher(['/dashboard(.*)', '/settings(.*)'])
export default clerkMiddleware(async (auth, req) => {
  if (isProtected(req)) await auth.protect() // 未認証はサインインへ
})

落とし穴②（最重要）：Cache Components 下は Suspense 必須

cacheComponents: true（create-next-app 既定）だと、auth()/currentUser()（＝Cookie/ヘッダ読み取り＝動的）を <Suspense> 境界の外で呼ぶと next build が失敗する。レイアウトのヘッダ（<Show>＋<UserButton>）やデータを読む Server Component は <Suspense> で囲む。これにより静的シェルを先に流し、認証部分はストリーミングで後追いになり、TTFB を保ちつつビルドも通る。auth() は async なので必ず await auth()。UID だけなら const { userId, isAuthenticated } = await auth() でネットワーク往復なし、currentUser() は Backend API を叩きレート制限を消費する点が決定的な差だ。

実務での勘所・注意点

'use client' はフックを使う自作コンポーネントだけの小島に隔離し、ページ本体・データ取得は RSC のまま残す（ClerkProvider やプリビルトは内部 Client だが親 layout を client 化する必要はない）。機密漏洩の罠として、currentUser() が返す Backend User には privateMetadata が含まれる＝丸ごとクライアントへ渡さない。クライアントで必要なら useUser() を使う。auth()/currentUser() は Cookie を読む＝そのルートが動的化するので、公開ページは認証を読まない設計にし、認証が要る枝だけ動的にするのが静的化を効かせるコツだ。

ひとこと

Clerk は『UI・ユーザー/組織管理まで預ける』マネージド路線で、Auth.js/Better Auth の『自前セッション＋OAuth』路線と使い分ける。Next.js 16 では proxy.ts と Suspense の2点さえ外さなければ、プリビルトを置くだけで本番品質の認証が数十分で立ち上がる。自分で試すなら npx clerk@latest init から入り、まず dashboard ルートを1つ protect して挙動を掴むのが早い。
