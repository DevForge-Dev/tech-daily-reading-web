next-safe-action v8 で Server Actions を型安全に — Standard Schema 採用でアダプタ不要、エラーは既定で握って漏らさない

素のServer Actionsが空ける3つの穴（検証なし・エラー漏洩・認可の手書き）を薄いラッパー1枚で塞ぐ。v8はStandard Schemaに乗り換え、Zod/Valibot/ArkTypeをそのまま渡せる。

📅 2026年10月11日 ⏱ 約4分 🔗 出典 4 件

背景。App RouterのServer Actionsは「'use server'を付けた非同期関数をそのまま呼べる」手軽さが魅力だが、生のまま使うと3つの穴が空く。(1) 引数が実質anyで実行時バリデーションが無い（クライアントから任意の値が来る＝公開エンドポイント）、(2) throwしたエラーがスタックごと本番でクライアントへ漏れうる、(3) 認証チェックやログ取りを毎アクション手書きする羽目になる。

何が新しいか。next-safe-action（現行v8.6.0）は、この3つを薄いラッパー1枚で塞ぐライブラリ。v8最大のトピックはStandard Schema採用だ。v7まで必要だったvalidationAdapterが不要になり、Zod・Valibot・ArkTypeなどStandard Schema準拠ライブラリをそのまま渡せる。バリデーション断片化を解消する業界標準に素直に乗り、乗り換えコストが大きく下がった。

仕組み（4段チェーン）。tRPCに着想を得た「クライアント生成→ミドルウェア→入力スキーマ→ハンドラ」のチェーンで、契約を全アクションに強制する。createSafeActionClient()で共通のエラー整形・メタデータ型を集約し、.use()で認可やログをctxに型付きで積み上げ、.inputSchema()（v7で.schema()から改名）を通過した値だけがparsedInputに入り、.action()で本体を書く。

返り値とエラー処理が肝。アクションの戻りは常に{ data, validationErrors, serverError }の決まった形。既定はフェイルセーフで、ハンドラがthrowしても汎用文言"Something went wrong"だけがserverErrorに入り、詳細はサーバログ止まり＝情報漏洩しない。handleServerErrorでActionErrorなど想定内の例外だけメッセージをユーザーに通せる。

// lib/safe-action.ts （'use server' は付けない！）
export const actionClient = createSafeActionClient({
  handleServerError(e) {
    console.error(e.message);               // 詳細はログだけ
    if (e instanceof ActionError) return e.message;
    return "予期しないエラーが発生しました";  // それ以外は汎用
  },
});

落とし穴。クライアント設定ファイル（lib/safe-action.ts）に'use server'を書かない——付けてよいのはアクションをexportするファイルだけ。Server Actionsは裏でPOSTエンドポイントとして公開されるので「サーバーだから安全」ではなく、認可は必ずミドルウェア/DALで。フックのexecute()はfire-and-forgetでthrowしないため、結果で分岐したいならexecuteAsync()を使う。成功後のrevalidatePath/revalidateTag（Next.js 16はupdateTag）は手動だ。v8ではredirect()/notFound()が透過的に扱われ、状態はhasNavigated・新設のonNavigationで受ける（handleServerError内で握り潰すと遷移が死ぬ）。

ひとこと。素のServer Actionsの"手軽さ"は本番では穴になる。型安全・エラー隠蔽・認可集約を一枚で担保できるこのレイヤは、公開APIとしてのServer Actionsに素直に効く。
