Sonnerで作る“良いトースト” — App RouterでServer Actionの結果をクライアントに橋渡しする3パターン

shadcn/ui既定のSonner（週4000万DL超）。スタックの滑らかさの本質はkeyframesではなくtransition、スワイプは速度ベース。最大の難所はServer Action（サーバー）→トースト（クライアント）の橋渡しで、useActionState／Cookieフラッシュ／searchParamsの3系統を使い分ける。

📅 2026年8月14日 ⏱ 約3分 🔗 出典 4 件

トーストは「作るのは簡単、"良い"ものを作るのは難しい」典型だ。素朴に実装すると連続発火でスタックがカクつき、スクリーンリーダーに読まれず、prefers-reduced-motionを無視し、Server Action→redirectをまたいで消える。Sonner（Emil Kowalski作、週4000万DL超、shadcn/uiの既定）はこれらを既定で解いており、2025〜26のReactエコシステムの事実上の標準になった。

仕組みの要点。状態管理はReact ContextではなくObserverパターン——<Toaster>がToastStateをsubscribeし、どのClient Componentからtoast()を呼んでもフックなしで届く。スタックアニメの本質はkeyframesではなくtransition：keyframesは中断・再ターゲット不可で連打時に古いトーストが新位置へジャンプするため、各トーストをposition:absoluteにし、indexに応じたtranslateYとscaleをtransitionで掛けて滑らかに追従させる。スワイプは速度ベースで、|swipe| / 経過ms が約0.11を超えれば短距離のフリックでも消える。裏タブはdocument.hiddenでタイマーを一時停止し、toast.promiseは処理中→成功/失敗を1つのトーストで自動遷移する。アクセシビリティはaria-live内蔵、reduced-motion環境ではCSSでtransitionを無効化する。

App Router固有の難所は、トーストは'use client'の世界なのに発火したいのはServer Action（サーバー）というズレだ。橋渡しは3系統。(1) useActionState + useEffect：actionが { ok, message, ts: Date.now() } を返し、useEffect([state.ts]) で発火する（同じstate値だと再発火しないためタイムスタンプ必須／ただしredirectをまたぐと直前と同じstateを返すため不向き）。(2) Cookieフラッシュ：Server Action内で cookies().set('toast-...', msg)、ルートに置いたasyncな <Toaster> Server Component（<Suspense>必須）がCookieを拾ってClientへ渡す——redirect・リロードをまたいでも生き残る。(3) searchParams：redirect('/done?toast=saved') して遷移先で読む（軽いがURLが汚れる）。

使いどころと注意点。同一ページ更新なら(1)、redirect後に確実に出すなら(2)が定番だ。トーストは副作用なのでレンダリング中に呼ばない（必ずevent／useEffect／transition内）。Cookie方式のToasterは動的APIを使うため<Suspense>で包み、PPRでも動的化しないよう気をつける。

ひとことまとめ：Sonnerは"良いトースト"の細部を既定で解く。App Routerでは「redirectをまたぐか」で橋渡しを選ぶのが勘所だ。
