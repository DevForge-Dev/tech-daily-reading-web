constとKeyはなぜ効くのか — ElementのcanUpdateを味方につけてrebuildを短絡する（11月3.50を前に）

stable 3.47.8（Dart 3.13.7・eMudhra CAブロックのセキュリティ更新）が出て、11月の3.50が射程に。足元で効くのは、const/Key/memoizationでElementの再利用を促し16.67msの予算を守る地味な技だ。

📅 2026年10月27日 ⏱ 約4分 🔗 出典 5 件

現況はstable 3.47.8 / Dart 3.13.7（10/23）。これは侵害されたeMudhra中間CA鍵をブロックするセキュリティ更新（勧告GHSA-frr6-h895-5pxp）で、本番はca-certificates更新＋3.47.8へpinが定石。betaは3.50.0-0.2.pre / Dart 3.14.0＝11月stable昇格の2本目で、Web WasmGC既定化・Android Impeller一本化・Wasm遅延ロードstable・Android17 day-zeroが確定事項。material_ui/cupertino_uiは11月に正式deprecation（移行はdart fix --code=migrate_design_widgets）。今のうちにbuild web --wasmとappbundleを緑にしておきたい。——その“足元を固める”流れで今日は、派手さは無いが効くrebuild短絡を深掘りする。

仕組み — canUpdate() が再利用の分かれ道

毎フレーム、frameworkは新しいwidgetツリーを既存のElementと突き合わせる。canUpdate()はruntimeTypeとkeyを比較し、一致すればElementを再利用してmount()ではなくupdate()を呼ぶ。ここでconstコンストラクタは正準インスタンス（canonical）を生むので、identical()で同一と分かった部分木は比較ごとスキップ＝rebuildを短絡できる。Keyはリスト並べ替えで「どのElementがどのwidgetに対応するか」を安定させ、部分木の作り直しを防ぐ。

どれだけ効くか（実測・非公式）

数字で見ると効果は無視できない。12 widgetの商品カードで7つをconst化＋TextStyle 2つをstatic final退避で4.2ms→1.8ms（約57%減）。20スイッチの設定画面でラベルをconstの_SettingLabelに抽出して3.1ms→0.9ms（OnePlus 9）。極めつけはKeyで、50件チャットの並べ替えが8〜12ms → ValueKey(message.id)で1ms未満。StatelessWidget単発rebuildはPixel6で約50〜200µs、ListViewタイル30個で1.5〜6ms——16.67msの予算に対して決して小さくない。

memoizationの型と使い分け

テーマ由来のTextStyle等はstatic final、不変モデル由来のwidgetはlate final、重い部分木はconst StatelessWidgetでラップして内側だけrebuild。使い分けの指針は「組み込み暗黙 > TweenAnimationBuilder（組み込みに無い単発プロパティ）> 明示アニメ（ループ）」と同じく、まず軽い手段から。

注意点・落とし穴

UniqueKey()をbuild内で使うと毎回別Element化するので禁物。Theme/MediaQuery等のInheritedWidget依存をキャッシュすると値がstale化し、コールバックを抱えたキャッシュは古いクロージャを掴む。そして最重要——const化は勘でやらない。必ず--profileビルドでDevToolsのWidget.buildスパンと「Track Widget Rebuilds」を見て、カードやリストタイルのような高頻度rebuildパスを計測してから効かせる。

ひとことまとめ

constは「定数宣言」ではなく「Elementに“これは変わらない”と伝える最適化ヒント」。11月の3.50でレンダリング基盤が動く前に、canUpdateを味方につける癖をつけておきたい。
