タブの下線が「滑って移動」する magic move — 4つの実装と、見た目とa11yの分離

アクティブ下線/ピルを旧位置から新位置へ滑らせる定番演出。素朴な left/width の setState はジャンクの元。Motion layoutId・FLIP+WAAPI・View Transitions・CSS-only の4型と、装飾は aria-hidden・意味は WAI-ARIA で別組みが要点。

📅 2026年8月12日 ⏱ 約3分 🔗 出典 4 件

タブやセグメンテッドコントロールの「アクティブを示す下線・ピル」が、選択を切り替えると旧位置から新位置へ滑って移動する演出（"magic move" / shared-element indicator）。ダッシュボードのタブ、設定のセグメント、ドキュメントのサイドナビと適用範囲が広い。本質は毎回「1個の要素が別のボックスへ移る＝旧box→新boxの補間」で、違いは誰が差分を計算し何が動かすかだけ。素朴に left/width を毎フレーム setState でトゥイーンすると再レンダー地獄でジャンクになる典型なので、正しい型を押さえたい。

①Motion layoutId（宣言的・最有力）：アクティブなボタン内にだけ <motion.span layoutId="tab-indicator"> を描く。アクティブが変わると旧要素が unmount・新要素が mount され、Motion が同名 layoutId を「同一要素」とみなして消えた位置から現れた位置へ自動 spring 補間。位置変更は animate ではなく style/className（レイアウトそのもの）で行うのが肝（二重駆動回避）。React 実装コスト最小。②FLIP+WAAPI（依存ゼロ）：旧 getBoundingClientRect→新rect→translateXに位置差・scaleXに幅比を入れて旧位置に見せ、el.animate([...]) で実位置へ戻す。読み取りと書き込みを分離し、補間対象は transform だけ＝コンポジタ合成でINP有利。③View Transitions：view-transition-name を付け DOM 更新を startViewTransition で包むと自動モーフ。2025年に match-element・:active-view-transition・要素スコープ版が入り、Firefox 144 対応でBaseline化。タブ切替がルート遷移そのものなら本命。④CSS-only：hidden radio＋:has(:checked) で transform: translateX()、RSCのまま hydration ゼロだが可変幅は苦手。

App Router 組み込み：CSS-only は Server Component のまま。Motion/FLIP/VT はインジケーターの島だけ 'use client'、初期アクティブを props で渡すとサーバー描画とクライアント state が一致し hydration mismatch なし・以後の切替でだけ滑る。

最重要は a11y——「滑る見た目」と「意味構造」を分離すること。インジケーターは装飾なので aria-hidden。パネルを切り替えるなら WAI-ARIA Tabs（親 role="tablist"／各 role="tab"＋aria-selected＋aria-controls、矢印キー移動＋ローミング tabindex）。ページ内リンク集は tablist ではなく <nav>＋aria-current="page"。prefers-reduced-motion: reduce で滑走を止め位置だけ即切替（動きに敏感な人は約3人に1人）。落とし穴は毎フレーム setState・key={index} での誤補間・フォント読込/リサイズ時の再計測漏れ。

まとめ：4型の本質は同じ「旧box→新boxの補間」。可変幅・対話性は Motion か FLIP、等幅の表示切替だけなら CSS-only。どれを選んでも a11y は別建てにする。
