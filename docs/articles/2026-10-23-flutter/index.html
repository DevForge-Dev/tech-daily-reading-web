状態管理を「アダプタ層」で隔離する — 2026のRiverpod3/BLoC/signals選定とベンチ

Widgetを抽象コントローラに依存させ、実体（Riverpod/BLoC/signals）を差し替え可能にする。乗り換えコストを下げる設計と、著者実測ベンチ・移行見積もりを総点検（現行 stable 3.47.7 前提）。

📅 2026年10月23日 ⏱ 約3分 🔗 出典 3 件

現行の安定版は 3.47.7 / Dart 3.13.5（beta 3.50.0、11月 stable 待ち）。3.47 で Material/Cupertino が material_ui/cupertino_ui 1.0 として分離し flutter_localizations も切り離されるなど土台が動いた今、上物の状態管理をどう選び、どう乗り換え可能に保つかが改めて問われている。核になる設計は単純だ——Widget を抽象コントローラ（interface）に依存させ、実体を Riverpod notifier / BLoC / signal-backed service のどれかにする。乗り換え時はアダプタ層だけ差し替えればよく、UIは無改修で済む。

2026の選定軸

判断は4軸。①チーム規模（1〜2人はどれでも可、3人以上は event/state/view を唯一強制する BLoC）、②非同期密度（auth/feed/chat/billingのCRUDは Riverpod 3、ローカル状態中心のツール/エディタ/ゲームは signals か BLoC）、③厳格さ、④1年以内の採用計画。推奨は、個人×Firebase/Supabase は Riverpod 3、小チームSaaS は BLoC、個人×リアクティブツールは signals。Riverpod 3 の実務差分として、Provider/AsyncProvider/NotifierProvider が build_runner 無しで使え、family 引数は位置・インライン型付けへ、autoDispose が既定に変わった。テストは ProviderContainer で任意providerをfakeにoverrideできる。

移行見積もりと土台

目安として Provider→Riverpod3 は約1スプリント（ほぼ1:1）、BLoC→Riverpod3 は機能あたり約1スプリント（eventをAsyncNotifierのメソッドへ。BLoCの非同期グラフがボトルネック化したときだけ価値がある）、Riverpod↔signals は機械的だが小さな抽象層が要る。土台は feature-first＋go_router 17.x＋freezed3＋fvm pin、生成物（*.f.freezed.dart/*.g.dart）は手編集禁止で analysis_options.yaml から除外、monorepo の codegen は leaf から順次（並列は AssetNotFoundException の原因）。本番は 3.47.7 に pin しつつ別ジョブで beta 3.50 を検証する二本立てが基本線だ。

ひとことまとめ

性能差は中位Androidでしか効かない以上、状態管理は「速さ」より「規律と乗り換えやすさ」で選ぶ。抽象コントローラ1枚を挟むだけで、将来の判断ミスのコストが1スプリントに収まる——これが最大の保険だ。
