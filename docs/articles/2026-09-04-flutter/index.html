Flutter 3.47.1 / Dart 3.13.1 — webOS(スマートTV)公式SDKへ、ImpellerのAndroid移行完遂とWasmをWeb既定へ

現行安定版は Flutter 3.47.1 / Dart 3.13.1（年4回=2/5/8/11月）。2026ロードマップはプラットフォーム拡張が目玉で、GoogleがLGと協業しwebOS(スマートTV)向け公式SDKをH1目標。描画はImpellerのAndroid移行完遂、WebはWebAssemblyを既定コンパイルターゲットへ。状態管理は新規=Riverpod 3.3系、監査/大規模=Bloc 9.0という基本線。

この回のFlutterは“到達点の移行が仕上げに入る”話が中心だ。現行安定版は Flutter 3.47.1 / Dart 3.13.1、次の機能リリースは 2026年11月（年4回サイクル）。2026ロードマップの4本柱は Performance(Impeller)・Tooling/DX・Web/Accessibility・Stability に AI を加えた構成で、地味だが土台の総取り替えが進む。

何が新しい/重要か

プラットフォーム面の目玉は webOS(スマートTV)向け公式Flutter SDK。GoogleがLGと協業し 2026年前半（H1）リリース目標で、モバイル/デスクトップ/Webに続く新ターゲットになる。描画は Impeller の Android 移行完遂をコミット（既存の shader を build時にオフラインコンパイルして pipeline state を事前構築し、runtimeのshader compilation jankを排除）。独立ベンチでは複雑シーンの raster時間を約50%短縮、Skia比 約100MB少ないメモリで、mid-range Android でも複雑アニメを 120fps 維持と報告される。Webは WebAssembly を既定コンパイルターゲットへ（現状 --wasm フラグ必須、描画は最大2倍高速）。3.38 での WasmGC 統合ではベンチで 読込時間を最大約40%短縮。iOSプラグインは Swift Package Manager が既定へ移りつつある。

アーキテクチャ/状態管理の基本線

公式推奨は MVVM × Feature-First（機能ごとに Views／ViewModels／Repositories／Services の4層）。Riverpod と組むと AsyncNotifier／NotifierProvider で API・stream・loading/error を first-class に扱え、最小boilerplateでViewModelを書ける。選定は「新規＝Riverpod 3.3系（唯一のFlutter Favorite汎用状態管理・compile-time safety・大規模は @riverpod codegen 推奨）」「監査証跡が要る規制業界（fintech/healthcare）＝Bloc 9.0（event→state を厳格分離しaudit trail生成）」が基本線。パフォーマンスは“性能問題の約80%が不要なwidget rebuild”で、const 徹底・build分割・select/buildWhen で局所再描画。計測は必ず profile モードで DevTools（16ms=60fps／11ms=90fps）。

注意点・自分が試すなら

webOSはまだ目標段階なので本番採用は様子見。Impeller/Wasm はいずれも“既定化へ”の途上で、Webの --wasm は当面フラグ運用と割り切る。まず既存アプリを profile モードで測り、rebuild削減（const・select）から着手するのが費用対効果が高い。

まとめ：描画（Impeller）とWeb（Wasm）の“既定化”が仕上げに入り、新ターゲットのwebOSが加わる。土台の移行期こそ、計測とrebuild削減の基本を固めておきたい。
