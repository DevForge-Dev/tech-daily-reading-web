`authInterrupts` — App Routerで401/403を`notFound()`流に投げる（forbidden / unauthorized）

401/403を"投げて最寄り境界で描く"宣言的モデル。実験的で本番非推奨だが、DAL中心の多層防御と相性がよく、CVE-2026-44575の教訓とも噛み合う。

📅 2026年10月9日 ⏱ 約3分 🔗 出典 4 件

背景。App Routerの認証/認可は長く「middlewareでリダイレクト」か「各ページで手書きガード→redirect('/login')」の2択で、正しいHTTPステータス(401/403)とは結びついていなかった。実験的API authInterrupts は、ここにnotFound()流の宣言的モデルを持ち込む。

何が新しいか。next.config.tsでexperimental.authInterrupts: trueを立てると、next/navigationのunauthorized()（401）とforbidden()（403）が使える。前者は未ログイン＝「誰か分からない」、後者は権限不足＝「誰か分かるが禁止」に対応し、最寄りのunauthorized.tsx/forbidden.tsxを描画する。redirect()と違いURLは変わらず、サーバー側でその場でレンダリングを停止する。導入はv15.1.0、ただしv16.4.0時点でも"not recommended for production"のまま。

仕組みのポイント。認可チェックはエッジではなくデータを読む場所（DAL）に寄せるのが要。returnは不要（戻り値型はneverで即throw）、await必須、そしてtry/catchで囲むとインターセプトを握りつぶす（必要時はunstable_rethrow()で再throw）。root layoutからは呼べない。

// app/admin/page.tsx
const s = await verifySession()
if (s?.role !== 'admin') forbidden()  // 403 を throw、forbidden.tsx を描画

タイムリーな理由と落とし穴。2026年5月のCVE-2026-44575（CVSS 7.5 High）は「middleware/proxyの照合だけに認可を頼ると、細工した.rscやprefetch URLで保護ページに到達できる」というバイパス（修正15.5.16/16.2.5）。forbidden()をDALで呼ぶ設計はその裏付けになる。もう一つの罠はステータスの機微で、<Suspense>のストリーミング開始後に呼ぶとシェルは送出済みのためステータスは200のまま中身だけ差し替わる。厳密な403が要るなら判定をストリーミング前かProxy(旧middleware)に置く。まとめ：宣言的で書き味はよいが、実験的フラグ・本番非推奨・200問題の3点を踏まえて段階導入したい。
