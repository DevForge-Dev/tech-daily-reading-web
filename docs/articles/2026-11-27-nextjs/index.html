Next.js 16 の next/image 変更点 — priority 非推奨・qualities 既定[75]・キャッシュ4時間で、移行が“静かに”壊れる所と直し方

next/image は LCP/CLS を最も左右する定番だが、Next.js 16 で既定値とAPIが複数変わり、15以前からの移行で静かに壊れる。priority が非推奨→preload、画質は images.qualities が既定[75]に制限、最適化画像の最小キャッシュが60秒→4時間、images.domains は remotePatterns へ、私設IP最適化は既定ブロック……。LCP悪化・画質劣化・400エラーを避ける要点を、next.config の明示設定とコードで押さえる。

next/image は LCP と CLS を最も左右する定番コンポーネントだが、Next.js 16 で既定値と API が複数変わり、15 以前からの移行で“静かに”壊れる。アップグレードした瞬間に LCP 悪化・画質劣化・400 エラーを踏まないよう、変更点と直し方を押さえる。

何が変わったか（破壊的変更が中心）

要点は5つ。① priority が非推奨になり、確実な LCP 画像は preload に置き換える（遅延読み込みだけ切るなら loading="eager"）。② images.qualities の既定が [75] のみに制限され、配列外の quality は最も近い値へ丸められ、/_next/image?q=… に許可外の値を直接投げると 400。③ 最適化画像の最小キャッシュが 60 秒→4 時間（14400 秒）に延長。④ images.domains が非推奨で remotePatterns へ。⑤ 私設 IP 宛の最適化がセキュリティ既定でブロック（dangerouslyAllowLocalIP で限定解放）。ほかに imageSizes から 16 が削除、maximumRedirects 既定 3、クエリ付きローカル画像は localPatterns 必須、など広く効く。

仕組みのポイントと直し方

共通の対策は「既定に任せず next.config で明示する」こと。使う画質は qualities に、外部ホストは remotePatterns に、差し替え頻度が高い画像があるなら minimumCacheTTL: 60 で旧挙動へ戻す。priority は全置換し、確実な LCP 画像だけ preload にする。移行は npx @next/codemod@canary upgrade latest が Turbopack 設定や next lint→ESLint 等をまとめて移すが、画像専用コードモッドは無いので、上記の既定変更は手動対応になる。

コードの要点

// next.config.ts
images: {
  qualities: [50, 75, 100],   // 既定は[75]のみ。使う値は明示する
  minimumCacheTTL: 60,        // 既定14400(4h)を旧60sへ戻す例
  formats: ['image/avif', 'image/webp'],
  remotePatterns: [
    { protocol: 'https', hostname: 'images.example.com', pathname: '/uploads/**', search: '' },
  ],
}
// LCPヒーロー: priority ではなく preload
<Image src={hero} alt="製品のヒーロー" fill sizes="100vw" placeholder="blur" preload />

落とし穴・ひとこと

踏みやすいのは「80 など特定品質を明示せず使い続けて 400」と「キャッシュが4時間に延びて画像差し替えが反映されない」の2つ。fill は親に position: relative が必須で、sizes 無しは 100vw 扱いで過大画像を取得しがち、という点は従来どおり。普遍則として width/height（または fill）でアスペクト比を予約して CLS を防ぐのは不変だ。アップグレードは画像の既定変更だけ手で潰す——これを押さえれば移行の“静かな事故”はほぼ消える。
