版は4日連続“据え置き”の静かな日 — だから拾う AnimatedList（要素の増減そのものをアニメする標準 widget）と、mobx 2.7.0 の細粒度リアクティブ

stable 3.50.1／beta 3.51.0-0.2.pre は動かず、次の節目は 3.51.0 の beta→stable 昇格待ち。版が静かな日こそ、挿入/削除をアニメする AnimatedList の設計と、観測したものだけ再描画する mobx を読む。

📅 2026年11月24日 ⏱ 約5分 🔗 出典 4 件

リリース面は4日連続で版の動きなし。stable は 3.50.1（Dart 3.14.0・11/20 の hotfix 一本）、beta は 3.51.0-0.2.pre（Dart 3.15.0）で据え置き、dev=main のエントリ日付だけが 11/23 に前進した。3.50 系は約2週間“安定運用フェーズ”に入っており、次の節目は 3.51.0 の beta→stable 昇格。公称ケイデンス（四半期ごと・最低4 stable/12 beta）からすると 3.51.0 stable は次四半期の枠で、今日時点で緊急の上げ替え要因はない。実務の結論は「プロダクションは stable 3.50.1 を pin、検証ジョブは別途 beta で緑化」。版が静かな日は、widget とアーキテクチャの地力を足す好機だ。

というわけで本日の主役は AnimatedList。公式の定義は「A scrolling container that animates items when they are inserted or removed.」で、ListView.builder に似たスクロールコンテナに「項目の挿入／削除をアニメーションする API」を足したもの。尺を固定して 0→1 補間する明示トランジションや lottie/Rive の素材再生とは違い、データ配列の増減そのものをアニメ対象にするのが特徴だ。

状態の掴み方は2通り。widget の key: に GlobalKey<AnimatedListState> を渡して listKey.currentState!.insertItem(...) と叩くか、item builder 内から AnimatedList.of(context)（null 許容版 maybeOf）で AnimatedListState を取得する。初期件数は initialItemCount（既定0）。widget は件数を自前で持たないため、鉄則は「自分のデータ配列の更新と insertItem/removeItem 呼び出しをペアで行う」こと。ここを片方だけにするとリストがずれる。

itemBuilder の型は Widget Function(BuildContext, int index, Animation<double> animation) で、第3引数の animation（0→1）を FadeTransition/SizeTransition に流して入場を描く。削除時は AnimatedRemovedItemBuilder に逆再生（1→0）された animation が渡る——消える瞬間の見た目を“削除ビルダ”として別途用意する必要がある（削除後も一瞬描くため）。仲間として sliver 版 SliverAnimatedList、グリッド版 AnimatedGrid/SliverAnimatedGrid、区切り線つきの AnimatedList.separated も揃う。

アーキテクチャ枠では mobx 2.7.0（vyuh.tech・MIT・Flutter Favorite）が俎上に。Observables／Actions／Reactions の三要素で状態をリアクティブに管理する TFRP（透過的関数型リアクティブ）で、標語は「What can be derived, should be derived. Automatically.」。Observable を変える正道は Action（最も外側の action 完了時にだけ observer を発火）、追跡した observable が変わると Reaction（autorun/reaction/when）が再実行、UI は flutter_mobx の Observer(builder: ...) が「builder 内で読んだ observable」の変化だけで再描画する。Store は @observable/@computed/@action 注釈＋build_runner の codegen で組む。Riverpod/Bloc が「provider/状態オブジェクト単位」で再構築するのに対し、mobx は読んだ reaction/Observer だけを動かす細粒度更新で、11/20 に見た signals と同系統だがデコレータ記法に馴染むチーム向けの老舗ラインだ。

性能枠は DevTools の Performance view。UI jank をフレーム単位で診断するビューで、1フレーム＝UI スレッドと raster スレッドの2本のバーで描かれ、16ms を超えたフレームは赤オーバーレイ、シェーダコンパイルを含むフレームは dark red で示される。必ず profile モードで計測（debug の数値は当てにならない）。遅いフレームを選ぶと Frame analysis が高コスト操作を自動指摘し、Enhance tracing の Track Widget Builds/Layouts/Paints で原因を build/layout/paint に切り分けられる。Render Clip/Opacity/Physical Shape レイヤを個別に OFF にして raster time が大きく下がれば、クリップ／半透明／影の使い過ぎが jank 要因、と当たりを付けられる。

自分が試すなら：ToDo やチャットのリストを AnimatedList に替え、追加時フェード＋削除時スライドの“ペア実装”を体に入れる。状態は mobx の Observer で包み、ジャンクが出たら Performance view を profile モードで開く——この3つは今日の素材がちょうど一本の線でつながる。ひとことまとめ：版が止まった日は、widget・状態管理・計測の“守り”を一段上げておくと、昇格後の 3.51.0 検証がぐっと楽になる。
