serverless Next.js のバックグラウンド処理 — after() の限界を越えて「定期実行／キュー／多段durable」を3層で使い分ける

「決済後にメール」「動画トランスコード」「毎朝レポート」を、リクエスト応答の外で確実に走らせたい。サーバーレスは常駐できないので、ジョブ実行を外部に委ね Next.js は呼ばれるエンドポイントに徹する。Vercel Cron／Upstash QStash／Inngest の3層を下から積む。

📅 2026年11月15日 ⏱ 約3分 🔗 出典 3 件

App Router の主戦場であるサーバーレス関数は「リクエストが来たら起動し、応答を返したら即終了」。常駐プロセス・ワーカー・インメモリキューを持てない（setInterval もスケール跨ぎで消える）。2026の定石は、ジョブ実行を外部サービスに委ね、Next.js 側は Route Handler として"呼ばれる"だけにすることだ。

なぜ after() ではダメか

after() は応答ストリーム完了後に副作用を走らせられ、PPR/Cache Components を壊さない点は優秀。だが永続性なし・自動リトライなし・DLQなしで、実行時間も maxDuration に縛られる＝落ちたら消える fire-and-forget。ロギングや分析の「ブロックしない副作用」専用で、必ず完了させたいジョブには不適だ。原則は「スケジュールとジョブ状態は外部の永続基盤に持たせ、Next.js は冪等な実行エンドポイントに徹する」。

① Vercel Cron（＝定期HTTP ping）

リポジトリ root の vercel.json に crons を書き、その path の Route Handler が GET を export するだけ。Vercel が時刻になると本番デプロイのURLをGETで叩く（preview/ローカルでは発火しない）。公開URLなので CRON_SECRET を Authorization: Bearer で検証し不一致は401に。最重要の制限はリトライなし・ベストエフォート（取りこぼし/二重発火あり）・同時実行制御なし。Hobby は1日1回±59分、Pro は毎分。キューではないので、重い処理は②③へ逃がす。

② Upstash QStash（＝"あなたのURLを呼ぶ"HTTPキュー）

デプロイするワーカー不要。publishJSON({ url, body }) で登録すると、QStash が指定URLへ POST し失敗で自動リトライする。受け手は verifySignatureAppRouter(handler) でラップするだけ（QSTASH_CURRENT/NEXT_SIGNING_KEY を自動参照＝鍵ローテ用に2本）。リトライ・指数バックオフ・DLQ・遅延・1分粒度のcron・flow control（下流への秒間レート/並列制御）まで揃う。配信は at-least-once なので受け手は必ず冪等に。

③ Inngest（＝durableなステップ実行）

関数を step の列として書くと各 step.run がチェックポイント化され、途中失敗時は完了済みstepはキャッシュ再生し失敗stepだけ再実行。app/api/inngest/route.ts で serve({ client, functions })、トリガは { event } か { cron }。step.sleep("wait","3d") で「3日後にリマインド」が1関数で書ける。多段・分岐・待機・fan-out の確実なワークフロー向け。

注意点と使い分け

共通の落とし穴は非冪等な受け手（二重課金・多重メール）、署名/秘密の検証漏れ、trailingSlash のリダイレクトでcronが無言失敗、CRON_SECRET 変更を再デプロイせず無効のまま、など。各ライブラリ（@upstash/qstash・inngest）はAPI変化が速いのでバージョン固定を。まず Cron で足りるか→足りなければ QStash→ワークフロー性が要れば Inngest、と下から上げるのが無駄がない。完了後は revalidateTag で画面に反映する。
