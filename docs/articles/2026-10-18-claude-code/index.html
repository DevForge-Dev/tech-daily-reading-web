Code Review GA と Idle圧縮、そして『コードは増えてもソフトは増えない』 — レビュー律速時代のClaude Code

日曜で新リリースはなし（最新 v2.1.302）。代わりに公式の二枚看板 Code Review のGA化と Idle compaction を押さえ、10/17の『産出増がデリバリー増に直結しない』という冷静な論考まで通して読む。

📅 2026年10月18日 ⏱ 約4分 🔗 出典 3 件

本日10/18(日)は新規のバージョンリリースがなく（最新は10/16の v2.1.302）、公式枠は 10/15にGA化したCode Review と、最近のchangelogで整備された Idle compaction（アイドル圧縮） の二つ。あわせて10/17に出た「コーディングエージェントはより多くのコードを生むがより多くのソフトウェアは生まない」という論考を読むと、機能追加の方向性がきれいに一本の線でつながる。要するに、生成はもう十分速い。詰まっているのはレビューと運用コストのほうだ、という話である。

Code Review が GA に — ルールは base ブランチの REVIEW.md から読む

Claude Code の Code Review がリサーチプレビューから一般提供（GA）へ移り、Claude Team / Enterprise で使えるようになった。レビュー時間はプレビュー期の約20分から 6〜10分に短縮され、管理者はリポジトリ単位で Quick / Standard / Deep の深度を選べる。設計上もっとも重要なのは、判定ルールを書いた REVIEW.md を PR自身の変更ではなく PR の base（デフォルト）ブランチから読む点だ。つまり PR 側でルールをこっそり緩めることはできず、新しいルールは先にマージして初めて効く。「エージェント標準は、PRが書き換えられない場所に置く」という原則の実装で、CODEOWNERS で所有者を固めるのと相性がいい。

Idle compaction — 長時間放置のキャッシュ失効を先回りで潰す

もう一つの地味だが効く変更が Idle compaction（v2.1.299〜302 で整備）。200Kトークンを超え、約54分アイドルになった会話を、1時間のプロンプトキャッシュが失効する前に自動で圧縮する。放置して戻ってきたときのキャッシュミスと、それに伴うコスト増・レイテンシを避けるのが狙いだ。閾値は CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS で調整でき、settings.json に "idleCompaction": false を書けば無効化、v2.1.302 では /config にON/OFFトグルも追加された。

『コードは増えてもソフトは増えない』 — ボトルネックはレビュー

10/17の論考は、この二つの機能がなぜ重要かを数字で裏打ちする。Chen & Stratton のデータ（2021〜2026/3、700社超・70万人超・約3億件のイベント）では、エージェント導入後に総行数+30%・コミット+20%・PR+23%と産出は大きく伸びた。ところが PR提出〜マージのレビュー時間は+49%、変更要求付きPRの割合はほぼ倍増し、肝心の Issue/Epic の解決には統計的に有意な変化がなかった。産出の増加はレビューに吸収され、デリバリーには届いていない。しかも約95%の企業が導入済みなのに、エージェントが触れているのはレビューコメントの約23%・PRの約11%どまりだ。

自分が運用で効かせるなら

やることは明快だ。まず REVIEW.md を base ブランチに置き、CODEOWNERS でレビュー所有者を固めて「ルールを後からPRで緩められない」状態を作る。Code Review は Team/Enterprise 限定なので、個人運用では GitHub 側のレビューゲート（必須レビュー・ブランチ保護）で同じ思想を代替する。Idle compaction はデフォルトONのまま長い調査セッションに効かせ、どうしても文脈を失いたくない重要セッションだけ /compact で「残すべき設計・テスト情報」を明示してから圧縮させる。そして計測軸はコード量ではなくデリバリー（解決したIssue/Epic、障害、ロールバック）に寄せる。

落とし穴とまとめ

注意点は二つ。REVIEW.md はbase読みゆえルール変更に先行マージのリードタイムが要る——急いで基準を変えたいときに一手遅れる。Idle compaction は便利な半面圧縮で文脈が削れるので、長丁場の設計会話では失ってはいけない前提を先に書き留めておくこと。結局この日の三題が指すのは同じ結論だ——生成を増やす前に、レビューと運用コストの処理能力を広げよ。速く書けること自体は、もう差別化要因ではない。
