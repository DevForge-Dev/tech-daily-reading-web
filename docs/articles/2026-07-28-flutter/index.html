Impeller 全プラットフォーム既定と 120fps 時代のフレーム予算 — 8.3ms をどう守るか

2026 の Flutter は Impeller がもはや experimental でなく iOS＋モダン Android の既定。120Hz が主流化し 1フレームの予算は 8.3ms まで縮む。予測可能なフレーム予算を活かす鍵は、不要な rebuild の撲滅と layout パス誤誘発の回避だ。

📅 2026年7月28日 ⏱ 約3分 🔗 出典 4 件

なぜ今これが話題か

フラッグシップ端末の 90/120Hz 化で、ユーザーが期待する「滑らかさ」の基準が 60fps から 120fps「ProMotion」へ上がった。同時に描画エンジン Impeller が iOS＋モダン Android（API 29+）の既定になり、シェーダーをビルド時に事前コンパイルすることで初回シェーダージャンクを排除、予測可能なフレーム予算を提供するようになった。2026 ロードマップは Android の Impeller 移行完遂（legacy Skia backend 撤去）を掲げる。

何が新しいか

安定版は Flutter 3.44.0（2026-05-18・Google I/O 2026）/ Dart 3.12、次の機能リリースは 2026年8月。トピックは Material・Cupertino ライブラリのパッケージ分離で、デザイン更新が四半期 SDK を待たず pub.dev から届く体制へ移り、M3 Expressive 等が独立 cadence で出荷される。状態管理は新規なら Riverpod 3.3.1 ＋ code generation が既定（compile-time safety・context-free read・first-class async）、監査証跡が要る fintech/healthcare は Bloc 9.0 という住み分けが定着した。

フレーム予算の守り方

要は上の窓（120fps なら 8.3ms）に毎フレーム収めること。基本は不要な rebuild の撲滅で、const の徹底、build の分割、最小スライスの watch、RepaintBoundary の戦略配置が効く。アニメで jank が出たら、純グラフィック変換のつもりがlayout パスを誤って誘発していないかを疑い、合成可能な Transform/Opacity へ寄せる。UI モーションの約80%（hover・state 遷移・レイアウト変化）は implicit（AnimatedSize 等）で十分で、複雑な choreography や physics のときだけ explicit を残す。

自分が試すなら

計測は必ず profile モードで行い、DevTools の flame chart で jank を起こす関数を特定する。widget inspector の persistent selection で、想定外に rebuild されている部分を洗い出したい。saveLayer を誘発する nested Opacity・複雑な clip・重複する影は優先的に潰す対象だ。

注意点

Dart 3.12 の primary constructors はまだ experimental で構文が変わり得るため本番は様子見。フレーム予算の数字（16/11/8.3ms）はあくまで上限で、OS やプラットフォームのオーバーヘッドを差し引くと実効はさらに短い。「60fps 出ているから十分」ではなく、ターゲット端末のリフレッシュレートで測るのが前提になった。

ひとことまとめ

Impeller が既定になったことで土台のジャンクは減ったが、120fps 時代はアプリ側の rebuild と layout の作法が体感を左右する。8.3ms を意識した設計と profile モード計測を習慣にするのが 2026 の基本線だ。
