Next.js 16のキャッシュ無効化 — updateTag / revalidateTag(tag,'max') / revalidatePath の住み分け

「デフォルト動的＋明示キャッシュ」への転換で次に効くのが無効化の設計。16では revalidateTag の単一引数が非推奨になりSWR化、Server Action専用の新API updateTag が read-your-own-writes を担う。呼ぶ場所と鮮度要件で3つを意図的に選ぶ。

📅 2026年8月16日 ⏱ 約3分 🔗 出典 3 件

背景。Next.js 16 は「デフォルト動的＋明示キャッシュ（use cache / Cache Components）」へ転換した。すると必ずぶつかるのが「キャッシュした値をいつ・どう捨てるか」＝オンデマンド再検証だ。従来の revalidatePath / revalidateTag に加え、16では仕様変更が2つ入り、選択を誤ると「投稿したのに一覧に出ない」という定番バグに直結する。

何が新しいか。ひとつは revalidateTag(tag) の単一引数が非推奨になり、第2引数 profile（'max' 推奨）が要るうえ意味論が即時失効→SWR（古い値を出しつつ裏で更新）へ変わった。もうひとつが新API updateTag（Server Action専用）で、即時失効＋次の読み取りは新データを待つ＝自分の書き込みを確実に見せる read-your-own-writes 専用だ。

仕組みのポイント。revalidateTag(tag,'max') はstaleの印を付けるだけで、そのタグを使うページが次に訪問された時に初めて再取得が走る（一斉再生成はしない）。対して updateTag はその場で失効させ次の読み取りが新データを待つ。前提としてタグ付けが必須で、use cache 関数内の cacheTag('posts') か fetch(url,{next:{tags:['posts']}}) で付ける。revalidatePath は動的セグメントなら type（'page'|'layout'）必須、rewrites は宛先パスを渡す。

'use server'
import { updateTag } from 'next/cache'
export async function createPost(data){
  const post = await db.post.create({ data })
  updateTag('posts')            // 一覧を即時失効
  updateTag('post-' + post.id)  // 詳細も
}

自分が試すなら、フォーム送信直後に自分の投稿が必ず見える経路は updateTag、ブログ/カタログなど「多少古くてOK」は revalidateTag(tag,'max')、外部Webhookは Route Handler で revalidateTag(tag,'max')（即時が要る時のみ {expire:0}）と割り当て、体感の待ち時間差を測りたい。

注意点。updateTag はRoute Handler / Client / Proxy では呼べない（Server Action専用）。マルチインスタンスでは無効化が既定でローカルなので、共有 cache handler の updateTags/refreshTags が無いと他インスタンスは古いまま（refreshTags は必ず try/catch）。「呼んだのに変わらない」の多くはタグ未付与かSWRの誤解だ。

ひとことまとめ：16の無効化は「待ってでも自分の変更を＝updateTag」「速さ優先＝revalidateTag(tag,'max')」「ページ単位＝revalidatePath」を意図的に選ぶ設計。タグ付けが全ての土台になる。
