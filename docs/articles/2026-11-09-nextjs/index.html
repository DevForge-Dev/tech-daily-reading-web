Stripe決済をApp Routerで — 署名検証はreq.text()、履行の真実はWebhook

App Router特有の決済ハマリは2つ。Webhookは生ボディが要る／履行はsuccess_urlでなくWebhookで。冪等性まで含めて型にする。

📅 2026年11月9日 ⏱ 約3分 🔗 出典 3 件

SaaS/EC を作れば必ず通る決済。Stripe は 2026 でもデファクトだが、App Router 特有のハマりどころが2つある。どちらも「ローカルでは動くのに本番で課金されない／署名エラー地獄」に直結するので、最初に型を押さえておきたい。

落とし穴①：Webhook は生ボディが要る

署名検証は受信したバイト列そのものに対して行う。req.json() で一度パースすると列が変わり検証が必ず失敗する。App Router の Route Handler では const body = await req.text() で生ボディを直接取れる（Pages Router の bodyParser:false 設定は不要＝App Router では消える定番ハマり）。検証は stripe.webhooks.constructEvent(body, sig, secret)、失敗は 400 を返す。Edge ランタイムは Node crypto が無いので await stripe.webhooks.constructEventAsync(body, sig, secret, undefined, Stripe.createSubtleCryptoProvider())（Web Crypto 版）を使う。

落とし穴②：履行の“真実”は success_url ではなく Webhook

成功ページ URL は未払いのユーザーでも直接叩けるため、在庫確定・権限付与・メール送信といった履行は必ず checkout.session.completed Webhook で行う。success_url は表示だけに使う。Checkout 自体は Server Action で価格をサーバー確定 → sessions.create → redirect(session.url) の数行で済む（redirect() は内部で例外を投げるので try/catch の外で呼ぶ）。金額・通貨はクライアント送信値を信じず、price ID か DB でサーバーが決める。

冪等性を忘れない

Stripe は 2xx を受け取るまで最大72時間・指数バックオフでリトライ＝同一イベントが複数回届く前提だ。event.id を一意制約付きで記録し、既処理ならスキップする。署名 OK ならなるべく早く 2xx を返し、重い履行は after() やジョブキューへ逃がして応答をブロックしない。握り潰して 200 を返すとイベントは永久に失われるので、確実に失敗してリトライさせたい時だけ 5xx を返す。Webhook は公開エンドポイント＝署名検証が唯一の認証で、proxy 側の認可には頼れない点も要注意。

ひとことまとめ

「生ボディで署名検証」「履行は Webhook だけ」「event.id で冪等」。この3点を型にすれば、App Router の決済は数十行で安全に組める。
