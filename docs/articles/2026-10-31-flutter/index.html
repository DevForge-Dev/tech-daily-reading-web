10/31のFlutter — Androidの既定ページ遷移がPredictiveBackに。予測型バックの覗き見とPopScope移行、テスト尺破壊への備え

stable 3.47.9 / beta 3.50.0-0.3.pre(10/29)。Androidの既定遷移がPredictiveBackPageTransitionsBuilderへ変わり遷移が300→450msに。WillPopScopeはPopScopeへ。あわせてVGVのFeature-First Clean ArchitectureとBackdropFilterの重さ対策も押さえる。

📅 2026年10月31日 ⏱ 約4分 🔗 出典 4 件

背景。現況は stable 3.47.9 / Dart 3.13.7、beta 3.50.0-0.3.pre / Dart 3.14.0(ともに10/29更新)。3.50-candidate.0(10/6 cutoff済)の上で、11月のstable昇格前に承認済みcherry-pickを重ねる最終安定化フェーズで、昇格直前の変更は新機能でなく回帰修正が主だ。11月の3.50確定事項(Web WasmGC既定・Android Impeller一本化・Wasm遅延ロードstable・Android17 day-zero・material_ui/cupertino_uiのdeprecation)は不変。本番は3.47.9にpinしつつ別CIでbeta 3.50系を緑化しておくのが定石だ。

何が重要か＝既定の戻る体験が変わった。Androidの既定ページ遷移が ZoomPageTransitionsBuilder から PredictiveBackPageTransitionsBuilder に変更済み(stable 3.38.0から)。予測型バック(predictive back)は、戻るジェスチャの途中で前の画面/アプリを“覗き見”し、そのまま離せば遷移確定・指を戻せばキャンセルして元に復帰する Android 機能で、遷移がジェスチャの進捗に連動して動く。有効化は AndroidManifest.xml の <application> に android:enableOnBackInvokedCallback="true"(Android13は要opt-in・14+は既定で有効)。ジェスチャが無い通常遷移では FadeForwardsPageTransitionsBuilder にフォールバックする。

仕組みと落とし穴。既定遷移が変わった結果、遷移時間が 300ms → 450ms に増加した。tester.pump(const Duration(milliseconds: 300)) のように尺をハードコードしたwidgetテストが壊れ得る——対策は TransitionDurationObserver を navigatorObservers に挿し、observer.pumpPastTransition(tester) や observer.transitionDuration ~/ 2 で尺非依存に書き換えること。戻る制御は WillPopScope が deprecated で PopScope へ移行する:canPop: false ＋ onPopInvokedWithResult: (bool didPop, Object? result) で確認ダイアログを挟むが、コールバックは成功pop後にも発火するので if (didPop) return; ガードが必須、ダイアログ待ちの間にwidgetが破棄され得るので context.mounted チェックも要る。旧挙動に固定したければ pageTransitionsTheme で ZoomPageTransitionsBuilder() を明示指定する(ただし予測型バックは使えなくなる)。

この日の他の収穫。アーキテクチャは Very Good Ventures の Feature-First Clean Architecture が示唆に富む:機能ごとに <feature>_domain/_data/_presentation の3パッケージに分け、層をパッケージ境界にすることで import違反をコンパイル時に弾く(domainは純Dart・presentationはdataに依存不可、機能跨ぎはdomainレベルだけ、Dart workspacesがリンク)。機能同士はルートをimportせず、Module widgetが型付きコールバックを公開しapp層が結線する。パフォーマンスでは BackdropFilter のぼかしが重い理由(背後キャンバスをキャプチャ→フィルタ→合成に saveLayer のオフスクリーンバッファが要り毎フレーム確保が走る)と、段階ぼかし(帯に分け ClipRect＋sigmaをindexで増やす、推奨8〜12ステップ・maxSigma15前後)という回避策が実務的だ。

自分が試すなら、まず既存アプリで予測型バックを有効化し、尺ハードコードのテストを TransitionDurationObserver ベースへ直す。WillPopScope が残っていれば PopScope へ機械的に移行し、didPop ガードと context.mounted を入れる。注意点は、段階ぼかしの ClipRect は“どこに描くか”を絞るだけで各帯のフィルタ処理量自体は必ずしも減らないこと、blur系は Impeller と Skia でキャッシュ挙動が変わるので必ず --profile＋DevToolsで実測してから詰めること。
