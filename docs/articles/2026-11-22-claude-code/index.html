11/22は新バージョンなし — v2.1.330据え置きの日に読む、auto mode のサードパーティ解放と v2.1.330 の“無人運用に効く”修正群

npm latest は v2.1.330 据え置き（stable=v2.1.323）で、日曜の今日は新リリースのない日。そこで直近2〜3版をまとめて復習する。最大の変化は v2.1.328 の auto mode 拡大——Bedrock・Google Cloud Agent Platform・Microsoft Foundry・Claude apps gateway で Opus 4.6／Sonnet 4.6 が auto になり、権限モード未設定の対話は auto 開始に。v2.1.330 では Code Mode の10分タイムアウトや LSP、Remote Control、Bedrock まわりの不具合が静かに潰された。

📅 2026年11月22日 ⏱ 約6分 🔗 出典 4 件

日曜の今日は版が動かなかった。npm view @anthropic-ai/claude-code dist-tags を一次確認すると latest=v2.1.330（2026-11-20 19:16 UTC 公開）で前日から変化なし、stable=v2.1.323。新機能の発表がない日こそ、直近の“効いてくる変更”を棚卸しする好機だ。この数日の Claude Code を貫くテーマは一貫して「速く賢く」ではなく「無人・自律のセッションを安全に、第三者クラウド上でも回す」ことにある。

何が新しいか：auto mode が“自前の Anthropic 契約”を離れた

直近で最も影響が大きいのは v2.1.328（11/18）の auto mode のプロバイダ拡大だ。これまで auto mode（危険度の低い操作を自動承認し、確認プロンプトを減らすモード）は実質 Anthropic 直の API 前提だったが、Amazon Bedrock・Google Cloud の Agent Platform・Microsoft Foundry・Claude apps gateway 上の Opus 4.6／Sonnet 4.6 でも使えるようになった。しかも権限モードを明示指定しない対話セッションは auto mode で開始する。つまり社内が Bedrock や Vertex 経由でも、設定を変えずに確認プロンプトが減る——裏を返せば、今まで都度確認だった環境が“黙って自動承認”に変わり得るということだ。

仕組みのポイント：既定値が変わったら“明示設定”で握り直す

対策は単純で、確認を残したい環境は permissions.defaultMode を明示設定すること。既定に任せると auto で開始するのだから、重要な本番リポや破壊的操作を含む運用では defaultMode を default（都度確認）側に固定しておくのが安全だ。あわせて v2.1.328 では mcp_tool フックに "onFailure":"block" が加わり、command/HTTP フックと同じくフック呼び出しが失敗したらアクションをブロックできるようになった。MCP 登録では v2.1.327 の claude mcp add-json が、サーバー JSON を標準入力から読みトークンをコマンド履歴に残さない（ただし Claude Code セッション内からは実行不可）。遅延ツールの再開を止める CLAUDE_CODE_DISABLE_DEFERRED_TOOL_RESUME も入った。

v2.1.330 の“地味だが効く”修正：無人運用の実害を消す

今日据え置きの v2.1.330 自体は機能追加より修正が主役だ。GitHub の一次 CHANGELOG から拾うと、Code Mode は「権限プロンプト／プラン承認／質問が10分開いたままだとスクリプトが止まる」「前のスクリプト実行中に接続した MCP サーバーを呼べない」「トップレベル変数が未設定時に黙って undefined になる」を修正。LSP は言語サーバー起動中に複数の呼び出し／編集が来ると失敗する問題や Esc で止められない問題を修正。Remote Control／クラウドセッションは再接続不可セッションへの再試行表示やツール結果の欠落を、Bedrock（Mantle）はモデル未選択で始めた端末セッションがピン留めした Opus を無視する問題を直した。運用面では self-hosted runner の /metrics に「受注→登録受理まで」「初回セッション受け渡しまで」の秒数メトリクス2種が増え、/stats の日次集計が UTC からローカルTZに修正された。

実務での使いどころ・落とし穴

自分の定期タスク運用に引きつけると効くのは2点。ひとつは、第三者クラウド経由なら auto mode の既定化を前提に defaultMode を棚卸ししておくこと——「確認が出ると思っていた操作が自動承認されていた」を防ぐ。もうひとつは、Code Mode やスケジュール実行で長時間待つワークフローがあるなら v2.1.330 の10分タイムアウト修正が効くので、latest に追従しておく価値があること。注意点は v2.1.330 は latest であって stable（v2.1.323）ではないこと。安定重視なら stable を pin しつつ、検証機で latest を触る二段構えが無難だ。

事例：ゼロ設定展開と“7時間の自律コーディング”

事例も2本公開されている。Stripe は 1,370 人のエンジニアへ「ゼロ設定」で展開し（端末・開発環境にプリインストールし、ルール／トークン／認証情報を事前設定）、npm 依存チェーンを避けるため Anthropic と2〜3か月かけて署名済みエンタープライズ版バイナリを構築した。Rakuten は市場投入までを 79%短縮（24営業日→5日）、複雑なリファクタリングで7時間連続の自律コーディング（担当者いわく「その7時間、コードを一行も書かなかった」）、複雑なコード改変で 99.9% の数値精度を挙げる。いずれもベンダー公表・自己申告の数値で第三者検証ではない点は割り引いて読む。

ひとこと：新バージョンが無い日の要点は「既定が変わったら握り直す」。auto mode の解放は便利さと引き換えに“確認が消える”変更でもある。defaultMode を一度見直し、latest 追従で Code Mode / Remote Control の修正を取り込む——それが今日やる価値のある地味な一手だ。
