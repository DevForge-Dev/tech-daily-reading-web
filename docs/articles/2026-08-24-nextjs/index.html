App Routerのファイルアップロード三択 — Server Action / Route Handler / 署名付きURLの使い分け

「input type=file を Server Action に渡すだけ」で始めると、1MBのボディ制限・一時FS・進捗バーが出せない壁に順に当たる。Next.js 16 前提で、経路の三択と進捗・検証の勘所を整理する。

📅 2026年8月24日 ⏱ 約3分 🔗 出典 4 件

ファイルアップロードはほぼ全アプリで必要になるのに、App Routerではどの経路で受けるかという設計判断がまず難所になる。素朴に Server Action へ <input type="file"> を渡して始めると、1MBのボディ制限、サーバーレスの一時FS、進捗バーが出せない（fetchはupload progress非対応）という壁に順番にぶつかる。Next.js 16 前提で三択を切り分ける。

経路の三択（最初の設計判断）

(1) Server Action + formData：formData.get("file") を File として受ける最も簡単な経路。プログレッシブエンハンスメントが効き、書込後の revalidatePath/Tag まで一直線。ただしバイト列がサーバーのメモリに乗るので大きい/多数同時には不向き。(2) Route Handler（app/api/upload/route.ts）：Web標準の Request を直接扱い、巨大ファイルは request.body（ReadableStream）を busboy 等でストリーム処理。CORSやカスタムヘッダなどHTTP面が要る時に。(3) 署名付きURL（presigned URL）：サーバーが「1ファイル・短時間だけ有効」のPUT URLを発行し、ブラウザが直接S3へアップロードする。サーバーはバイトに一切触れないのでボディ制限やメモリを回避でき、数MB超のユーザー投稿はこれが本命。

三大落とし穴

ボディ1MB制限：Server Actionのボディは既定最大1MB。next.config の experimental.serverActions.bodySizeLimit で変更するが、これは生HTTPボディ全体（境界やメタ込み）なので上限ギリギリは10〜20KBの余白を見込む。数MB超は(2)(3)へ逃がすのが公式も推す定石。進捗バー：Fetch APIは upload progress を持たない。リアルタイム％を出せるのは実質 XMLHttpRequest の xhr.upload.onprogress だけで、loaded/total から％を算出する。一時FS：多くのホスティングで実行環境のFSは一時的（書けるのは /tmp のみ）。fs.writeFile("public/uploads/...") は本番で壊れるので、永続化はS3/R2/Blobへ。

検証とセキュリティ

アップロードは全部「信頼できない入力」。サイズはサーバーで再チェック、種別は file.type（詐称可能）でなくマジックバイトで判定、保存キーはUUID/ランダムにしてユーザー名をパスにしない（パストラバーサル/上書き回避）、画像は sharp で再エンコード、許可種別はホワイトリスト化。"use server" は認可を付けないので verifySession() とレート制限は各自で。

自分が試すなら・ひとこと

プロフィール画像や書類なら(3)署名付きURL＋XHR進捗で組み、ドロップゾーンは必ず本物の <input type="file"> を併設して role="status" で状態を言語化する。丸ごと面倒を見たいなら UploadThing、DnDは react-dropzone、Vercelなら @vercel/blob の put() が同思想のマネージド版。「小さいは(1)、制御は(2)、大きいは(3)」——サイズで経路を割り切るのが結局いちばん速い。
