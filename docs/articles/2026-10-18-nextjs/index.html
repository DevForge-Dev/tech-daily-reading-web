App Routerでページ遷移に『退場』を出す — template.tsxの限界、FrozenRouterハック、そして公式ViewTransitionへ

App Routerには router.events が無く、素直に AnimatePresence で包んでも exit が発火しない。なぜ動かないのか、template.tsx で何がどこまでできるのか、退場まで出す FrozenRouter の仕組み、そして公式推奨 <ViewTransition> への移行判断を一本に整理する。

📅 2026年10月18日 ⏱ 約5分 🔗 出典 4 件

「ページが滑らかに入れ替わる」演出は定番の依頼だが、App Router では罠だらけだ。Pages Router 時代は router.events（routeChangeStart 等）を購読し <AnimatePresence> でページ全体を包めば enter/exit が付いた。ところが App Router にはこの router.events が存在せず、ナビゲーションの「開始」をフックできない。しかも App Router は遷移時に古いページを先にアンマウント→新しいページをマウントするため、page.tsx を素直に包んでも退場（exit）が一切発火しない。ネット上の解法も「enterだけ動く」「exit中に新ページの中身が見えてしまう」など不完全なものが大半だ。

なぜ exit が出ないのか（根本原因）

<AnimatePresence> は自分の子が消えるのを検知して exit を走らせる。だから「消える要素より上」で生き残っていなければならない。page.tsx 内に置くと遷移でラッパーごと消え、検知役がいなくなる。では layout.tsx に置き子を key={pathname} で差し替えると——enter は出る。しかし App Router の子レンダリングは共有の LayoutRouterContext 経由で、遷移が確定した瞬間にこのコンテキストが新ルートの内容を指す。結果、退場中の motion.div の中身まで新ページに差し替わり、「新ページが一瞬見えてから消える」ガタつきになる。

FrozenRouter — 退場中だけコンテキストを凍結する

対策は、退場アニメーション中だけ古い LayoutRouterContext の値を使い続けること。useContext(LayoutRouterContext) で現在値を取り、useRef に前回値を保持しておき、セグメントが変わった瞬間（＝退場中）は前回値を <LayoutRouterContext.Provider> に流し込む。これで退場中の motion.div は古い中身を保ったまま exit できる。key を useSelectedLayoutSegment() にすればネストしたレイアウトのその階層のセグメントをキーにでき、特定の配下だけ別演出という局所適用が効く。ラッパーには <AnimatePresence mode="wait" initial={false}> を使い、旧ページの退場完了後に新ページを入場させて2枚重なりを防ぎ、初回ロードのちらつきも抑える。

template.tsx でできること／できないこと

template.tsx は layout.tsx と違い遷移ごとに新インスタンスを生成（＝毎回リマウント）する。おかげで入場だけなら key も AnimatePresence も不要で、initial→animate が毎遷移発火する最も手軽なフェードイン遷移になる。ただしexit は出せない——旧インスタンスは新インスタンスのマウント前に破棄されるため、退場を見せる相手がいない。覚え方は単純で、「入場のみ=template.tsx」「退場も要る=layout.tsx + AnimatePresence + FrozenRouter」だ。

公式の現在地と、自分が新規で組むなら

見逃せないのが公式の推奨変化だ。Next.js 16 + React 19.3 では import { ViewTransition } from 'react' が App Router で設定不要で動く（公式ガイド「Designing view transitions」2026-10更新）。JS量が小さく mount/unmount 管理が不要で、グリッドと詳細に同じ name を付けるだけで共有要素モーフが得られ、方向付けは <Link transitionTypes={['nav-forward']}> で与える。だから新規・長期運用でブラウザ要件がChromium中心ならこれを第一候補にする。既存の Motion 資産があり細かい制御が要る場合に限って FrozenRouter を採る、という順序が実務的だ。

落とし穴とまとめ

FrozenRouter 最大の弱点は、next/dist/shared/lib/app-router-context.shared-runtime という非公開の内部パスに依存する点。マイナー更新や Turbopack で予告なく壊れ、型も付かない（@ts-expect-error が要ることも）。これが <ViewTransition> 移行の強い動機になる。ほかにも mode="wait" は exit→enter を直列化して体感2倍遅くなるので duration は 0.2〜0.35s に抑える、Suspense fallback でスケルトンがマウントされ演出が崩れることがある、useReducedMotion() で位置移動（y/x スライド）を切り不透明度だけに落とす——あたりを押さえたい。まとめると、既存資産や局所制御は Motion+FrozenRouter、新規は公式 <ViewTransition>。内部API依存を背負うかどうかが分岐点だ。
