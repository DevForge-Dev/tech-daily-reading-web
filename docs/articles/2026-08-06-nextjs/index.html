instrumentation.ts で始める分散トレース — @vercel/otel・onRequestError・client計測の三点セット

instrumentation.ts は 15/16 で設定不要に。register() で OTel を初期化し、onRequestError でサーバー全エラーを一元捕捉、instrumentation-client.ts でハイドレーション前のクライアント計測。@vercel/otel なら数行・Edge 対応でプロバイダ非依存。

📅 2026年8月6日 ⏱ 約4分 🔗 出典 4 件

アプリが複雑になるほど「本番で何が遅い／何が壊れているか」を推測ではなくデータで掴む必要がある。Next.js は OpenTelemetry(OTel) を最初から自前で計装済みで、instrumentation.ts に数行書くだけでリクエスト→ルート描画→fetch→Route Handler までの分散トレースを任意のバックエンド（Datadog / Grafana / Sentry / Vercel Observability 等）へ送れる。肝はプロバイダ非依存＝コードを変えず送り先だけ差し替えられることだ。

何が新しいか。2025〜2026で三つ動いた。(1) instrumentation.ts が安定化し Next.js 15/16 では設定不要で自動検出（13/14 の experimental.instrumentationHook は不要に）。(2) onRequestError（15 導入）でサーバー側 throw を1箇所で捕捉でき、Sentry は Sentry.captureRequestError を代入するだけ。(3) instrumentation-client.ts（15.3 導入）で React ハイドレーション前にクライアント計測を初期化でき、onRouterTransitionStart で App Router のナビ開始も観測できる。

仕組みのポイント。register() は新サーバー起動時に一度だけ・リクエスト受付前に走るのでグローバル初期化に最適。全ランタイムで呼ばれるため、NodeSDK のような Node 専用コードは process.env.NEXT_RUNTIME === 'nodejs' でガードして動的 import する。Next.js は下図のようなデフォルト span を自動で吐く（NEXT_OTEL_VERBOSE=1 で詳細、NEXT_OTEL_FETCH_DISABLED=1 で fetch span 抑制）。

使いどころ。@vercel/otel なら registerOTel({ serviceName: 'next-app' }) の数行で exporter・span processor・fetch 計装まで自動構成でき、Edge ランタイムにも唯一対応する。エラー観測は多層で組むのが正解で、onRequestError（サーバー全エラーの計測ハブ）＋ error.tsx（UI 回復）＋ instrumentation-client.ts（クライアント計測）を併用する。

落とし穴。onRequestError はサーバー限定でクライアント例外は捕捉しない。instrumentation-client.ts は開発時に初期化が 16ms 超で warning が出るほど軽量前提で、同期のトップレベルコードだけがハイドレーション前完了を保証する（ポリフィルは静的 import ＋同期適用が鉄則）。カスタム span は finally で必ず span.end() しないとリークする。

ひとことまとめ。「3ファイル・プロバイダ非依存・多層エラー観測」。迷ったら @vercel/otel で始め、送り先だけ後で差し替えるのが最短だ。
