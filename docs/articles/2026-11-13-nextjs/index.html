Next.js — React Taint APIでサーバー機密のクライアント漏洩を描画時に止める（experimental）

取得オブジェクトをうっかりClientに渡すとRSCペイロードで機密が漏れる。Taint APIは参照/値を汚して描画時にthrowする最後の防壁。ただし参照でしか追えない落とし穴に注意。

📅 2026年11月13日 ⏱ 約4分 🔗 出典 4 件

App Router は Server Components 既定で、DB 行・環境変数・セッショントークンをサーバー側で自由に読める。便利な反面、「取得したオブジェクトをうっかりそのまま Client Component に props で渡す」と、機密フィールドが RSC ペイロード（ブラウザまで届くシリアライズ JSON）に載って漏洩する。React の Taint API は、この“うっかり漏洩”を描画時に Error で止める最後の防壁（backstop）だ。Next.js 16.2／2026 時点でも experimental（React experimental チャネル＋experimental.taint:true）で、本番導入は慎重に。

2つの API：参照を汚す / 値を汚す

どちらも Server Component 内でのみ使い、返り値は undefined。experimental_taintObjectReference(message, object) はオブジェクトの参照そのものに汚染マークを付け、その参照が未加工のまま Client へ渡ると message 付きで throw する。experimental_taintUniqueValue(message, lifetime, value) は特定の一意な値（string / bigint / TypedArray のみ）を汚染し、lifetime オブジェクトが生きている限りブロックし続ける。value は暗号トークンや秘密鍵のような高エントロピーな一意値に限ること。

最大の落とし穴は「参照でしか追えない」

Taint は参照の同一性で追跡するので、コピーすると未汚染になる。{...user} やフィールド抽出した新オブジェクトは追跡外だ。同様に派生値も追えない——toUpperCase()・文字列連結・base64・substring などで作った値は汚染が外れる。

// コピーは別オブジェクト（未汚染）
const copy = { ...user };            // taintObject(user) は効かない

// 派生値は追跡されない（未汚染で漏れる）
const label = "version::" + key;     // 新しい文字列＝汚染されず Client へ

さらに PIN・電話番号・boolean・短い数値などの低エントロピー値は汚染してはいけない。攻撃者がリクエストで全列挙して「どれが汚染値か」を当てられてしまうからだ。lifetime の設計も罠で、globalThis/process を渡すとアプリ生存期間中ずっと汚染、逆に lifetime なしで React 外のグローバルストアに置くと未汚染化する。

実装の勘所と、自分が試すなら

定石は DAL（Data Access Layer）でデータ取得直後に汚染し、import 'server-only' でモジュールごと Client import をビルドエラーにすること。環境変数の秘密は server-only＋taintUniqueValue(msg, process, process.env.API_PASSWORD) の併用が定番。自分で試すなら、まず next.config.ts に experimental:{ taint:true } を入れた検証ブランチを切り、既存 DAL の戻り値に taintObject を足して「丸ごと渡し」が本当に落ちるかをテストで確認する。

注意点・ひとことまとめ

公式は「taint API を唯一の防御にするな」と明言する。本線はあくまで「DAL が権限チェック→必要最小限の DTO だけ返す」設計で、SERVICE_API_KEY はそもそも戻り値から除くのが最善。Taint は、取得関数が制御外だったり RSC 描画中に機密へ触れる状況への“追加の保険”として重ねる層だと割り切る。experimental チャネルが入る副作用もあるので本番は慎重に。
