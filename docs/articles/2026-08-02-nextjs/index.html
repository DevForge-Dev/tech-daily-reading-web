App RouterのSEOはRSCで完結 — Metadata API・動的OG画像・ストリーミングメタデータ、metadataBaseとparams awaitが落とし穴

generateMetadataは人間には非ブロッキング／ボットにはブロッキングで配信されSEOを壊さない。opengraph-image.tsxで動的OG画像、sitemap.ts/robots.tsを型付きコード生成。Server Component専用でJSに依存せずクローラに強い。落とし穴はmetadataBase未設定とNext.js 16のparams await忘れ。

📅 2026年8月2日 ⏱ 約4分 🔗 出典 4 件

直近はアニメーション寄りが続いたので、今日は毎回必要になる“土台”テーマ——App RouterのSEO。ポイントは、Next.jsのSEOが<head>を手で書く時代を終わらせたこと。型付きのmetadataオブジェクトとgenerateMetadata関数、そしてopengraph-image・sitemap.ts・robots.tsといったファイル規約で、<head>とクローラ向けファイルをフレームワークが自動生成する。

何が新しい/重要か：2026年（Next.js 16）の勘所は3つ。第一にストリーミングメタデータ（15.2導入・16で標準）。async generateMetadataは人間のブラウザには非ブロッキング（UIを先に流し、解決後にmetadataを注入）、ボットにはブロッキング（初期HTMLの<head>に完全なタグを入れる）という二段構えで、体感速度とSEOを両立する。第二に動的OG画像——opengraph-image.tsxを置くだけでルートごとに1200×630の画像をImageResponse（next/og）がJSX+CSSから生成。第三にsitemap.ts/robots.tsのコード生成でDBと同期し、TypeScriptの型で構造ミスをビルド時に検出できる。

実装の型：ルートレイアウトでmetadataBaseとtitle.template／title.defaultを定義しておけば、子ページは短いタイトル文字列だけ返せば<title>CLI Reference | MySite</title>のように合成される。metadataとgenerateMetadataは同一ファイルで併用不可（どちらか一方）で、いずれもServer Component専用（'use client'からはエクスポート不可）。だからSEOはJSに依存しないRSCの世界で完結し、クローラに強い。

// app/blog/[slug]/page.tsx（Next.js 16）
export async function generateMetadata(
  { params }: { params: Promise<{ slug: string }> }
): Promise<Metadata> {
  const { slug } = await params        // ← 16は await 必須
  const post = await getPost(slug)      // ← react cache() で page と共有
  return { title: post.title, alternates: { canonical: `/blog/${slug}` } }
}

自分が試すなら：新規App Routerでは、まずapp/layout.tsxにmetadataBase: new URL('https://…')・title.template・OGのデフォルトを入れる。動的ルートにはopengraph-image.tsx（display:flex必須・grid不可）とsitemap.tsを置き、記事/商品ページはJSON-LDをRSCで出力してリッチリザルトを狙う。generateMetadataとpageが同じデータを使うならReact cache()で二重フェッチを排除。注意点：metadataBase未設定だと開発はlocalhost、本番はVERCEL_URLにフォールバックしてOG画像URLが壊れる。paramsのawait忘れは16で即エラー。ひとことまとめ：SEOはRSCで完結する領域。metadataBaseとparams awaitさえ外さなければ、ボット最適な<head>が自動で手に入る。
