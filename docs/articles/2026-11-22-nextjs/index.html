Next.js 16.3 の Partial Prefetching — 「全ページ or loading.tsx」の二択を終わらせ、App Shell だけを先読みする

積年の弱点だった「動的ルートは既定でプリフェッチされず遷移が遅い」を、16.3 の Instant Navigations が作り直した。中核の Partial Prefetching は、どのルートからも再利用可能な App Shell を抽出し、リンクごとに“どこまで先読みするか”を選べる。cacheComponents と partialPrefetching の両方を有効化するのが条件で、use cache が Next.js に初めてクライアント側キャッシュをもたらす。

ナビゲーションの体感速度（perceived performance）は、長らく「loading.tsx による再利用可能なローディングシェル」か「<Link prefetch={true}> による全ページ丸ごとのプリフェッチ」の二択で設計されてきた。とりわけ cookies()／searchParams を読む動的ルートは既定でプリフェッチされず、クリックしてからサーバー往復が走るため“もっさり”する——これが積年の弱点だった。Next.js 16.3（リリースポスト 2026年8月3日）の Instant Navigations はここを作り直し、その中核が Partial Prefetching（部分プリフェッチ）だ。

何が新しいか：App Shell という第三の粒度

16.3 は、どのルートの UI からでも再利用可能な App Shell（ローディングシェル）を抽出し、リンクごとに「ターゲットページのどこまでをプリフェッチするか」を選べるようにした。<Link> の prefetch は boolean | "auto" | null を取り、既定は "auto"。Partial Prefetching 有効時、"auto" はそのルートの App Shell だけを先読みし、URL 固有（params／searchParams）のコンテンツは遷移後に解決する。true は App Shell に加えてそのリンクの URL データに依存するキャッシュ済みコンテンツまで含むが、リンク1つにつきサーバー呼び出しが1回増えるので opt-in で使う。false は Partial Prefetching 下では App Shell の先読みも無効化する。

仕組み：クライアントキャッシュと layout の重複排除

プリフェッチした RSC ペイロードはメモリ上にルートセグメント単位でキー付けして保存される。兄弟遷移（例：/dashboard/settings → /dashboard/analytics）では親 layout を再利用し、更新される leaf page だけを取得する（layout の重複排除）。Cache Components なしなら静的ルートは全体プリフェッチ＋クライアントキャッシュ TTL 既定5分、動的ルートは loading.js が無い限りプリフェッチされず TTL は既定オフ。プリフェッチは本番のみ有効で next dev では起きないため、挙動検証は必ず本番ビルドで行う。スケジューラは「viewport 内 → hover/touch で意図を示した → 新しいリンクが古いものを置換 → 画面外は破棄」の優先順で帯域を溢れさせない。

有効化の条件と実装手順

Partial Prefetching（16.3.0+）は cacheComponents: true と partialPrefetching: true の両方が必要。cacheComponents 無しだと next dev／next build が設定バリデーションで throwする。将来のメジャーで既定化しオプションは削除予定だ。実装は、App Shell に乗せたい静的 UI を 'use cache' で prerender 可能にし、URL 依存部分は <Suspense> で包んで遷移後に解決させる。

// next.config.ts
export default { cacheComponents: true, partialPrefetching: true } satisfies import('next').NextConfig

// app/products/[id]/page.tsx（Server Component）
export const prefetch = 'partial'            // セグメント単位 opt-in
export default function Page({ params }) {
  return (
    <section>
      <StaticShell />                      {/* App Shell に入る */}
      <Suspense fallback={<SkeletonRows />}>
        <ProductDetail params={params} />  {/* URL依存 → 遷移後 */}
      </Suspense>
    </section>
  )
}

落とし穴

いくつか踏みやすい点がある。prefetch は本番のみで dev では検証できない。layout／page 本体に副作用を書くとプリフェッチ中に実行されるので、副作用は Client Component の useEffect に逃がす。prefetch={true} を未 opt-in のルートへ向けると dev console にエラーが出る（グローバルの partialPrefetching かセグメントの export const prefetch = 'partial' で有効化が要る）。キャッシュ寿命を触る experimental.staleTimes は本番非推奨で、安定運用は Cache Components ＋ partialPrefetching 側で設計する。Server Actions の即時無効化（updateTag・revalidatePath・即時期限の revalidateTag）は、プリフェッチ済みルートをクリアする点も覚えておく。

自分が試すなら・ひとこと

試すなら、まず cacheComponents＋partialPrefetching を入れて本番ビルドで兄弟遷移（タブ切替のようなダッシュボード内移動）を観察し、Instant Insights パネルで“instant でない遷移”を洗い出すのが近道だ。注目アイテムのリンクにだけ prefetch={isFeatured ? true : 'auto'} で URL 依存データまで含め、残りは既定の App Shell 先読みに任せる——この「既定は App Shell、重要リンクだけ full」の配分が肝になる。プリフェッチで速くなった遷移に過剰なページトランジションを足すと逆に遅く見えるので、動きは控えめにし prefers-reduced-motion では止める。
