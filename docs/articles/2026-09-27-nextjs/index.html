Jotai を App Router で安全に — atom×RSC境界、useHydrateAtomsとhydration mismatch回避

サーバーで取った初期値を、リクエスト間で漏らさずクライアント状態へ渡す設計を型として押さえる。

📅 2026年9月27日 ⏱ 約3分 🔗 出典 6 件

Jotai は Recoil 系譜のボトムアップ型・アトミックな状態管理（pmndrs製、現行 v2 / 2.8.x）。Zustand が「1つのストアをトップダウンに切る」のに対し、Jotai は atom() という最小の状態単位を組み合わせて依存グラフを作り、購読している atom が変わったコンポーネントだけを再描画する。useState の延長の書き味で、Context の「値が変わると配下が全再描画」も、Zustand のセレクタ設計の負担も避けられるのが持ち味だ。

App Router で効くのは、RSC（Server Components）との境界設計がそのまま状態設計になる点。atom は本質的にクライアント状態で、サーバーで取った初期値をリクエストごとに閉じたストアへ注入できれば、「サーバー取得データをクライアントの初期値にする」頻出パターンを hydration mismatch なしに書ける。逆にここを外すと、グローバルストア共有によるリクエスト間のデータ漏洩や、localStorage 由来の初期値ズレを踏む。

肝は3つ。①Provider は必須級——default store をサーバーで使うと全リクエストが同一ストアを共有し、あるユーザーの状態が別ユーザーへ漏れうる。'use client' の Providers を app/layout.tsx で children に被せ、リクエストごとにストアを分離する。②useHydrateAtoms は初回だけ——名前に反してクライアントフックで、そのストアに一度しか初期値を入れない。③派生・非同期 atom——atom((get)=>...) は依存が変われば自動再計算、read が Promise を返せば非同期 atom になり <Suspense> でサスペンドする（SSR中はPromiseを返せないので初期値は hydrate 方式で渡す）。

実装の王道はこう：

// page.tsx (RSC)
const user = await getUser();
return <UserPanel initialUser={user} />;

// user-panel.tsx ('use client')
useHydrateAtoms([[userAtom, initialUser]]); // 初回だけ
const [user, setUser] = useAtom(userAtom);

落とし穴：hydration は初回レンダのみ。router.push() のソフト遷移では Provider が保持されて再 hydrate されず、サーバーの新しい値が反映されない。対策は (a) app/template.tsx に Provider を置く（遷移ごと再マウント＝再hydrate だが全クライアント状態がリセットされる）か、(b) useHydrateAtoms ＋ useEffect で明示更新。atomWithStorage はサーバーHTMLが initialValue、クライアントは保存値を読むため mismatch の主因——見た目に効くものは ssr:false の next/dynamic か ClientOnly でクライアント専用描画にする。URL同期の atomWithHash は Next 13+ で Router.events 非公開のため実質使えず、URL状態は nuqs や useSearchParams を第一候補に。

ひとこと：Zustand=一枚岩ストア、Jotai=細粒度の派生状態、と状態の「形」で住み分ける。App Router では「RSCで取得→propsでClientへ→useHydrateAtomsで初期値化」を型として覚えれば、漏れず・ズレずに書ける。
