Flutter 3.50 stable定着＋3.51/Dart 3.15 beta始動。例外を「型」にする公式Resultパターンと、const構築子が効く本当の理由

stableは3.50.0のまま（hotfix 3.50.1は未登場）、betaは同日に3.51.0-0.1.preへ。あわせて、uncheckedな例外をsealed Result<T>でコンパイラに網羅強制する公式パターンと、「StatelessWidgetの再構築はタダ」神話の誤りを整理する。

📅 2026年11月14日 ⏱ 約5分 🔗 出典 4 件

リリース状況から。stable は 3.50.0 / Dart 3.14.0（11/11公開）が現在も最新で、公開直後の最初の hotfix 3.50.1 は未登場。一方 beta は同日 11/11 に 3.51.0-0.1.pre が切られ Dart は 3.15.0 に前進——stable が3.50に乗った途端、開発ラインは次サイクルを回し始めた二層構造だ。本番は 3.50.0 を新たなpin基準にしつつ、別ジョブで 3.51 beta を緑化して Dart 3.15 を先取り検証しておくのが定石。以下は今日の digest から、実装で効く2本を読み物として再構成する。

例外を「型」にする：公式 Result パターン

Dartの例外は unchecked——メソッドは例外を宣言する必要がなく、呼び出し側もcatchを強制されない。Service側にいくらドキュメントしても、ViewModelがrepository越しだと見落として uncaught exception になる。公式 App Architecture の「Error handling with Result objects」（3.50基準）はこれを戻り値の型で塞ぐ。sealed class Result<T> に Result.ok(value) / Result.error(error) の2つの名前付き構築子を置き、本体は Ok<T> と Error<T>。末端サービスで try-catch を封じ込め、戻り値を Future<Result<T>> にして返す。消費側のViewModelは switch で分岐するが、sealed ゆえにケース網羅をコンパイラが強制するので、呼び出し側にunwrapを強要できる＝「エラー確認のし忘れ」が型レベルで消える。

sealed class Result<T> {
  const factory Result.ok(T value) = Ok._;
  const factory Result.error(Exception error) = Error._;
}
// 消費側（ViewModel）: sealed なので case 漏れはコンパイルエラー
switch (result) {
  case Ok<UserProfile>():    userProfile = result.value;
  case Error<UserProfile>(): error = result.error;
}
notifyListeners();

自作が面倒なら pub.dev の result_dart / result_type / multiple_result が既製。なお Error は dart:core の Error を shadow する点だけ注意。

constが効く本当の理由：再構築の「打ち切り」

公式 perf best-practices「Control build() cost」の核心は、「前フレームと同一インスタンスの子widgetに再会した時点で、子孫を再構築する走査が止まる」こと。同一かどうかは operator== で評価される。const 構築子はコンパイル時に正準（canonical）インスタンス化され、毎フレーム同じインスタンスが渡るので、この「同一インスタンスで打ち切り」が発火する。つまり const 化は見た目のためでなく再構築の走査を途中で止めるための最適化だ。

「StatelessWidgetの再構築はタダ」は神話。コストは subtree の深さ・構築子の複雑さ・アロケーション圧に比例し、非const子は毎フレーム新規オブジェクトを確保してminor GCで jank を招き得る（非査読ブログの実測では12ネストのカードを7構築子const化＋TextStyle巻き上げで 4.2ms→1.8ms など。端末・ビルドモード記載なしで数値は鵜呑み厳禁）。実務の武器は const・部分木抽出・ValueKey・child:退避 の4つ。打ち切り判定を identical() と書く解説も見かけるが、公式表現は operator== なので、== を安易にoverrideしない（overrideはO(N²)化、leaf widgetのみ例外）のが安全側だ。

遷移を1ルートだけ自作するなら PageRouteBuilder

アプリ全体の遷移は PageTransitionsTheme＋PageTransitionsBuilder 群で差すが、特定1ルートだけ別演出にしたいなら PageRouteBuilder。pageBuilder（中身・初回ビルドのみ＝重い構築はここ）と transitionsBuilder（遷移・毎フレーム呼ばれるので軽く）の2コールバックで、animation.drive(Tween(...).chain(CurveTween(curve:))) を SlideTransition に流すのが定石。なお 3.50 の material/cupertino 分離構成で iOS風横スライド（CupertinoPageTransitionsBuilder）を差すなら package:cupertino_ui/cupertino_ui.dart の import が別途必要になった点に注意。

ひとことまとめ

stableは3.50で据わり、設計の勘所は「例外を型に／再構築を打ち切る」。Resultで確認漏れを封じ、const＋ValueKeyでGC起因のjankを削る——どちらも“速くする”前に“無駄を生まない”側の工夫だ。
