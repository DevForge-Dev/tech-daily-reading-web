Flutter 3.44系のデスクトップ/Web強化 — マルチウィンドウ・Wasm既定化・Material切り出しと、90/120Hzのフレーム予算

現行安定版は3.44.7／Dart 3.12。DesktopはCanonical主導でマルチウィンドウ対応、Webはflutter build web --wasmでWasmGCへ、ロードマップはWasmを既定ターゲットに。MaterialはSDKから切り出され独立更新。90/120Hz時代の1フレーム8〜11ms予算を軸に、今の勘所を整理する。

📅 2026年8月15日 ⏱ 約3分 🔗 出典 4 件

現行安定版はFlutter 3.44.7／Dart 3.12（docsは2026-08-04更新）。次の機能リリースは2026年8月のリリース窓に入り、ロードマップは年4回・最低4回のstableをコミットしている。昨日はImpeller既定化と状態管理を扱ったので、今日はデスクトップ/Webの土台強化と90/120Hz時代のフレーム予算を軸に見ていく。

何が新しいか。Desktopはマルチウィンドウ対応が進み、複数ウィンドウを1つのFlutterアプリから制御できるようになった。Canonicalがデスクトップ開発を主導し、Linux／デスクトップ体験を底上げしている。WebはWebAssemblyレンダリングとアクセシビリティが改善し、flutter build web --wasm でWasmGCターゲットを出力できる。ロードマップはWasmをWebの既定コンパイルターゲットにする方針で、移行は dart:html／package:js を dart:js_interop へ置き換える。加えてMaterial／Cupertinoがコアから material_ui／cupertino_ui へ切り出され、独立バージョニングでM3更新がSDKを待たず届き、app sizeも削減される。iOS/macOSはSwift Package Managerが新規既定（CocoaPods段階的廃止）だ。

仕組みとポイント。フラッグシップは90Hz/120Hzが主流で、1フレームを8〜11msで描かないとカクつきを知覚する。フレーム予算は60fps=16ms／90fps=11ms／120fps=8.3ms、rasterは60fpsで4ms未満／120fpsで8.3ms未満が目標だ。計測は必ずprofileモードで行い、DevToolsのPerformance／Memory／Networkの3タブでUIスレッド・Rasterスレッドの処理状況とjankフレーム位置を可視化する。最も多い性能問題は不要なwidget rebuildで、対策は const 徹底・大きな build() の分割・select による局所再描画・アニメ領域を RepaintBoundary で隔離。

自分が試すなら、デスクトップ向けにマルチウィンドウのサブ画面（プレビュー用の別ウィンドウ等）を1つ足して制御APIの手触りを確かめ、Web側は --wasm ビルドで初期描画とスクロールのjankを実機比較したい。dart:js_interop への置換は影響範囲を先に洗っておく。

注意点。Wasm既定化やMaterial切り出しは依存とビルド構成に破壊的変更を伴う。移行前は flutter upgrade・Impeller実機検証（差の切り分けは --no-enable-impeller）・dart fix/format＋flutter analyze で警告を解消しておく。SPM移行はプラグインの対応状況を確認してから進める。

ひとことまとめ：3.44系はデスクトップ（マルチウィンドウ）とWeb（Wasm）を前へ、MaterialはSDKから独立させて更新を速めた回。土台が広がるほど、90/120Hzのフレーム予算を守る計測規律が効いてくる。
