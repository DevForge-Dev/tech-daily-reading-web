Route HandlerからSSEでストリーミング配信 — 即returnしてenqueue、バッファ層を外し、abortを連鎖させる

LLMトークン/進捗/通知/ライブダッシュボードをSSEで。ReadableStreamの即return、no-transform・X-Accel-Buffering、request.signalでの中断連鎖、EventSource vs fetch+getReaderの使い分けまでを土台化する。

📅 2026年9月17日 ⏱ 約4分 🔗 出典 5 件

チャットの「トークンが1文字ずつ出る」、長時間ジョブの進捗バー、通知バッジ、ライブダッシュボード。2026 年の Next.js アプリではサーバー→クライアントへ継続的に push する要件が当たり前になった。これを最軽量で実現するのが Server-Sent Events（SSE）で、HTTP の 1 本のレスポンスを閉じずに text/event-stream としてチャンクを流し続ける。双方向や低遅延バイナリが要るときだけ WebSocket を検討すればよく、単方向 push なら SSE は「ただの HTTP・自動再接続・実装が桁違いに軽い」と利点が多い。

ワイヤープロトコルはほぼ改行だけ

1 メッセージ＝ data: ... のあとに空行（改行2つ）で 1 イベント確定。これを忘れるとクライアントがイベント境界を検出できない。省略可能フィールドは event:（名前付き）、id:（再接続時に Last-Event-ID で送り返される）、retry:（再接続間隔）、そしてコロン始まりのコメント行はハートビート（keep-alive ping）に使う。JSON は 1 行に詰めるのが定石だ。

最大の落とし穴は「途中の層がバッファする」

ストリームが正しくても、間の層が全チャンクを溜めてから一括転送すると体感は「一括表示」に退化する。潰すべきは、Next.js の圧縮（Cache-Control: no-cache, no-transform を付ける）、リバースプロキシ（X-Accel-Buffering: no で無効化）、CDN のバッファ、そしてハンドラの書き方だ。正解は ReadableStream を即 return し、start(controller) の中で await しながら enqueue すること。ループを回し切ってから返すと当然バッファされる。NextResponse は溜めることがあるので素の new Response(stream) を使い、export const dynamic = 'force-dynamic' で静的化を確実に外す。

クリーンアップと中断連鎖

クライアントが離脱すると request.signal が abort する。setInterval / DB 購読 / 上流 fetch を必ず止めないと、サーバーで interval とストリームがリークして CPU と接続を食い続ける。LLM 中継なら、クライアントの AbortController.abort() がサーバーの request.signal を発火させ、上流 SDK の呼び出しまで連鎖キャンセルできる＝課金の無駄も止まる。

受信の使い分け・ひとことまとめ

通知系のように GET と自動再接続で足りるなら EventSource（'use client' 必須）。会話履歴を POST したい・認証ヘッダを載せたいチャット系は、EventSource が GET しか投げられない制約に当たるので fetch + res.body.getReader() + TextDecoder で自前パースする（再接続は自前か @microsoft/fetch-event-source）。高レベルに寄せるなら Vercel AI SDK の streamText().toUIMessageStreamResponse() ＋ useChat がフレーミング・中断・再接続を隠蔽してくれる。要点は「即 return して enqueue、バッファ層を全部外す、abort を必ず処理する」の 3 つだ。
