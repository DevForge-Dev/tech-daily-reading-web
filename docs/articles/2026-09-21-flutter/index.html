material_ui / cupertino_ui 1.0 が standalone パッケージ化 — SDKを待たずデザインシステムを更新

本日の主役はデザインシステムのコアSDKからの切り離し。material_ui / cupertino_ui 1.0 がpub.devからweekly配信され、SDK更新を待たずウィジェット改善を受け取れる。使う分だけ依存でき app size 削減にも効く。現行安定は Flutter 3.47.4 / Dart 3.13.3。

📅 2026年9月21日 ⏱ 約3分 🔗 出典 3 件

背景。Flutterではデザインシステム（Material/Cupertino）がコアSDKに同梱され、ウィジェットの改善や新コンポーネントを受け取るにはSDK自体の更新を待つ必要があった。本日の主役 material_ui / cupertino_ui 1.0 の standalone パッケージ化 はこの前提を崩す。

何が新しいか

デザインシステムがコアSDKから切り離され、pub.devからweeklyでリリースされる。SDKを更新しなくてもウィジェット改善・新コンポーネントを取り込めるうえ、使うデザインシステムだけ依存できるので app size削減にも効く。移行は dart fix --apply --code=migrate_design_widgets でimportを自動書き換え。旧 material.dart / cupertino.dart は2026年秋（11月stable予定）にdeprecated見込みだ。

足回り：安定版と言語機能

現行安定は Flutter 3.47.4 / Dart 3.13.3（9/11 patch）。3.47系はImpellerが全デスクトップ既定・Widget Previews stable・最低iOS15/macOS12・iOS26/Xcode26対応が到達点。Dart 3.13 でprimary constructors / dot shorthandsがstableになり、型が推論できる文脈で .start のように先頭ドットで列挙値・staticメンバ・constructorを省略でき、冗長な型名の反復を減らせる。betaは Flutter 3.48 / Dart 3.14（WasmGC既定化・Androidの Impeller 一本化・build hooks stable）。

実務での使いどころ・自分が試すなら

新規は最初からstandalone前提で依存を組むと、後の移行コストが小さい。既存アプリは dart fix をブランチで当てて差分を確認してからマージ。デザインシステムだけ先行アップデートしてUI改善を早取りする運用も現実的だ。状態管理は新規=Riverpod 3.3.1＋@riverpod codegen、監査/規制はBloc 9.0、ルーティングはgo_routerの型安全ルート（@TypedGoRoute）が引き続き既定線。

注意点・落とし穴

weekly配信ゆえバージョン整合の管理が要る。標準ウィジェットは11月stableまで併存するが、deprecated後の移行を見越して早めにimportを寄せておくと安全だ。

ひとことまとめ

UIの進化速度がSDKのリリース周期から解き放たれた——それが1.0 standalone化の本質だ。
