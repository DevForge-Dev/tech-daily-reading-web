スワイプで消すカードスタック — Pointer Events＋setPointerCapture＋「距離 OR 速度」で依存ゼロの fling-to-dismiss

指に1:1追従して投げれば飛び、未達ならバネで戻る。Pointer Events一本化・setPointerCapture・距離/速度のOR判定・transformのみ描画、そしてWCAG 2.5.7のボタン代替までを一気に押さえる。

📅 2026年9月15日 ⏱ 約5分 🔗 出典 4 件

モバイルの通知消去、オンボーディングのカード送り、マッチングの候補送りで頻出する直接操作（direct manipulation）——「カードを掴んで横に投げると消える」あのパターンを、依存ゼロで正しく作るための勘所を整理する。指の動きに1:1で追従し、勢いよく投げれば飛び、中途半端なら手元に戻る物理的な手応えが「操作している感」を生む。似て非なる既存パターン（vaul=縦シートのdismiss、dnd-kit=並べ替え）とは役割が違い、本テーマは最前面カードを横に投げて捨てる（fling to dismiss）ジェスチャそのものだ。

何が要点か

核心は4点。(1) pointerdown/move/up のPointer Events だけで mouse/touch/pen を一本化（二重実装や300msクリック、ゴーストクリックを回避）。(2) pointerdown 内で el.setPointerCapture(e.pointerId) を呼び、指がカードや画面の外に出てもイベントを対象要素に届け続ける——これを忘れると「速く動かすとドラッグが切れる」最頻出バグになる。(3) 投げたか否かは移動量 or 放した瞬間の速度のどちらかが閾値超えで判定（OR にすると「勢いよく弾く」も「ぐいっと寄せる」も両取り）。(4) 未達はバネで原点復帰、超過はその向きへ画面外まで飛ばしてDOM除去。

仕組みと最小コード

Pointer Events 自体に velocity は無いので自前計算する。pointermove ごとに {x,t} を数点保持し、放す直前の直近2〜3サンプルの平均で Δx/Δt（px/ms）を求める（1点差分はノイズで誤爆する）。動かすのは transform: translate() rotate() と opacity だけに閉じ、left/width は使わない（リフローでカクつく）。ドラッグ量に応じて端ほど回転を強め、LIKE/NOPE ラベルの opacity を offsetX にマップすると意図が伝わる。

function onPointerDown(e){
  if (e.button !== 0) return;          // 主ボタンのみ
  card.setPointerCapture(e.pointerId); // ★枠外でも追従
  start = {x:e.clientX,y:e.clientY};
  samples = [{x:e.clientX,t:e.timeStamp}];
}
function onPointerUp(e){
  const dx = e.clientX - start.x;
  const a = samples[0], b = samples.at(-1);
  const v = (b.x-a.x)/Math.max(1,b.t-a.t);        // px/ms
  (Math.abs(dx)>120 || Math.abs(v)>0.5) ? flingOut(Math.sign(dx||v)) : springBack();
}
card.addEventListener('pointercancel', springBack); // ★中断で復帰

CSS では touch-action を必ず指定する。横スワイプだけ奪い縦スクロールは残すなら touch-action: pan-y;、全方位ドラッグなら touch-action: none;。未指定だとモバイルでスクロール/ピンチと競合し、ドラッグ中に pointercancel が飛んで掴みが外れる。

Next.js（App Router）での組み込み

ドラッグ制御の殻だけ 'use client' に隔離し、カードの中身（画像・テキスト）はRSC のまま next/image 等で描画して children として流し込む。候補一覧は RSC で取得、追加ロードは Server Action か Route Handler でページング。「既読/いいね/スキップ」は Server Action に送り、useOptimistic で投げた瞬間に UI からカードを除去→失敗時ロールバック。初期スタックは transform 無しの静止状態で描くので hydration mismatch が起きず、JS 未ロードでも内容とボタンは見える（Progressive Enhancement）。Strict Mode の二重マウント対策として、リスナ登録・rAF・spring ループは useEffect の cleanup で必ず解除する。ライブラリは依存ゼロの vanilla（数十行・挙動を完全掌握）か、宣言的に最短な Motion（drag="x"＋dragSnapToOrigin＋onDragEnd の info.offset.x/info.velocity.x 判定）が現実的。

落とし穴とアクセシビリティ

最重要は WCAG 2.2 SC 2.5.7 Dragging Movements（AA）——ドラッグで達成する機能は単一ポインタの代替が必須なので、各カードに「スキップ／いいね」ボタンを併設し、ドラッグはショートカット扱いにする。キーボードは ←/→/Enter で同アクション、消去は aria-live="polite" で通知し「元に戻す」を提供。prefers-reduced-motion: reduce では慣性・回転・バウンドを止め、消去という結果だけ残す（即時 or 短いフェード）。その他の定番バグは、pointercancel 未処理での固着、setPointerCapture 忘れでの切断、velocity の1サンプル計算での誤爆、画像のネイティブ drag との競合（user-drag:none / draggable="false"）。

ひとことまとめ

「Pointer Events 一本化＋setPointerCapture＋距離OR速度＋バネ復帰」の4点と、transform/opacity だけで動かす規律を守れば、依存ゼロでも 60fps の投げ捨てUIは作れる。そのうえで 2.5.7 のボタン代替と reduced-motion を最初から設計に織り込むのが本題だ。自分が試すなら、まず vanilla で最小実装して挙動を掌握し、スタック表示（背後カードの scale+translateY）と Server Action 連携を足す順で組む。
