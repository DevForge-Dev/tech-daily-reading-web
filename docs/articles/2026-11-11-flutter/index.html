Flutter — プロセス終了をまたいでUI状態を復元するState Restoration（3.50はなお足踏み）

stable 3.50は11/11も未公開で昇格ゲートは7日据え置き。新機能待ちの谷間こそ、OSのkillに耐えるState Restorationで足回りを固める好機。

📅 2026年11月11日 ⏱ 約3分 🔗 出典 3 件

背景：stable 3.50 は 11/11 時点でも未公開、beta 3.50.0-0.4.pre は 11/4 以来7日据え置き、release-tracker #195830 は 11/2 起票以来"人の動き"ゼロ（Dart hash 欄はプレースホルダのまま）。本番は 3.47.9 を pin し続けるのが安全だ。この新機能待ちの谷間こそ、OS の kill に耐える State Restoration で足回りを固める好機として掘り下げる。

何の問題を解くか：OS はバックグラウンドのアプリをいつでも kill する。保存が無ければ復帰時は"ゼロから起動"。しかも Android の instance state は 1MB 上限で、超えると TransactionTooLargeException でネイティブ側がクラッシュする。

仕組み：① MaterialApp 等に restorationScopeId を定義すると RootRestorationScope が注入され復元が自動 ON。② TextField/ScrollView 等に restorationId を付けると組込の復元が効く。③ カスタム widget は RestorationMixin を混ぜ、restorationId getter と restoreState() を実装し、その中で registerForRestoration(property, id) を呼ぶ。restoreState は initState 直後と新データ到着時に呼ばれる。

状態は素のフィールドでなく RestorableInt/String/Bool 等の RestorableProperty で保持し、toPrimitives()/fromPrimitives() で往復、値が変われば notifyListeners() で保存を促す。全 property は State.dispose で dispose 必須。遷移自体も残すなら Navigator を restorablePush/restorablePushNamed に置換する。

自分が試すなら・落とし穴：端末を「バックグラウンドで state を保存しない」設定にしてプロセス終了からの復元を検証し、終わったら必ず元へ戻す。復元対象は"UI の見た目の状態"に絞り、ネットワーク由来のデータは復元でなく再取得——これは 1MB 制約にも素直に合う。まとめ：3.50 待ちで手が空くいまこそ、落ちても戻るアプリへ足回りを底上げしておきたい。
